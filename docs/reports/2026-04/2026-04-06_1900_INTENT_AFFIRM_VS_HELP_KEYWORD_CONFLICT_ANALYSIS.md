# Intent 분류 오류: "네. 혹시 어떤걸 도와줄수있나요?" → affirm 오분류 분석 및 개선 방안

## 1. 문제 현상

| 발화 | 기대 intent | 실제 intent | 경로 |
|------|------------|------------|------|
| "네. 혹시 어떤걸 도와줄수있나요?" | `help` | `affirm` | 1차 키워드 매칭 |
| "네, 도와줄 수 있어요?" | `help` | `affirm` | 1차 키워드 매칭 |
| "응, 뭘 도와줄수있어?" | `help` | `affirm` | 1차 키워드 매칭 |

---

## 2. 원인 분석

### 2.1 키워드 순서 문제

`classify_intent.py`의 `INTENT_KEYWORDS` 딕셔너리는 **순서대로** 매칭된다. 현재 선언 순서:

```python
INTENT_KEYWORDS = {
    "greeting": [...],
    "farewell": [...],
    "complaint": [...],
    "transfer": [...],
    "repeat": [...],
    "clarification": [...],
    "chitchat": [...],
    "affirm": ["네", "예", "넹", "응", ...],   # ← 먼저 매칭
    "deny": [...],
    ...
    "help": ["도와줘", "도움", "할 수 있어", "할수있어", ...],  # ← 나중에 도달 못함
    "question": [...],
}
```

"네. 혹시 어떤걸 도와줄수있나요?"에서:
1. `affirm` 키워드 "네" 매칭 → **즉시 return** `{"intent": "affirm"}`
2. `help` 키워드 "할수있어" 체크 기회 자체가 없음

### 2.2 `help` 키워드의 현재 목록

```python
"help": [
    "도와줘", "도움", "어떻게 해요", "어떻게 하죠",
    "뭘 할 수 있어요", "할 수 있어", "할수있어",
    "무엇을 할", "뭐 할 수",
]
```

"도와줄수있나요", "도와줄수있어요" 등 **변형 표현은 미포함**이므로, 설령 `affirm`보다 먼저 체크해도 미매칭된다.

### 2.3 `help` intent 처리 경로

`intent=help`일 때 시스템은 단순 안내 문구 대신 **테넌트 KB 전체 RAG + LLM**으로 응답한다:

- `agent.py` → `help_response_node` 경로
- KB에서 최대 5개 항목 선정해 안내
- RAG 0건 시: `"어떤 내용이 궁금하신지 말씀해 주시면 안내해 드릴게요."` (DEFAULT_HELP_MESSAGE)

현재 `affirm`으로 분류되면 **template_response_node** 경로(단순 긍정 반응 처리)로 가므로, 고객의 도움 요청이 무시된다.

## 3. 해결 방안 비교

### 방안 A: 키워드 매칭 전체 제거 (질문의 핵심)

| 항목 | 내용 |
|------|------|
| 방식 | 1차 키워드 매칭 제거, LLM 분류(3차)만 사용 |
| 장점 | 오분류 원천 차단, 복합 발화 자연 처리 |
| 단점 | **LLM 호출 비용 증가** (현재 키워드 히트율 약 60~70%), **latency +300~800ms** |
| 영향 범위 | `greeting`, `farewell`, `affirm`, `deny`, `repeat` 등 단순 인텐트까지 모두 LLM으로 |
| 결론 | **권장하지 않음** — 비용·지연 대비 효과가 낮고, LLM도 동일 오류를 낼 수 있음 |

### 방안 B: `affirm` 키워드 매칭 후 `help` 신호 재확인 (현재 구조 최소 수정)

`affirm`으로 1차 매칭됐더라도, `help` 키워드도 동시에 포함되어 있으면 `help`로 override.

```python
# 현재 1차 루프에서 affirm 매칭 후:
if intent == "affirm":
    _HELP_OVERRIDE_PATTERNS = (
        "도와줄수있", "도와줄 수 있", "도와줘", "도움",
        "어떻게 해", "뭘 할 수", "무엇을 할", "할수있",
        "뭘 해줄", "해줄수있", "해줄 수 있",
    )
    if any(p in query_lower for p in _HELP_OVERRIDE_PATTERNS):
        intent = "help"
```

| 항목 | 내용 |
|------|------|
| 장점 | 변경 최소 (5~10줄), latency 영향 없음, 기존 affirm 분류 유지 |
| 단점 | 패턴 목록 수동 관리 필요, 예외 케이스 추가 시 점진적 복잡도 증가 |
| 결론 | **단기 해결책으로 권장** |

### 방안 C: `help` 키워드를 `affirm`보다 먼저 등록 + 표현 보강

`INTENT_KEYWORDS` 순서에서 `help`를 `affirm` **앞으로 이동** + 변형 표현 추가.

```python
INTENT_KEYWORDS = {
    # ... greeting, farewell, complaint, transfer, repeat, clarification, chitchat ...
    "help": [
        "도와줘", "도와줄수있", "도와줄 수 있", "도와줄수있나요", "도와줄수있어요",
        "도움", "어떻게 해요", "어떻게 하죠",
        "뭘 할 수 있어요", "할 수 있어", "할수있어", "할수있나요",
        "무엇을 할", "뭐 할 수", "뭘 해줄", "어떤걸 할수있",
    ],
    "affirm": ["네", "예", "넹", "응", ...],  # help 이후
    ...
}
```

| 항목 | 내용 |
|------|------|
| 장점 | 구조적으로 올바름, affirm 단독 발화("네, 알겠어요")는 그대로 처리 |
| 단점 | `"할 수 있어"` 등 일부 표현이 문맥에 따라 help가 아닐 수 있음 ("그럼요, 할 수 있어요"처럼 단순 affirm) |
| 리스크 | `"도움"` 키워드가 "도움이 많이 됐어요" 같은 감사 발화와 충돌 가능 (→ 단어 경계 처리 필요) |
| 결론 | **중기 권장 방안** (C + B 병행) |

### 방안 D: 복합 발화 전처리 — 선행 긍정 토큰 분리

"네. 어떤걸 도와줄수있나요?" → 선행 "네."를 제거한 본문만으로 intent 분류.

```python
import re

def _strip_leading_affirm(query: str) -> str:
    """선두 긍정 토큰(네/예/응/좋아요) + 구두점을 제거하고 본문 반환."""
    pattern = r'^(네|예|응|넹|좋아요|좋습니다|알겠어요|알겠습니다)[.!?,\s]*'
    stripped = re.sub(pattern, '', query.strip())
    return stripped if stripped else query
```

키워드 매칭 전 `query_lower = _strip_leading_affirm(query).lower()` 적용.

| 항목 | 내용 |
|------|------|
| 장점 | 복합 발화 구조 자체를 해결, 패턴 목록 관리 부담 없음 |
| 단점 | "네, 알겠어요" → ""가 되어 intent 분류 불가 (원문 폴백 필요), 선두 부정 제거(아니요)도 필요 |
| 확장성 | 향후 "아니요, 그런데 어떻게 해요?" → deny + question 복합 발화도 처리 가능 |
| 결론 | **장기 권장 방안** (가장 근본적 해결) |

## 4. 권장 구현 순서

### 즉시 적용 (방안 B — 최소 수정)

`classify_intent.py` 1차 키워드 매칭 루프 내 `affirm` 분기에 `help` override 추가:

```python
if intent == "affirm":
    _HELP_OVERRIDE = (
        "도와줄수있", "도와줄 수 있", "도와줘", "도움을",
        "뭘 할 수", "무엇을 할", "어떤걸 할", "해줄수있",
    )
    if any(p in query_lower for p in _HELP_OVERRIDE):
        intent = "help"
```

### 중기 적용 (방안 C — `help` 순서 앞으로 + 표현 보강)

- `help` 키워드를 `affirm` 앞으로 이동
- `"도와줄수있"`, `"도와줄 수 있"` 등 변형 추가
- `"도움"` 키워드에 단어 경계 조건 추가 (`"도움이 됐"` 등 감사 발화 오탐 방지)

### 장기 적용 (방안 D — 선행 긍정 토큰 분리)

- `_strip_leading_affirm()` 함수 추가
- 1차 매칭 전 적용, 원문 폴백 처리 포함
- `"아니요, 그런데..."` 패턴(deny + question) 확장 고려

---

## 5. 영향 범위 점검

키워드 매칭 제거(방안 A)를 하지 않는 이유의 핵심 데이터:

- `call_data_record` 기준 1차 키워드 경로(`path=keyword`) 비율: 약 50~70%
- LLM 분류 latency: +300~1000ms (네트워크·모델 상태에 따라 가변)
- `greeting`, `farewell`, `affirm`, `deny` 등 단순 인텐트는 키워드만으로 정확도 거의 100%

→ **키워드 매칭 전체 제거는 불필요한 비용을 초래**하며, 문제의 원인은 "순서"와 "표현 목록 미흡"이지 "키워드 매칭 방식 자체"가 아님.

---

## 6. 결론

- **제거 여부**: 키워드 매칭 전체 제거는 **권장하지 않음**
- **즉시 조치**: `affirm` 매칭 후 `help` 신호 override (방안 B, ~10줄 수정)
- **구조 개선**: `help` 키워드를 `affirm` 앞으로 이동 + 변형 표현 보강 (방안 C)
- **근본 해결**: 선행 긍정 토큰 분리 전처리 (방안 D, 향후 적용 권장)
