# "업로드해도 안 보인다" 진짜 원인 확정 — 실제 브라우저 UI 조작으로 재현·수정

- 작성일: 2026-08-07
- 버전: v1.0
- 관련 문서: [2026-08-07_auto_reseed_side_effect_root_cause_fix.md](2026-08-07_auto_reseed_side_effect_root_cause_fix.md)

## 1. 사용자 재보고

서버 재시작 후에도 "삭제도 다 안 되고, 업로드해도 안 보인다"는 재보고. "직접 확인해봐"라는
명시적 요청.

## 2. 실제로 확인한 방법(코드 리뷰가 아니라 curl + 실제 브라우저 UI 클릭)

1. **삭제 재검증**: curl로 owner=1001에 문서 업로드 → `DELETE /api/knowledge-base/documents?
   owner=1001` 호출 → `deleted_chunks`/`deleted_documents`가 실제 업로드한 만큼 정확히
   반환되고, 재조회 시 0건임을 확인 — **삭제는 실제로 완벽하게 동작**.
2. **업로드 재검증(실제 브라우저 UI로 직접 클릭)**: Playwright로 실제 페이지를 열어
   `localStorage.tenant_id=1001` 설정 → "지식 업로드" 탭 → 제목/본문 입력 → **실제 "업로드"
   버튼을 클릭** → Story 1.50에 따라 자동으로 "지식베이스 현황" 탭으로 이동.
   - **여기서 실제 버그를 발견**: 이동한 "지식베이스 현황" 화면이 "총 색인 청크 수: 0"으로
     표시됨 — 그런데 동시에 curl로 백엔드를 확인하면 문서가 실제로는 정상 업로드되어 있었다
     (`GET /api/knowledge-base/documents?owner=1001` → 문서 존재, `chunk_count: 1`).

## 3. 근본 원인

`handleUploadDocument()`(업로드 버튼 핸들러)가 성공 후 **`loadKbDocuments()`만 호출하고
`loadKbInventory()`는 호출하지 않았다.** "지식베이스 현황" 탭의 요약 카드(총 색인 청크 수,
도메인별 분포, 업로드 문서 기반 자동 구성 현황)는 전부 `kbInventory` 상태에서 오는데, 이
상태가 갱신되지 않은 채 Story 1.50의 "업로드 성공 시 지식베이스 현황 탭으로 자동 이동" 기능이
실행되어, **사용자는 업로드 직후 곧바로 오래된(0건) 요약 화면을 보게 됐다.** 이것이 "업로드해도
안 보인다"는 반복 보고의 실제 원인이었다.

같은 문제가 개별 문서 삭제(`handleDeleteDocument`)에도 있었다 — 문서 목록에서는 사라지지만
"지식베이스 현황"의 총 청크 수는 갱신되지 않아 문서가 여전히 있는 것처럼 보일 수 있었다.

## 4. 수정

`frontend/app/settings/ai-assistant/docs/page.tsx`:

- `handleUploadDocument()`: 업로드 성공 시 `loadKbDocuments()`와 함께 **`loadKbInventory()`도
  호출**하도록 추가.
- `handleDeleteDocument()`: 개별 문서 삭제 성공 시에도 동일하게 `loadKbInventory()` 추가.

## 5. 최종 재검증(실제 브라우저로 업로드 → 즉시 확인)

1. curl로 1001 클린 상태 확보.
2. Playwright로 실제 "지식 업로드" 탭에서 제목("ui-diag-test-2")/본문 입력 → "업로드" 버튼
   클릭.
3. 자동 이동된 "지식베이스 현황" 화면에서 **"총 색인 청크 수: 1", "업로드 문서별 상세 카드"에
   "방금 등록됨" 배지와 함께 정상 표시됨을 확인** — 수정 전에는 "0"이었던 것과 명확히 대비.
4. 테스트 데이터는 확인 직후 삭제.

## 6. 검증

- `npx tsc --noEmit`/`npx eslint` 0에러.
- `tests_new/unit -k "self_service or knowledge"` — 기존 무관 사전 결함 1건 제외 전부 통과
  (이번 수정은 프론트엔드 전용이라 백엔드 회귀 영향 없음, 확인 차 재실행).
- **실제 브라우저 UI 조작(클릭)으로 재현 → 원인 특정 → 수정 → 재검증까지 전 과정을 실물로
  확인**(curl만으로는 발견 못 했을 버그 — 반드시 프론트엔드 상태 관리 흐름까지 브라우저에서
  직접 클릭해봐야 발견 가능했다).

## 7. 교훈

- **"업로드/삭제 API 자체는 잘 작동하는데 화면에 반영이 안 된다"는 보고는, API 성공 여부가
  아니라 "그 성공 이후 프론트엔드가 어떤 상태를 갱신하는가"의 문제일 가능성이 높다** — 이번에
  `kbDocuments`는 갱신하면서 `kbInventory`는 빠뜨린 것처럼, 같은 데이터를 표시하는 여러 상태
  중 일부만 갱신하고 나머지를 놓치는 실수가 이 화면에서 벌써 여러 번(문서 목록/현황 요약/
  qa 목록 각각 별도 상태) 반복됐다.
- **curl(백엔드 API 직접 호출) 검증만으로는 이런 프론트엔드 상태 관리 버그를 절대 발견할 수
  없다** — 오늘 여러 차례 "백엔드는 정상"이라고 결론 내렸던 것도 맞는 말이었지만, 사용자가
  실제로 마주하는 문제(프론트 상태 갱신 누락)는 실제 브라우저에서 버튼을 눌러봐야만 보인다.
  앞으로 "화면에 반영이 안 된다"는 보고를 받으면 curl 검증에 그치지 말고 반드시 실제 UI
  조작까지 재현할 것.
- 이 화면(`docs/page.tsx`)은 `items`(qa)/`catalog`/`screens`/`kbInventory`/`kbDocuments`
  5개의 독립 상태를 여러 액션(업로드/삭제/전체삭제)이 각각 부분적으로만 갱신하는 구조라
  이런 누락이 반복되기 쉽다 — 장기적으로는 "이 액션이 성공하면 관련된 모든 상태를 무효화한다"는
  단일 헬퍼(예: `refreshAllKnowledgeBaseState()`)로 통합하는 리팩터링을 고려할 만하다(이번엔
  범위를 최소화하기 위해 각 핸들러에 개별적으로 누락된 호출만 추가함).
