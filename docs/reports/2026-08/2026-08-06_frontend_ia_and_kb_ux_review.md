## 0.5 (2026-08-06 후속) 실제 오류 수정 — 지식 문서 업로드 422(Failed to fetch)

**증상**: `/api/knowledge-base/documents` 업로드 시 `owner`/`title`/`source_type`이 모두
`"input": null`로 "missing" 처리되며 422 발생.

**근본 원인**: `frontend/lib/api.ts::apiJson()`가 body 타입과 무관하게 항상
`authHeaders()`(기본값 `includeJsonContentType=true`)로 `Content-Type: application/json`을
먼저 설정해버렸다. 이후 `FormData` 여부를 검사해 JSON 직렬화는 건너뛰었지만, **이미 설정된
`Content-Type` 헤더는 그대로 남아** 브라우저가 `multipart/form-data; boundary=...`를 자동
설정하지 못하게 막았다 — 결과적으로 서버는 body를 멀티파트로 파싱하지 못해 모든 `Form(...)`
필드가 비어 보였다.

**수정**: `isFormLike = rawBody instanceof FormData || rawBody instanceof Blob`을 먼저 계산해
`authHeaders(!isFormLike)`로 호출하고, FormData/Blob이면 `Content-Type` 헤더를 명시적으로
삭제하도록 변경(`frontend/lib/api.ts`). 이 함수는 지식 문서 업로드뿐 아니라 앱 전체의 모든
`apiJson()` 기반 파일 업로드가 공유하므로 일괄 수정된다.

**교훈**: `fetch`에 `FormData` body를 넘길 때는 `Content-Type` 헤더를 절대 수동 설정하면 안
된다(브라우저가 무작위 boundary를 포함해 자동 생성해야 함) — 공용 API 헬퍼에 기본
`Content-Type`을 미리 깔아두는 패턴이 있다면, FormData 요청 경로에서 반드시 이 헤더를 제거하는
분기를 넣을 것.

다시 업로드해 정상 동작하는지 확인 부탁드립니다(서버 재시작 불필요 — 프론트엔드 전용 수정,
Next.js dev 서버가 자동 반영).

## 1. "AI 에이전트" 메뉴 중복 — 확인됨, 설정 하위로 일원화 필요

`frontend/components/AppHeader.tsx`:

```tsx
const MAIN_NAV = [
  ...
  { href: '/ai-agent', label: 'AI 에이전트' },   // 최상위 메뉴
];

const SETTINGS_NAV = [
  ...
  { kind: 'link', href: '/ai-agent', label: 'AI 에이전트 플랫폼' },  // 설정 하위에도 동일 링크
  { kind: 'link', href: '/settings/ai-assistant', label: 'AI 도우미 변경 이력' },
];
```

**같은 `/ai-agent` 라우트를 최상위 메뉴와 설정 하위 메뉴 양쪽에 중복 등록**한 상태다. 코드
주석(`Story 1.36(FR34-B): 새 진입점은 /ai-agent — 기존 링크 호환을 위해 유지`)을 보면, 원래
"설정 하위"에 있던 진입점을 Story 1.36에서 최상위로 승격시키면서 **구 링크를 지우지 않고
남겨둔 것**이 원인이다. 사용자가 지적한 대로 관리 기능을 최상위 메뉴에 노출할 이유가 없다
(통화이력/연락처/예약관리 등과 성격이 다른 "설정" 성격의 화면).

**권고**: `MAIN_NAV`에서 `/ai-agent` 항목을 제거하고 `SETTINGS_NAV`의 "AI 에이전트 플랫폼"
항목 하나만 유지한다(라벨은 "AI 에이전트"로 통일). `/settings/ai-assistant`("AI 도우미 변경
이력")는 `/ai-agent` 페이지의 "시스템 설정" 섹션에서 이미 링크로 연결되어 있으므로
`SETTINGS_NAV`에서 중복 노출할 필요도 없다(선택적 정리).

## 2. 지식베이스 관리 파편화 — 확인됨, 4개 탭(qa/catalog/screen/kb)이 사실상 하나의 개념을
   인위적으로 쪼갠 것

`frontend/app/settings/ai-assistant/docs/page.tsx`:

```tsx
type Tab = "qa" | "catalog" | "screen" | "policy" | "kb" | "upload";
```

현재 사용자가 "AI가 아는 것"을 확인하려면 서로 다른 탭 6개를 오가야 한다.

| 탭        | 라벨              | 실제 데이터 소스                   | 문제                                                                                                           |
| --------- | ----------------- | ---------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| `qa`      | 이용 매뉴얼 Q&A   | ChromaDB(매뉴얼 색인)              | 청크 텍스트만 나열, 어떤 화면/설정에 연결되는지 모름                                                           |
| `catalog` | AI 변경 가능 설정 | `self_service_catalog_config`(DB)  | 위 Q&A와 별개 화면, 서로 연결 안 보임                                                                          |
| `screen`  | 화면 안내         | `screen_graph`(정적/DB)            | 이것도 별개 탭                                                                                                 |
| `kb`      | 지식베이스 현황   | `knowledge_base_inventory.py`      | **총 청크 수/도메인별 개수/최근 색인 시각뿐** — 사용자가 지적한 대로 "이게 뭘 도와주는지" 알 수 없는 통계 나열 |
| `upload`  | 지식 업로드       | `knowledge_documents`(업로드 문서) | 업로드 문서별 Tool/API 상세와 hop 경로는 사실 `kb` 탭 하단에 렌더링됨(위치 불일치)                             |

**"지식베이스 현황" 탭의 실제 노출 정보**(`page.tsx` 1698~1830줄)를 그대로 인용하면:
- "총 색인 청크 수", "소스 문서(섹션) 수", "최근 색인 시각"
- 도메인별 청크 수 표
- (업로드 문서가 있을 때만) "이용 매뉴얼 Q&A/AI 변경 가능 설정 후보/쓰기 가능 후보/화면 안내
  노드 수" 카드 4개 + 엔드포인트/메서드/쓰기가능 표

지적하신 대로 **"청크 수", "섹션 수" 같은 값은 사용자가 AI 지식을 관리하는 데 아무 도움이
안 되는 내부 구현 지표**다. "이 벡터가 어떤 Tool/REST-API/설정 항목과 실제로 연결되어
있는지"가 핵심인데, 그 정보(`upload` 탭의 업로드 문서 상세 카드 + hop 경로)는 정작 다른 탭에
있다.

### 개선 방향 (구현 전, 방향 제시)

**핵심 아이디어: "지식 항목(벡터/문서/설정 하나하나)"을 1급 단위로 승격시켜, 탭이 아니라
그 항목의 상세 화면에서 연결된 Tool/API/화면안내/RAG전략/관련 대화이력을 한 번에 보여준다.**

1. **탭 구조를 "출처별 나열"에서 "지식 항목 단위 통합 뷰"로 전환**
   - 현재: qa/catalog/screen/kb/upload가 각각 독립된 데이터셋을 별개 화면에 나열
   - 개선: 하나의 "지식베이스" 화면에서 항목 리스트(문서·설정·화면안내 전부 합친 단일 목록)를
     먼저 보여주고, 항목을 클릭하면 상세 패널에 다음을 한 화면에 표시:
     - 원문(Q&A 또는 API 설명)
     - 연결된 도메인/화면(hop 경로 — 이미 `HopPathTrail`로 사람이 읽을 수 있게 번역되어
       있음, Story 1.46)
     - 연결된 Tool/REST-API(메서드/엔드포인트/쓰기 승인 여부)
     - 이 항목이 최근에 실제 응대에 쓰인 이력(Story 1.46의 "최근 이 항목이 쓰인 대화 보기"
       링크 — 이미 존재하므로 위치만 통합하면 됨)
   - 이미 구현된 조각들(hop 번역, 교차탐색 링크)을 재배치하는 작업이라 **백엔드 신규 개발은
     최소화 가능**, 주로 프론트엔드 정보 구조 개편.

2. **"지식베이스 현황"의 통계 카드는 관리 화면의 부가 정보로 격하**
   - 총 청크 수/섹션 수는 상단에 작은 요약 배지 정도로만 유지하고, 메인 콘텐츠는 위 1번의
     항목 리스트로 교체.

3. **업로드(등록) 흐름과 조회(관리) 흐름의 관계 재정의**
   - `upload` 탭(등록/추가)과 `kb` 탭(조회/현황)이 나뉘어 있는 것 자체는 "쓰기 vs 읽기" 관점
     에서 합리적일 수 있으나, 현재는 등록 직후 결과를 확인하려면 다시 다른 탭으로 이동해야
     한다. 등록 완료 시 방금 만든 항목의 상세 패널로 바로 이동시키는 도입부 연결이 필요하다.

4. **`catalog`/`screen` 탭도 위 통합 리스트에 항목으로 편입**
   - 현재 설정 카탈로그·화면 안내는 "관리자가 직접 조작하는 원본 설정"이라 업로드 문서와
     저장 방식은 다르지만(Epic 2/설계 원칙상 의도적으로 분리 — repo 메모 2026-08-04 FR33
     계획의 NFR8), **사용자 화면에서는 같은 리스트 안에 "설정 항목" 유형으로 섞어서
     보여주는 것**이 사용자 지적("파편화 없이 하나로")에 부합한다. 데이터 계층 통합이 아니라
     프레젠테이션 계층 통합만 하면 되므로 회귀 위험이 낮다.

이 개선은 규모가 있는 프론트엔드 리팩터링이라, 착수 전 BMAD 절차(PRD 신규 FR → architecture
IA 설계 → Story 분할)를 거칠 것을 권장한다(하네스 규칙에 따라 Frontend 개편은 UI 미리보기
승인 후 착수).

## 3. Raw 데이터 노출 — 확인됨, 3곳에서 원시 JSON을 그대로 출력 중

| 위치                                                                                                                         | 코드                                                                                |
| ---------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| [frontend/components/RagSearchDoneDetail.tsx](../../../frontend/components/RagSearchDoneDetail.tsx#L76)                      | `{JSON.stringify(trace, null, 2)}` — RAG 검색 추적 raw JSON을 `<pre>`로 그대로 출력 |
| [frontend/app/dashboard/page.tsx](../../../frontend/app/dashboard/page.tsx#L954)                                             | `<pre>...{forJson 필드를 JSON.stringify}...</pre>` — 통화 상세의 부가 필드 raw 출력 |
| [frontend/components/call-history/CallHistoryPanel.tsx](../../../frontend/components/call-history/CallHistoryPanel.tsx#L670) | 위와 동일 패턴(통화이력 패널)                                                       |

세 곳 모두 "혹시 필요할 수도 있는 내부 필드"를 개발 디버깅 화면처럼 그대로 얹어놓은 형태다.
`RagSearchDoneDetail.tsx`는 RAG 검색 추적(쿼리·매칭 문서·점수 등)을 이미 위쪽(58줄)에서
사람이 읽을 수 있는 형태로 일부 렌더링해두고, 그 아래에 **또다시 동일 데이터를 raw JSON으로
중복 노출**하고 있어 특히 개선 효과가 크다.

### 개선 방향
- 세 곳 모두 raw JSON 블록을 제거하고, 그 안에 있는 필드들을 의미 있는 라벨의 카드/표로
  변환한다(이미 `RagSearchDoneDetail.tsx` 상단에 그 패턴이 존재하므로 확장만 하면 됨).
- 정말 raw 데이터가 필요한 사용자(개발자/QA)를 위해서는 "고급 정보 보기" 토글 뒤에 숨기는
  타협안도 가능하나, 기본 노출은 금지.
- 구체적으로 어떤 필드를 카드화할지는 **실제 업로드하신 테스트 데이터로 화면을 재현한 뒤**
  함께 확정하는 것이 정확하다(아래 4번 참고).

  "이용 매뉴얼 Q&A" 탭에 색인되는 흐름과 지식베이스 현황 통계 반영을 확인할 수 있다.

업로드 후 화면에서 어떤 정보가 더 필요한지/불필요한지 알려주시면 위 2·3번 개선 설계에
구체적으로 반영하겠다.

## 5. 추가 점검 — "분명 개선했는데 화면엔 안 보인다"는 감각이 든 이유

사용자가 "1번 문제(구 링크 미삭제)와 같은 패턴이 또 있을 것 같다"고 지적해 전체 네비게이션·
라우트를 재점검했다. **결론: 실제로 같은 패턴이 최소 2건 더 있다.** 원인은 전부 동일하다 —
"신규 기능을 새 경로에 만들고, 구 경로/구 메뉴를 지우거나 명확히 통합하지 않고 그대로
공존시킨 것". 즉 지금 보시는 화면이 "버그로 개선이 안 된 것"이 아니라 **"개선판을 새로
만들어 놓고 구판을 정리 안 해서, 사용자가 둘 중 뭐가 최신인지 구분 못 하는 상태"**다.

### 5-1. "지식베이스"라는 이름이 서로 다른 두 기능에 중복 부여됨

`MAIN_NAV`(`AppHeader.tsx` 11행)의 `/knowledge`("지식베이스")와, `/ai-agent` 안의 "지식베이스"
섹션은 **완전히 다른 시스템**이다.

| 구분      | `/knowledge` (레거시)                                                                                 | `/ai-agent` 지식베이스 섹션 (Story 1.26~)                                                    |
| --------- | ----------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| 저장 대상 | `KNOWLEDGE_CATEGORIES`(persona/greeting/chitchat/complaint 등) — **실시간 통화 응대용 핵심 RAG 지식** | `knowledge_documents`(테넌트가 업로드한 매뉴얼/OpenAPI 문서) — **셀프서비스 AI 도우미 전용** |
| 용도      | 전화 걸려왔을 때 AI가 실제로 참고하는 페르소나·인사말·잡담 등                                         | 사용자가 스스로 설정을 바꾸거나 질문할 때 참고하는 매뉴얼/API 지식                           |
| 결론      | **둘 다 실제로 존재하고 둘 다 필요한 기능** — 삭제 대상 아님                                          | 삭제 대상 아님                                                                               |

즉 1번 항목(`/ai-agent` 메뉴 중복)과 달리 이건 **같은 라우트의 중복이 아니라 "같은 이름표를
서로 다른 물건에 붙인 것"**이라 더 헷갈린다. 사용자가 "지식베이스 관리했는데 왜 그 화면이
아니지?"라고 느낄 수 있는 지점이다.

**권고**: `MAIN_NAV`의 `/knowledge` 라벨을 "지식베이스"에서 "AI 응대 지식(페르소나·인사말)"
등으로 명확히 구분하거나, `/ai-agent` 쪽 라벨을 "지식베이스"가 아니라 "AI 도우미 지식베이스"
처럼 소유 주체를 명시하는 이름으로 바꿀 것. 두 기능을 통합하는 것은 데이터 성격이 근본적으로
달라(실시간 통화 RAG vs 셀프서비스 매뉴얼) 과설계이므로 **이름 분리만 권장**.

### 5-2. "지식 업로드" 진입점이 실제로 3곳 존재(레거시 1 + 신규 2)

| 경로                                                                                  | 기능                                                                                                         | 상태                                                                  |
| ------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------- |
| `frontend/app/knowledge/upload/page.tsx`                                              | TXT 파일 업로드 → LLM으로 FAQ 자동 추출 → `/knowledge` 항목으로 저장(레거시, owner 기본값 하드코딩 `'1004'`) | 코드상 살아있음, `/knowledge` 페이지 내부 버튼에서 여전히 연결 중     |
| `frontend/app/knowledge/add/page.tsx`                                                 | `/knowledge` 항목 수동 추가 폼                                                                               | 레거시 지식베이스 전용, 정상                                          |
| `/ai-agent` → 지식베이스 → "지식 업로드" 탭(`settings/ai-assistant/docs` `upload` 탭) | OpenAPI/마크다운/PDF 문서 업로드(Story 1.26/1.30/1.41)                                                       | 신규, 이번 리뷰에서 테스트 데이터로 검증 대상으로 안내한 바로 그 기능 |

> **정정(2026-08-06 후속 확인)**: 최초 작성 시 "`dashboard/page.tsx`가 레거시 업로드로
> 안내한다"고 썼던 것은 **잘못된 인용**이었다. 이 워크스페이스에는 `frontend/`(루트, 서비스
> 안 됨)와 `sip-pbx/frontend/`(`start-all.ps1`이 실제로 기동하는 경로) **동일 이름의 폴더가
> 두 개** 있는데, grep 결과의 경로가 앞의 미사용 사본이었다. 실제 서비스되는
> `sip-pbx/frontend/app/dashboard/page.tsx`에는 지식 업로드 바로가기 자체가 없다 — 이 항목은
> 대시보드 링크 문제가 아니라 **"레거시 `/knowledge/upload`와 신규 `/ai-agent` 업로드 두
> 진입점이 서로 링크 없이 병존한다"**는 점만 유효하다.

**권고**: `/knowledge` 페이지의 업로드 버튼 옆에 신규 `/ai-agent` 지식 업로드로의 안내 링크를
추가하거나, 두 업로드가 서로 다른 용도(레거시=통화 응대 FAQ 자동추출, 신규=셀프서비스 매뉴얼/
API)임을 라벨로 명확히 구분한다("빠른 FAQ 추출(TXT, 통화 응대용)" vs "지식 문서 업로드
(OpenAPI/매뉴얼, AI 도우미용)").


### 5-3. 점검했지만 "실제로는 문제 없음"으로 확인된 항목

- **시뮬레이터 잔재**: Story 1.39가 실제로 UI에서 `simulate` 탭/상태/타입을 전부 제거했음을
  코드로 재확인(주석만 남고 관련 JSX/상태 완전히 삭제됨) — "폐지했다던 시뮬레이터가 아직
  보인다"는 걱정은 기우였다.
- **`SETTINGS_NAV`의 "AI 도우미 변경 이력"**(`/settings/ai-assistant`): `/ai-agent` 페이지의
  "시스템 설정" 섹션에서도 같은 경로로 링크하고 있어 1번과 유사한 중복처럼 보이지만, 이건
  "최상위 메뉴 vs 설정 하위 메뉴" 중복이 아니라 "설정 하위 메뉴 vs 그 안의 상세 페이지 링크"
  관계라 중복이라기보다는 정상적인 계층 구조에 가깝다 — 다만 `SETTINGS_NAV`에 직접 노출할
  필요는 없으므로(1번 권고에 포함) 정리하면 자연히 함께 해소된다.

### 종합 결론

문의하신 "현재 버전이 오류인지, 추가 개선이 필요한 건지"에 대한 답: **오류(회귀)는 아니고,
각 Story가 끝날 때마다 "새 기능 추가"까지만 하고 "구 진입점 정리"를 후속 작업으로 미뤄온 것이
누적된 결과**다. 코드 자체(백엔드 로직, Story별 AC)는 설계대로 정확히 동작하고 있으나, **이런
정리성 작업을 별도 Story로 명시적으로 잡지 않으면 계속 반복될 패턴**이므로, Epic 4 후속으로
"레거시 진입점 정리" 전용 Story를 하나 두는 것을 권장한다(1번/5-2번 항목을 함께 처리).
