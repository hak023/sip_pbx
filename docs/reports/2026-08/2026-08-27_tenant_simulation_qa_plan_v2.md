## 1. 요청 배경

사용자 지시 3가지:

1. 실제 통화가 필요한 작업(Epic 3/4/5/7 계열)은 현재 시험이 어려우므로 **연기**.
2. **셀프서비스 쪽 구현/검증**이 필요하다.
3. **실제 테넌트 예제로 QA 문서 작성**(실 테스트는 나중, 계획부터). 문서의 필수 조건:
   - 계획한 테넌트를 **실제로 시뮬레이팅할 수 있어야** 한다(API 문서는 더미로 준비).
   - **사람이 보기 좋게 가독성 있게** — 어떤 케이스이고, 어떻게 시뮬레이팅했으며, 시스템이 어떻게
     반응했는지, 무엇이 정상인지, 실제 수행 기록까지 남아 **문서만 보고 시험 경위를 알 수 있어야** 한다.

추가 확인 사항(질의 응답):
- 대상: **1002 카페 오더 테넌트 1개에 집중**(더미 매뉴얼 + OpenAPI + 시뮬레이터 신규 제작),
  이후 기존 1001 시험 항목과 비교해 부족한 부분 개선.
- 기존 v1.0 계획서는 **신규 문서로 대체**(1001만 다루고, 표현이 너무 간략함).

## 3. 시뮬레이터 설계 (테넌트 1002)

SIP PBX와 완전히 무관한 "원격지의 낯선 시스템"을 재현한다. 1001 의류 시뮬레이터(port 8090)와
동시 기동해 **테넌트 격리 검증**도 가능하도록 포트를 분리했다.

```
GET    /menu                     메뉴 목록(카테고리·품절 필터)
GET    /menu/{menu_id}           메뉴 단건
PATCH  /menu/{menu_id}/status    품절 처리/해제          ← 쓰기(승인 대상)
GET    /orders                   주문 목록(상태 필터)
GET    /orders/{order_id}        주문 단건
PATCH  /orders/{order_id}/status 주문 상태 변경          ← 쓰기(승인 대상)
GET    /inventory                원부자재 재고(부족 필터, 기준 3 이하)
GET    /inventory/{item_id}      재고 단건
PATCH  /inventory/{item_id}      재고 수량 변경          ← 쓰기(승인 대상)
GET    /stats/sales              매출 통계
GET    /store/settings           매장 운영설정 조회
PATCH  /store/settings           매장 운영설정 변경      ← 쓰기(의도적 미승인)
POST   /_qa/reset                QA 전용 시드 복원
GET    /health                   헬스체크
```

### 설계 의도 3가지

1. **`POST /_qa/reset`** — 1001 시뮬레이터에는 없던 기능. 케이스마다 초기 상태를 보장해
   판정이 흔들리지 않게 한다(쓰기 케이스를 반복 실행해도 기대값이 고정됨).
2. **`PATCH /store/settings`를 의도적으로 미승인 대상으로 남김** — "승인하지 않은 쓰기는 Tool
   목록에 생성조차 되지 않는다"(NFR9 화이트리스트)를 검증하는 전용 케이스(CAFE-REG-04)를 위해서다.
3. **재고↔메뉴 연결(`linked_menu_ids`)** — 매뉴얼의 N-hop 시나리오(재료 0 → 메뉴 품절 처리)가
   데이터 레벨에서도 성립하도록 구성.

### 검증 실적

- `app.openapi()` 직접 호출로 12개 경로 생성 및 `servers[0].url = http://127.0.0.1:8091` 확인.
- 매뉴얼 픽스처를 실제 파서(`manual_indexer.parse_manual_qa_with_meta`)로 파싱해
  **Q&A 18건 / 도메인 태그 9종이 정확히 추출**됨을 확인(intro, menu-management, order-management,
  inventory-management, sales-stats, store-settings, api-integration, multi-hop-menu-inventory,
  multi-hop-stats-inventory).

## 4. QA 문서 구조 — 가독성/기록성 요구사항 반영 방식

사용자가 요구한 "문서만 보고 시험 경위를 알 수 있어야 한다"를 만족시키기 위해 모든 케이스를
**동일한 카드 구조**로 통일했다.

```
▶ CASE ID · 한 줄 제목
  ├─ 목적            이 케이스가 무엇을 검증하는가
  ├─ 전제            실행 직전 시스템/데이터 상태(시드 값 명시)
  ├─ 시뮬레이션 방법  턴 단위 입력 발화 원문(그대로 복사해 사용)
  ├─ 기대 흐름        유형 판정 → 검색/Tool → 응답 경로(주요 케이스는 mermaid)
  ├─ 정상 판정 기준   체크박스. 전부 충족해야 PASS (가점 항목은 별도 표기)
  └─ 실행 기록        ← 시험 수행자가 채움
       실행 일시 / 실제 응답 원문 / tool_trace / 근거 로그 /
       시뮬레이터 상태 변화(전·후) / 판정(PASS·FAIL·BLOCKED·N/A) / 특이사항
```

부가 장치:

- **§0.4 근거 수집 3중 구조**(응답 원문 + 시뮬레이터 실제 상태 + 서버 구조화 로그)를 도식화해,
  "응답 화면만 보고 판정"하는 것을 구조적으로 막았다.
- **§2.1 시드 데이터 정답값 표** — 메뉴 5건/주문 4건/재고 4건/매장설정 전체 값과 매출 계산식
  (33,800원)까지 명시해 판정 기준을 객관화.
- **§3 시스템 동작 이해** — 유형 A~I 판정 흐름과 공통 응답 규칙(API 경로 미노출, 예외 원문
  미노출, 지어내기 금지)을 먼저 제시.
- **§7 진행 현황판 / 실행 환경 기록 / 총평** — 실행 결과가 문서 안에서 집계되도록 구성.
- 다이어그램 9개(mermaid), 판정 기록란 35개 + 치환 실행 표 17행 = **총 52건 기록 가능**.
