## 문제 요약

`knowledge_graph.py::traverse()`는 `manual_qa→catalog_domain→frontend_screen`,
`catalog_domain→writable→intent_type`라는 고정 2단 체인만 처리했다. 신규 지식 유형(업로드
문서, API 엔드포인트, 절차 단계)이 늘어날 때마다 순회 로직 자체를 다시 작성해야 하는 구조였다.

## 수행 내용

1. **노드/엣지 타입 레지스트리 도입**(`NodeTypeSpec`/`EdgeTypeSpec` dataclass + `_register()`
   패턴, `settings_catalog.py`/`intellidecision_policy.py`와 동일 컨벤션). 노드 7종(기존 4종 +
   신규 `document`/`api_endpoint`/`procedure_step`), 엣지 5종(기존 2종 `rendered_by`/`writable` +
   신규 `relates_to`/`depends_on`/`documents`) 등록.
2. **범용 `traverse_graph(start_type, start_id, *, max_hops, owner)`** 구현 — 등록된
   `(source_type, edge_type)` 인덱스를 hop마다 실제로 순회하는 BFS 엔진. 개별 리졸버 실패는
   해당 엣지만 건너뛴다(best-effort, 기존 원칙 유지).
3. **기존 공개 API 무변경 보장(AC5)**: `traverse(domain, *, max_hops=2)`/`format_decision_hint(domain)`을
   `traverse_graph()` 위의 얇은 래퍼로 재작성 — 반환 값의 형태·내용은 Story 1.18과 동일. 직접
   비교 단위테스트(`TestTraverseBackwardCompatibility`)로 검증.
4. **`document` 노드 실제 연결(Task 5)**: `relates_to` 엣지(catalog_domain→document)가
   `knowledge_documents_db.list_documents(owner, domain_tag)`(Story 1.26)를 재사용해 실제
   업로드 문서를 그래프에 연결한다. owner 없이는 빈 목록을 반환해 테넌트 격리를 보장한다(NFR2).
   `api_endpoint`/`procedure_step`과 `depends_on`/`documents` 엣지는 실제 데이터 소스가 아직
   없어 no-op 리졸버로 예약만 해두었다(AC1/AC2, 후속 Story에서 실제 데이터 연결 예정).
5. **`rag_strategy_hint="graph_local"`**(GraphRAG Local Search 개념 차용, §3.11) 추가 후 유형
   A에 적용. 기존 단위테스트 2건을 새 값에 맞게 갱신.

## 검증 결과

- 신규 단위테스트 22건(`test_knowledge_graph.py`) 전체 통과 — 노드/엣지 레지스트리(AC1/AC2),
  범용 순회(AC3), 리팩터링 전후 직접 비교(AC5, chat-relay/contacts 도메인), document 노드
  연결(Task 5) 검증 포함.
- 기존 self_service/knowledge 관련 회귀 전체 재실행 — 258건 전체 통과(0 FAILED).
- `intellidecision_policy.py` 변경에 따른 기존 단위테스트 2건을 새 기대값(`graph_local`)으로
  갱신, 회귀 없음 확인.

## Non-Goal 확인

Full GraphRAG 수준의 자동 엔터티 추출·Leiden 클러스터링은 이번 Story 범위에 포함하지 않았다
(AC6) — 명시적 스키마 기반의 소규모 파이썬 dict 그래프 구조를 그대로 유지했다.

  노드로 승격, 절차 단계 데이터 모델 설계)은 후속 Story 범위.
- Story 1.29(Contextual Retrieval 스파이크) 착수 가능.
