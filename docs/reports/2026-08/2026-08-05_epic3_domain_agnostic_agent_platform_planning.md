# Epic 3(FR34) 계획 리포트 — 도메인 비종속 AI 에이전트 플랫폼 전환

**작성일**: 2026-08-05
**작성자**: Copilot (BMAD PM/Architect 역할)
**상태**: 계획 수립 완료(코드 변경 없음) — PRD/architecture/Story 문서 증분 반영 완료

## 1. 요청 요약

사용자가 [MCP_VS_CLIENT_CENTRIC_UNIVERSAL_AGENT_MARKET_RESEARCH.md](../../design/MCP_VS_CLIENT_CENTRIC_UNIVERSAL_AGENT_MARKET_RESEARCH.md)
리서치 결과를 바탕으로, 리서치했던 타 시스템(GPT Actions/mcp-link 등)처럼 **API 도메인에 의존적
이지 않고, 테넌트별 데이터만 업로드하면 지식베이스가 즉시 반영/구성되어 사용 가능한** 방향으로
개발 방향을 재편해달라고 요청했다. 구체적으로 4가지 재편 요구사항과 4가지 핵심 설계 포인트를
제시했다.

**재편 요구사항**:
1. 실제 API 실행(현재 Non-Goal)을 업로드된 데이터대로 실행되도록 지원.
2. `settings/ai-assistant` 하위 위치가 적절한지 Frontend IA(정보 구조) 재검토, 하위 메뉴 재편.
3. UI/UX에 유저 친화적 지식베이스 노출 디자인 보강.
4. (3번과 연계) 유저 친화적 AI 투명성 경험 강화.

**핵심 설계 포인트**:
1. 데이터 업로드만으로 임의 REST API 시스템에 말/채팅 AI 도우미를 즉시 적용.
2. 지식베이스 구성이 웹사이트에서 투명하게 조회 가능 — Tool(API)은 하나마다 상세 정보 + 관련
   hop 정보까지 확인 가능해야 함.
3. IntelliDecision 스마트 응대 + 응대 과정 투명성(유형별 응대 순서도, RAG vector 검색·hop 활용,
   화면안내 hop 활용을 유저 친화적으로 시각화).
4. 기존 응답 시뮬레이터 기능을 고도화·통합하거나, 3번이 충분히 해소되면 시뮬레이터 자체를
   불필요하게 만들지 재검토.

## 2. 현황 진단(코드/문서 직접 확인)

- Story 1.26/1.31이 이미 "업로드만으로 지식베이스 자동 구성"의 핵심(매뉴얼 Q&A/설정 항목 후보/
  화면 안내 노드 자동 생성)을 구현해뒀음을 확인 — 리서치에서 발견한 시장 표준 패턴(GPT Actions,
  mcp-link 등)과 본질적으로 동일한 접근을 이미 채택하고 있었다.
- 유일하게 빠진 조각은 **실제 API 실행**(Story 1.31에서 명시적 Non-Goal로 지연)이며, 이것이
  리서치 비교표에서 우리 시스템과 RestGPT/GPT Actions/mcp-link의 유일한 차이점이었다 —
  요청 1번과 정확히 일치.
- Frontend는 `settings/ai-assistant/docs` 페이지 하나에 7개 탭이 몰려 있음을 코드로 재확인 —
  Epic 1 초기 설계("테넌트 관리자가 자기 설정을 보는 화면")의 잔재이며, "AI 에이전트 플랫폼"
  정체성과 어긋남 — 요청 2번의 문제의식이 타당함을 확인.
- IntelliDecision 투명성은 Story 1.18/1.32로 이미 상당 부분 구현됐으나(정책 표/그래프, hop_path),
  "유형별 응대 순서도(flowchart)" 형태는 아직 없음 — 요청 3-1의 공백을 확인.

### FR34 하위 요구사항 매핑

- **FR34-A(실제 API 실행 지원)**: Story 1.34(안전 설계 스파이크 — 화이트리스트 승인+undo)에서
  선행 설계 후, Story 1.35(실제 실행 연결)에서 구현. Epic 2의 "함수명 화이트리스트" 원칙과
  Story 1.17 Undo 패턴, 리서치 GoEx의 "undo/damage confinement" 철학을 그대로 계승한다.
- **FR34-B(Frontend IA 재편)**: Story 1.36. "설정 > AI 도우미"에서 독립 "AI 에이전트" 최상위
  메뉴로 승격, 하위를 지식베이스/응대 투명성/시스템 설정 3개 섹션으로 재편.
- **FR34-C(지식베이스 투명성 UI 고도화)**: Story 1.37. API/Tool 단위 상세 카드 + hop 뷰.
- **FR34-D(IntelliDecision 응대 투명성)**: Story 1.38. 유형별 응대 순서도(flowchart) UI, RAG
  hop 활용과 화면안내 hop 활용을 구분 시각화.
- **FR34-E(시뮬레이터 통합/재검토)**: Story 1.39. Story 1.38 순서도가 실시간 대화에서도 노출
  가능한지 스파이크 검증 후, 통합 또는 시뮬레이터 내 임베드 여부를 결정 지원 리포트로 문서화.

## 4. 실행 순서 권고

1. **Story 1.34 → 1.35**(실제 API 실행) — 리서치 격차 해소, 플랫폼의 핵심 차별화 포인트.
2. **Story 1.36**(Frontend IA 재편) — 이후 Story(1.37/1.38/1.39)가 배치될 새 IA를 먼저 확정해야
   순서상 합리적(1.37~1.39가 1.36의 신규 섹션 안에 들어감).
3. **Story 1.37 → 1.38**(지식베이스 투명성 → 응대 순서도) — 사용자가 명시한 우선순위(핵심 설계
   포인트 2→3 순서)를 따른다.
4. **Story 1.39**(시뮬레이터 통합/재검토) — 1.38 완료 후에만 의미 있는 판단이 가능하므로 마지막.

## 5. Non-Goal(명시적 범위 제외)

- 음성(실시간) 세션에서의 실시간 투명성 패널 노출(Story 4.2의 TTS 조기 송출·barge-in 상호작용
  리스크 미검증 상태 — Story 1.39도 채팅 세션 한정으로 범위를 좁힘).
- Full MCP 서버 자체 구현, 타 시스템의 자동 발견(discovery) — 업로드 기반 명시적 등록이 우선.
- 임의 외부 API에 대한 "제외 목록" 방식(Epic 2와 동일 방식)이 아닌 "화이트리스트 방식" 채택 —
  신뢰도가 검증되지 않은 외부 시스템이므로 기본 거부·명시적 승인이 더 안전.

## 7. 추가 요청 반영(2026-08-05, 동일 계획 증분 내 수정)

사용자가 계획 확정 직후 3가지 요청사항을 추가로 제시했다:

1. "AI 의사결정 로직" 탭은 시뮬레이션 방식이 아니라, 유형별 정의 + 지식베이스 기반 실제 사례
   설명으로 전환할 것(실시간 LLM 호출 없이 KB 데이터만으로 설명).
2. 응답 시뮬레이터는 재검토 대상이 아니라 **삭제 확정** — 대신 평소 숨겨진 SIP MESSAGE 패널인
   `GlobalSmsDock`을 상시 노출해, 테넌트 관리자가 자기 자신에게 실제 메시지를 보내 실제 AI
   응답을 받는 방식으로 시뮬레이션을 대체할 것.
3. "최근 판단 이력"(기존 Story 1.21/1.22)이 현재 거의 쓸모없는 수준이므로, 실제 대화 이력만
   사용해 유형별 응대 과정을 순서도(flowchart)로 시각화하도록 고도화할 것 — 시뮬레이션은 절대
   사용하지 않음.
