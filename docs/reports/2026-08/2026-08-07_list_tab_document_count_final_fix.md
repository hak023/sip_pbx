# 8번째 재발 최종 수정 — "도우미 지식베이스" 문서 카운트가 업로드/삭제 후 갱신 안 되던 진짜 원인

- 작성일: 2026-08-07
- 버전: v1.0
- 관련 문서: [2026-08-07_upload_inventory_refresh_missing_fix.md](2026-08-07_upload_inventory_refresh_missing_fix.md)

## 1. 사용자 피드백

"똑같아" — 지난 수정(kbInventory 갱신 추가) 이후에도 "도우미 지식베이스"(`list` 탭)에서
문서 수가 업로드/삭제와 무관하게 그대로였다. 8번째 같은 이슈 핑퐁이라는 강한 지적과 함께
"직접 웹페이지로 시험"을 명시적으로 요구.

## 2. 계획(실행 전 정리)

1. 지난 수정은 `kbInventory`(지식베이스 현황 탭 카드)만 갱신했을 뿐, "도우미 지식베이스"
   (`list` 탭)의 "문서 N건" 카운트가 실제로 어떤 상태(`items`)에서 오는지 재확인한다.
2. `items`를 갱신하는 `loadQa()`가 업로드/개별 삭제 핸들러에서 호출되는지 코드로 직접 확인한다.
3. 코드로 원인을 특정한 뒤, 반드시 **실제 브라우저에서 업로드→"도우미 지식베이스" 탭 확인→
   삭제→"도우미 지식베이스" 탭 확인**까지 전 과정을 클릭으로 재현해 고쳐졌는지 검증한다
   (curl만으로 끝내지 않는다 — 지난 7번의 실패가 이 원칙을 어겨서 반복됐다).

## 3. 근본 원인(코드로 확정)

"도우미 지식베이스" 탭의 "문서 N건" 배지는 `items.length`(즉 `loadQa()`가 채우는 `items`
상태)에서 온다. 그런데:

- `items`는 `qaLoadedOwnerRef`라는 ref로 **owner당 최초 1회만** 로드되도록 가드되어 있다
  (2026-08-07 앞선 세션에서 반복 재조회 버그를 고치며 도입한 가드).
- `handleUploadDocument()`(업로드)와 `handleDeleteDocument()`(개별 삭제)는 성공 후
  `loadKbDocuments()`/`loadKbInventory()`만 호출했을 뿐 **`loadQa()`를 전혀 호출하지
  않았다.** 이 두 액션은 owner를 바꾸지 않으므로 `qaLoadedOwnerRef` 가드가 항상 재조회를
  막았고, "도우미 지식베이스" 탭으로 돌아가도 `items`는 페이지 최초 로드 시점의 오래된 값
  그대로였다.

즉 지난 수정(`kbInventory` 추가)은 정확했지만 **범위가 절반뿐이었다** — 같은 액션이 갱신해야
할 상태가 `kbInventory` 하나가 아니라 `kbInventory`+`items` 두 개였는데 하나만 고쳤다.

## 4. 수정

`frontend/app/settings/ai-assistant/docs/page.tsx`:

- `handleUploadDocument()`: 성공 시 `loadKbDocuments()`/`loadKbInventory()`에 이어
  **`loadQa(false)`도 호출**하도록 추가(부작용 없는 조회, `auto_index=false`).
- `handleDeleteDocument()`: 개별 삭제 성공 시에도 동일하게 `loadQa(false)` 추가.
- (`handleResetKnowledgeBase()`은 이미 `loadQa(false)`를 호출하고 있어 수정 불필요 —
  전체 삭제는 애초에 정상 동작했었다.)

## 5. 실제 브라우저로 전 과정 재검증(요청대로 직접 시험)

1. curl로 owner=1001 클린 상태 확인(`deleted_chunks: 0`).
2. Playwright로 실제 페이지 새로고침(수정된 프론트 반영) → "도우미 지식베이스" 탭 →
   **"문서 0건" 확인**.
3. "지식 업로드" 탭에서 실제 제목/본문 입력 후 **"업로드" 버튼 클릭** → 성공.
4. **"도우미 지식베이스" 탭으로 클릭 이동** → **"문서 1건"**과 방금 업로드한 내용이
   "(도메인 미지정)" 그룹으로 정상 노출됨을 확인.
5. "지식 업로드" 탭으로 돌아가 방금 올린 문서의 **"삭제" 링크 클릭** → 목록에서 사라짐
   확인.
6. **"도우미 지식베이스" 탭으로 다시 클릭 이동** → **"문서 0건"**으로 즉시 복귀함을 확인.

전 과정을 실제 클릭으로 3회 왕복(업로드 확인 → 삭제 확인)하며 매번 화면이 정확히 반영됨을
실물로 확인했다.

## 7. 교훈 — 왜 8번이나 반복됐는가

- 이 페이지는 같은 "지식베이스 데이터"를 **3개의 서로 다른 React 상태**(`items`/`kbInventory`/
  `kbDocuments`)로 중복 보유하고, 각 상태는 서로 다른 화면(list/kb/upload 탭)에서 쓰인다.
  업로드/삭제 같은 하나의 액션이 성공하면 이 3개 상태를 **전부** 무효화해야 하는데, 매번 "이번에
  문제가 된 상태 하나만" 고치고 다음 라운드에서 "또 다른 상태 하나"가 발견되는 패턴이 반복됐다
  (이번까지 포함해 최소 3개 상태 각각에서 한 번씩 이 문제가 났다).
- **재발 방지책(다음에 유사한 "데이터 갱신 안 됨" 이슈가 나오면 즉시 적용)**: 업로드/삭제/
  전체삭제 3개 핸들러가 공통으로 `void Promise.all([loadQa(false), loadKbInventory(),
  loadKbDocuments()])` 같은 **단일 헬퍼**를 호출하도록 리팩터링하는 것을 강력 권장한다 —
  지금처럼 각 핸들러에 개별적으로 호출을 추가하는 방식은 "네 번째 상태"가 생기면 또 놓칠 수
  있다. 이번엔 시간 압박상 개별 추가로 마무리했으나, 다음에 이 페이지를 다시 만지게 되면 이
  리팩터링을 최우선으로 적용할 것.
- **가장 중요한 교훈**: 사용자가 "8번째 같은 이슈"라고 지적했을 때, 매번 "코드를 고쳤으니
  됐다"고 응답하지 않고 **이번처럼 실제 브라우저에서 업로드→확인→삭제→확인의 전체 사이클을
  클릭으로 재현**해야 진짜로 끝났는지 확신할 수 있다. curl 검증이나 부분 재현으로 끝내면
  놓친 상태가 있어도 알 수 없다.
