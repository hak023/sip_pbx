## 3. 발견하고 수정한 근본 원인 5건

1차 라운드에서 쓰기 케이스가 12건 중 11건 실패했다. 재시도 횟수를 늘리는 식의 완화가 아니라
**실제로 원격 API에 무엇을 보내고 있는지**를 직접 확인해 원인을 특정했다.

### ① OpenAPI `$ref`가 해석되지 않아 Tool이 본문 스키마를 몰랐다

- **증상**: `{"detail":[{"type":"missing","loc":["body","stock_qty"]}]}` 422가 연속 발생.
  LLM이 `{"quantity": -5}`처럼 **필드명을 지어냈다**.
- **원인**: `OpenApiSpecAdapter`가 `requestBody`를 `{"$ref": "#/components/schemas/InventoryUpdate"}`
  그대로 저장했고, `_build_dynamic_tool_doc()`은 경로/쿼리 파라미터만 문서화하고 **request body를
  아예 설명하지 않았다**. LLM 입장에서 "body(요청 본문 dict)"라는 안내만 있고 어떤 필드가
  필요한지 알 방법이 없었다.
- **수정**: `_resolve_refs()`로 `$ref`를 실제 정의로 치환(순환 참조 8단계 방어) +
  `_describe_request_body()`로 필드명·타입·필수여부·**허용값(enum)** 을 Tool 설명에 명시.
- **효과**: 주문 상태 Tool 설명에 `status (string, 필수): 변경할 주문 상태: 결제완료 | 제조중 |
  픽업대기 | 픽업완료 | 취소`가 노출되어, 1차의 `PREPARING`(영문 변환)·`픽업 대기`(공백 삽입)
  오류가 사라졌다.

### ② 식별자 확보 지침이 없어 사용자에게 내부 ID를 되물었다

- **증상**: "딸기라떼 품절 해제해줘" → *"딸기라떼 메뉴의 ID를 알려주시면 처리해 드릴게요"*
- **원인**: 목록 조회로 ID를 찾으라는 지침이 프롬프트에 없었다. 관리자도 내부 ID를 모르는 것이
  정상이므로 이 되묻기는 사실상 기능 불능이다.
- **수정**: `prompt_rules.py`에 동적 API 실행 규칙 5개(a~e) 신설 — 식별자는 되묻지 말고 GET
  목록 조회로 확보 / body 필드명·값을 지어내지 말 것 / Tool 이름 전체를 쓸 것 / 다건은 조회
  후 건수 확인 / 미승인 동작을 다른 Tool로 대체하지 말 것.

### ③ 스냅샷 경로가 틀려 Undo가 구조적으로 불가능했다

- **증상**: 시뮬레이터 접근 로그에 `GET /orders/ORD-2001/status → 405 Method Not Allowed`.
- **원인**: 쓰기 전 `pre_state` 스냅샷을 **쓰기 경로 그대로** GET했다. `/orders/{id}/status`처럼
  하위 액션 경로는 GET이 없어 항상 실패하고, `pre_state`가 null로 저장되어 되돌릴 근거 자체가
  사라졌다. **응답 텍스트만 봐서는 절대 드러나지 않는 결함**으로, 시뮬레이터 접근 로그를
  대조해서야 발견했다.
- **수정**: `_resource_path_candidates()`로 부모 리소스 경로 폴백(`/orders/{id}/status` →
  `/orders/{id}`) + 스냅샷에 성공한 경로를 `request_json.pre_state_path`에 기록해 Undo가
  **같은 경로로** 역호출하도록 연결.

### ④ 경로 파라미터를 최상위 인자로 보내 플레이스홀더가 치환되지 않았다

- **증상**: `arg_keys: ['body','owner','menu_id']` — GET으로 `M-STL`을 찾아놓고도 404.
- **원인**: Tool 시그니처는 `(owner, params, body)`인데 LLM이 `menu_id`를 `params` 안이 아니라
  최상위로 보냈다. 그 결과 경로의 `{menu_id}`가 치환되지 않은 채 호출됐다.
- **수정**: `_normalize_dynamic_api_args()` — `api_`로 시작하는 Tool 호출 시 알려진 인자
  (owner/params/body) 외의 키를 `params`로 흡수. 추가로 치환되지 않은 플레이스홀더가 남으면
  404를 유발하는 대신 **"목록 조회로 대상을 먼저 찾으라"는 구체적 안내**를 반환하도록 가드.
  (Tool 스키마를 오염시키는 `**kwargs` 방식은 의도적으로 배제 — 단위 테스트로 확인)

### ⑤ Tool 이름의 해시 접두사를 빼먹어 호출이 실패했다

- **증상**: `{"error": "알 수 없는 도구: patch_orders_order_id_status"}` (CAFE-D-01/D-02 전멸)
- **원인**: 동적 Tool 이름이 `api_<문서해시>_<메서드>_<경로>` 형태라 LLM이 앞의 무의미한 해시를
  생략하고 불렀다.
- **수정**: `_execute_self_service_tool()`에 접미사 폴백 — 접미사가 **유일하게** 일치할 때만
  해석하고 `self_service_tool_name_resolved_by_suffix` 로그를 남긴다(모호하면 기존대로 거부).

> **검증**: 신규 단위 테스트 8건 포함 관련 스위트 54건 전부 통과.
> 수정 파일: `document_adapters.py`, `dynamic_api_tool.py`, `prompt_rules.py`,
> `langgraph/nodes/self_service_agent.py`

## 4. 잔여 결함 (후속 Story 필요)

### ① 자연어 → 내부 식별자 매핑이 불안정 — 심각도 **높음**

같은 Tool·같은 프롬프트인데도 성공과 실패가 갈린다.

| 케이스                                 | 결과                                 |
| -------------------------------------- | ------------------------------------ |
| CAFE-F-02 "카라멜마끼아또 품절"        | ✅ GET → `M-CMK` 매핑 → 실행 성공     |
| CAFE-B-02 "딸기라떼 품절 해제"         | ❌ GET은 했으나 매핑 실패 → 404       |
| CLTH-B-02 "크루넥 니트 재고 20개"      | ❌ GET 없이 상품명을 SKU로 사용 → 404 |
| CLTH-E-01 "오버핏 후드 집업 재고 30개" | ❌ 동일                               |

프롬프트 지침(수정 ②)만으로는 LLM이 매번 지키지 않는다. **코드 레벨 해결**이 필요하다 —
예: 경로 파라미터가 스펙상 ID 형식인데 한글/공백이 포함되면 목록 조회로 자동 해석하는
resolver를 실행기에 내장.

### ② 매뉴얼의 업무 규칙을 위반한 실행 — 심각도 **높음**(보안·정합성)

**CLTH-SP-03**: 매뉴얼 §5에 *"취소는 결제완료 또는 배송준비중 단계에서만 가능"* 이라고 명시돼
있는데, **배송중** 상태인 ORD-1003을 확인 절차만 거치고 **실제로 취소**했다
(`배송중 → 취소` 반영 확인). 시뮬레이터 API는 이 제약을 강제하지 않으므로 **매뉴얼 지식만으로
막아야 하는** 케이스인데 실패했다.

RAG는 `api-integration` 도메인만 매칭했고 취소 조건이 적힌 청크를 가져오지 못했다. 즉 실행 직전
관련 업무 규칙을 확인하는 단계가 없다. **쓰기 실행 전 대상 도메인의 제약 조건을 재검색하는
가드**가 필요하다.

### ③ 테넌트 지식이 있는데도 플랫폼 온보딩 응답이 나옴 — 심각도 **중간**

**CAFE-C-03 / CLTH-C-01 / CAFE-F-01 / CLTH-F-01**에서 카페·의류와 무관한 SIP PBX 온보딩
체크리스트가 나왔다.

> "아직 서비스 소개(페르소나)가 등록되지 않았어요… 착신 규칙이 하나도 없어서 전화를 어떻게
> 받을지 규칙을 최소 1개 만들어야…"

모호한 발화("그거 바꿔줘")에서도 *"채팅 자동응답인가요, AI 에스컬레이션인가요?"* 로 되물어
테넌트 도메인을 벗어난다. 테넌트가 자기 지식을 업로드한 경우 플랫폼 기본 온보딩보다 **업로드된
지식을 우선**해야 한다.

### ④ RAG 검색 품질 — 심각도 **중간**

- 매칭 점수가 **0.11대**로 일관되게 낮고, `hits`가 사실상 2로 고정된다.
- 질문과 무관한 도메인이 자주 매칭된다(예: "우유 재고 12로 채워줘" → `multi-hop-stats-inventory`).
- `related_domains`가 비어 있는(`[]`) 경우도 빈번하다.
- **유형 C 하이브리드 검색(`self_service_agent_hybrid_rag_merged`)이 50건 전 케이스에서 단 한 번도
  기록되지 않았다** — Story 1.33의 `looks_like_broad_help_query()` 휴리스틱이 이번 발화들에서
  발동하지 않은 것으로 보이며, 별도 조사가 필요하다.

### ⑤ 응답에 API 경로 노출 — 심각도 **낮음**

**CAFE-C-02**에서 *"원부자재 재고 목록 조회: `GET /inventory`…"* 처럼 원시 API 경로가 그대로
노출됐다(계획서 §3 공통 응답 규칙 위반). 전화·문자 사용자에게는 무의미한 정보다.

### ⑥ 없는 기능을 안내 — 심각도 **낮음**

**CLTH-C-02**에서 *"새로운 상품의 재고 정보를 추가할 수 있습니다"* 라고 답했으나 의류
시뮬레이터에 상품 추가 엔드포인트는 없다.

### ⑦ 유형 I(반복 요청)에서 RAG 재검색 발생 — 심각도 **중간**

**CAFE-I-01**: "다시 말해줘"에 대해 직전 응답을 재사용하지 않고 **턴2에서 RAG 검색이 다시
실행**됐다. 유형 I는 설계상 재검색·재실행이 없어야 하는데(계획서 §3), 실제로는 매 턴 검색이
수행된다. 응답 내용은 유사했으나 불필요한 벡터 검색과 LLM 호출이 발생해 지연·비용에 직접
영향을 준다.

> 이 결함은 **자동 판정을 도입해서야 드러났다**. 응답만 보면 "같은 내용을 다시 말했으니 정상"
> 으로 보이기 때문이다.

### ⑧ 응대 이력 조회 실패는 제품이 아니라 **QA 하네스 결함**이었음 (정정)

초판(v1.0)에서 "유형 판정을 수집하지 못했다"를 제품 결함으로 분류했으나, 재조사 결과
**QA 하네스 오류 3건**이 원인이었다. 제품은 정상 동작 중이었다.

| #   | 잘못 사용한 값                                | 실제                                 |
| --- | --------------------------------------------- | ------------------------------------ |
| 1   | `/api/settings/ai-assistant/decision-log/...` | `/api/self-service/decision-log/...` |
| 2   | `session_key` = converse 응답값(`1002:1002`)  | `voice:{call_id}`                    |
| 3   | 응답 필드 `sessions`                          | `items`                              |

계획서 §0.4의 근거 수집 표에 **경로부터 틀리게 적혀 있었고** 러너가 그대로 따라간 것이다.
올바르게 호출하니 `type_sequence` / `final_type`이 정상 제공되며, `self_service_decision_log`에
1002 기준 103건이 이미 쌓여 있었다. 기록이 남아 있어 **재실행 없이 소급 보강**했다
(`scripts/qa_backfill_intent_types.py`, 85턴 전부 복구).

> **교훈**: "측정하지 못했다"를 제품 결함으로 기록하기 전에 **측정 도구 자체를 먼저 의심**해야
> 한다. 이번에는 QA 문서의 오탈자가 두 라운드에 걸쳐 유형 판정 검증을 통째로 무력화했다.

## 4.5 QA 체계 개선 — 항목별 자동 판정 도입

초판에서는 케이스 단위로만 PASS/FAIL을 기록했고, 계획서의 판정 기준 체크박스 134개는 **전부
미체크 상태**였다. 즉 "이 케이스가 왜 PASS인지"를 추적할 수 없었다. 이를 해결하기 위해 판정
기준을 기계 검증 가능한 규칙으로 옮기고 자동 대조 체계를 만들었다.

| 산출물                                | 역할                                                                     |
| ------------------------------------- | ------------------------------------------------------------------------ |
| `scripts/qa_case_criteria.py`         | 검증식 라이브러리(응답 문구·Tool 호출·시뮬레이터 상태·유형 판정 등 24종) |
| `scripts/qa_case_criteria_cafe.py`    | 1002 30개 케이스의 판정 기준 정의(계획서 문구 그대로 + 검증식)           |
| `scripts/qa_case_meta_cafe.py`        | 케이스별 시험 목적·지식베이스 구성(KB-1~8)·연계 케이스                   |
| `scripts/qa_evaluate.py`              | 실행 결과와 기준을 대조해 PASS/FAIL/**UNMEASURED** 판정                  |
| `scripts/qa_render_plan.py`           | 판정 결과 + 지식베이스 원문 + 대화 기록 → 계획서 본문 자동 생성          |
| `scripts/qa_backfill_intent_types.py` | 과거 실행 결과에 유형 판정 소급 보강                                     |

**판정을 3값으로 구분**한 점이 핵심이다. `UNMEASURED`(측정 불가)를 `FAIL`과 섞지 않아야
제품 결함과 QA 환경 결함이 뒤섞이지 않는다. 이번 라운드는 §4-⑧ 수정으로 측정 불가가 0건이 됐다.

이제 계획서의 각 케이스는 **분류 축 → 시험 목적 → 사용된 지식베이스(원문 포함) → 입력·응답 →
원격 시스템 상태 변화 → 판정 기준별 실제 관측값 → 연계 케이스** 순으로 기록되며, 재실행 시
`qa_render_plan` → `qa_apply_section4`로 문서 전체가 자동 갱신된다.

### 5.1 계획서 설계 오류 정정 — 승인 세분성

계획서 원안의 CAFE-REG-04는 "`PATCH /store/settings`만 미승인"이었으나, 코드 확인 결과
`approved_methods_json`은 **문서당 메서드 목록 하나**이고 `build_dynamic_tools_for_owner()`가
승인된 메서드의 **모든 엔드포인트**를 노출한다. 즉 **엔드포인트별 통제가 불가능**해 원안은
표현할 수 없는 시나리오였다. `DELETE` 미승인 방식으로 재설계해 화이트리스트 자체는 검증했다.

> **실운영 관점의 구조적 한계**: "재고 수정(PATCH)은 허용하되 결제 설정(PATCH)은 금지" 같은
> 통제가 불가능하다. `approved_methods_json`을 `["PATCH /orders/{id}/status", ...]`처럼
> **메서드+경로 쌍**으로 확장하는 후속 Story를 권장한다(하위 호환: 메서드만 있으면 기존처럼 전체 허용).
