## 실측 방법

1. **데이터셋**: owner `9001`의 실제 ChromaDB `self_service_manual` 청크 52건(매뉴얼 Q&A 전량,
   서버 프로세스 기동 없이 `chromadb_client.get_vector_db()`로 직접 조회).
2. **맥락 요약 생성**: 청크 52건 각각에 대해 Gemini(`gemini-2.5-flash`)로 1문장 맥락 요약
   프리픽스를 실제로 생성(Anthropic Contextual Retrieval 프롬프트 패턴 축약판).
3. **검색 품질 벤치마크(self-retrieval)**: 각 청크 자신의 질문(question)을 쿼리로 사용해
   "그 청크 자신이 top-K에 다시 나타나는가"를 hit@1/hit@3으로 측정 — baseline(원문 임베딩) vs
   contextual(맥락 요약+원문 임베딩), 로컬 SentenceTransformer 임베딩(비용 없음).
4. **BM25 비교**: 외부 의존성 추가 없이 순수 파이썬으로 구현한 최소 BM25(k1=1.5, b=0.75)로
   동일 쿼리 세트의 키워드 검색 히트율을 측정.

## 실측 결과

### 비용·지연(AC1)

| 항목             | 값            |
| ---------------- | ------------- |
| LLM 호출 수      | 52회          |
| 총 토큰(추정)    | 68,081 tokens |
| 총 소요 시간     | 362.9초       |
| 청크당 평균 지연 | 6.98초        |

52건(현재 매뉴얼 Q&A 전량) 기준 약 6분이 소요됐다 — 문서가 수백~수천 건 규모로 늘어나면
색인 파이프라인에 상당한 지연이 추가되고, 재색인(문서 수정 시 Story 1.26 `PUT`)마다 이 비용이
반복 발생한다.

### 검색 품질(AC2) — self-retrieval hit@1 / hit@3 (n=52)

| 방식                            | hit@1      | hit@3  |
| ------------------------------- | ---------- | ------ |
| baseline(원문 벡터)             | **94.23%** | 100%   |
| contextual(맥락 요약+원문 벡터) | 86.54%     | 98.08% |
| BM25(키워드)                    | **100%**   | 100%   |

**핵심 발견**: Anthropic이 보고한 "실패율 최대 67% 감소"는 이번 데이터셋에서 **재현되지 않았고,
오히려 contextual 임베딩이 baseline보다 hit@1 기준 7.7%p 더 낮았다**. 원인 분석: 우리 매뉴얼
청크는 이미 "Q: 질문\nA: 답변" 형태로 짧고 자기완결적(self-contained)이라 Anthropic이 해결하려는
문제(긴 문서에서 잘려나온 청크가 문맥을 잃는 문제, §3.1)가 애초에 존재하지 않는다. 오히려 모든
청크 앞에 유사한 문장 구조의 일반적 맥락 요약을 붙이면 청크 간 임베딩이 서로 더 가까워져
(맥락 요약 문장들끼리의 유사도가 실제 청크 내용 차이보다 커짐) 변별력이 떨어진 것으로 판단된다.

BM25는 두 벡터 방식을 모두 앞질러 hit@1/hit@3 100%를 기록했다 — 한국어 질문에 등장하는
구체적 키워드(도메인명·기능명 등)가 청크 원문에도 그대로 등장하는 경우가 많아 키워드 매칭이
매우 효과적이었다.

### AC3(OpenAPI 문서에서 BM25 이점) — 측정 불가, 범위 제한 명시

이번 스파이크는 owner 9001의 `self_service_manual` 청크만 사용했다 — 실측 시점에 Story 1.26
OpenAPI/PDF 업로드 문서가 별도 `doc_type`으로 색인되어 있었으나, 청크 추출·질의 표본 구성까지
포함하면 스파이크 범위가 커져 이번 실측에서는 제외했다. **AC3(OpenAPI 문서에서 BM25 특히
유리한지)는 검증하지 못한 상태로 남는다** — 후속 스파이크 또는 Story 1.26 문서가 충분히
누적된 시점에 별도로 재실측을 권장한다.

## 결론(AC4)

**① Contextual Retrieval → 미채택.** 근거:
- 현재 규모(청크 수십~백여 건, 짧고 자기완결적인 Q&A 위주)에서는 품질 개선 효과가 없고 오히려
  악화됐다(hit@1 -7.7%p).
- 청크당 평균 6.98초의 LLM 호출 비용이 추가되며, 문서가 늘어날수록(Story 1.26 이후 지속 증가
  중) 색인·재색인 지연이 선형으로 증가한다.
- Story 1.25가 예상했던 "우리 규모에서는 효과가 제한적"이라는 판단이 Story 1.26 이후에도
  실측으로 재확인됐다.

**② BM25 하이브리드 검색 → 조건부 채택 권장(후속 Story 검토 대상).** 근거:
- 벡터 검색(baseline) 대비 hit@1이 5.8%p 더 높고(100% vs 94.23%), 추가 LLM 비용이 없다
  (로컬 계산, 임베딩 모델 호출도 불필요).
- 단, 이번 실측은 self-retrieval(자기 자신 찾기)이라는 관대한 벤치마크이므로, 실제 사용자
  발화(패러프레이즈·오타·다른 표현)에 대한 일반화 성능은 별도로 검증해야 한다 — 이번 스파이크
  범위를 벗어나므로, "BM25 하이브리드 검색 스파이크"를 별도 후속 Story로 제안한다.
- AC3(OpenAPI 문서에서의 이점)도 이 후속 스파이크에서 함께 검증할 것을 권장한다.

## Non-Goal 확인

BM25 구현은 스파이크 실측 전용 순수 파이썬 코드(`scripts/spike_contextual_retrieval.py`
`SimpleBM25` 클래스)로만 존재하며 프로덕션 코드에 통합하지 않았다(AC5). Contextual Retrieval도
프로덕션 파이프라인(`manual_indexer.py`/`knowledge_documents.py`)에 어떤 코드도 추가하지 않았다.

## 후속 작업 제안

- 신규 Story(가칭 1.30): BM25 하이브리드 검색(벡터+키워드) 실사용 발화 기준 재검증 + Story 1.26
  OpenAPI/PDF 문서 포함 AC3 실측 + 채택 시 실제 `RAGEngine` 통합 설계.
