# 실서버 직접 검증 — 업로드 문서 RAG 반영 여부 (사용자 "5번 고쳤다는데 계속 재발" 재확인)

- 작성일: 2026-08-07
- 버전: v1.0

## 배경

사용자가 "시험 방법대로 문서 업로드했으나 실제 지식베이스에 반영되지 않는다"고 재보고 —
오늘 같은 계열 문제를 5차례 수정했다고 보고했음에도 계속 재발한다는 지적. 코드 리뷰만으로
"고쳤다"고 결론짓지 않고, 실행 중인 서버에 직접 API 호출로 실증했다.

## 검증 절차 및 결과 (전부 curl로 실제 실행, 추측 없음)

1. **프로세스 상태 확인**: 현재 API 서버(PID 12772)는 2026-08-07 14:45:38에 시작 — 오늘 만든
   모든 수정 파일(`rag.py`/`hybrid_rag.py` 13:21, `settings_ai_assistant.py` 13:59 등)보다
   늦게 시작되어 **최신 코드를 반영한 상태**임을 확인.
2. **신규 테스트 owner(9999test)로 업로드→검색 end-to-end 검증**:
   - `POST /api/knowledge-base/documents`로 마크다운 1건 업로드 → `indexed_chunks=1` 성공.
   - `GET /knowledge-base/inventory?owner=9999test` → `total_chunks=1` 정상 집계.
   - `GET /docs?owner=9999test&auto_index=false` → 업로드한 Q&A가 `items`에 정상 노출.
   - `POST /api/self-service/test/converse`(owner=9999test, 업로드한 질문 그대로 입력) →
     `tool_trace`의 `self_service_rag_search`가 `matched_doc_ids`로 방금 업로드한 청크를
     정확히 반환하고, **최종 AI 응답이 업로드한 답변 원문 그대로** 반환됨(`"네, 이것은 실서버
     진단용 테스트 답변입니다."`).
3. **실제 1001 테넌트(QA에서 실제로 업로드했던 의류판매 매뉴얼)로 동일 검증**:
   - `GET /knowledge-base/inventory?owner=1001` → `total_chunks=12`(업로드한 12개 청크와 정확히
     일치), `doc_type: "knowledge_document,self_service_manual"`로 두 종류 모두 집계됨.
   - `POST /api/self-service/test/converse`(owner=1001, `"재고 부족한 상품 어떻게 봐?"`) →
     `matched_doc_ids`에 실제 업로드 청크가 잡히고, **응답이 업로드한 매뉴얼 §3 원문과 정확히
     일치**(`"재고관리 화면 상단에 있는 '재고 부족만 보기' 체크박스를 선택하시면..."`).

## 결론

**백엔드(업로드 → 색인 → 집계 → RAG 검색 → 실제 대화 응답)는 현재 실행 중인 서버에서 100%
정상 동작함을 실제 API 호출로 실증했다.** 코드 리뷰가 아니라 실제 데이터로 확인된 사실이다.

사용자가 "반영 안 됨"을 계속 겪는다면, 원인은 백엔드가 아니라 **프론트엔드 표시 계층**일
가능성이 매우 높다. 특히:

- 오늘 `frontend/app/settings/ai-assistant/docs/page.tsx`에 `useRef` 훅을 다수 추가하는
  구조 변경을 여러 차례 수행했다 — Next.js Fast Refresh(HMR)가 훅 구조 변경을 완벽히 반영하지
  못하고 이전 상태를 들고 있는 경우가 있다(Next.js 공식 알려진 한계).
- 브라우저가 이전 JS 번들/상태를 캐싱하고 있을 수 있다.

## 권장 조치 (사용자 확인 필요)

1. 브라우저에서 해당 탭을 **완전히 새로고침**(Ctrl+F5 또는 개발자 도구 "캐시 비우고 강력
   새로고침")한 뒤 재확인.
2. 그래도 안 되면 프론트엔드 개발 서버만 재시작(`Frontend` Job 재시작 — `stop-all.ps1` 후
   `start-all.ps1`, 또는 `frontend` 디렉터리에서 개발 서버 프로세스만 재기동).
3. 그래도 재현되면, 정확히 **어느 화면(탭)에서 어떤 값이 기대와 다른지**(스크린샷 또는 실제
   보이는 숫자/텍스트)를 알려주면 그 특정 프론트엔드 렌더링 경로를 다시 추적하겠다 — 이번
  검증으로 데이터 소스(API) 자체는 정상임이 확인됐으므로, 다음 조사는 프론트엔드 렌더링/캐싱
  쪽으로 범위를 좁혀 진행한다.
