# "삭제해도 계속 데이터가 다시 보인다" 진짜 원인 확정 — GET 조회의 숨은 부작용(자동 재색인)

- 작성일: 2026-08-07
- 버전: v1.0
- 관련 문서: [2026-08-07_full_reset_hard_delete_fix.md](2026-08-07_full_reset_hard_delete_fix.md),
  [2026-08-07_unified_kb_view_reset_and_upload_visibility_fix.md](2026-08-07_unified_kb_view_reset_and_upload_visibility_fix.md)

## 1. 사용자 재보고

서버 재시작 후 "지식 업로드" 탭에서 다시 전체 삭제를 수행했는데, "도우미 지식베이스"(구
"지식베이스(통합)") 탭에는 여전히 데이터가 보인다고 재보고. "몇 번을 계속 제대로 못 하는지
모르겠다"는 지적과 함께 왜 반복되는지 원인 파악을 요청.

## 2. 실제 브라우저로 직접 재현·검증(추측 없이 Playwright로 실제 조작)

1. 실제 브라우저 페이지를 열고 `localStorage.tenant_id=1001` 설정 후 새로고침 → **이 시점엔
   "문서 0건"으로 정상 표시됨**(하드 삭제 수정이 반영된 상태).
2. **아무 삭제 조작 없이 페이지를 한 번 더 새로고침**했더니 → "문서 52건"으로 다시 채워짐.

**이것이 결정적 단서였다.** 삭제 버튼을 누르지 않고 단순히 화면을 재방문(새로고침)했을 뿐인데
데이터가 다시 나타났다 — 삭제 로직 자체의 문제가 아니라 **조회(GET) API 자체가 데이터를
변경하는 부작용을 갖고 있었다.**

## 3. 근본 원인

`GET /api/settings/ai-assistant/docs`(도우미 지식베이스 탭이 쓰는 조회 API)는 "해당 owner의
문서가 0건이면 자동으로 기본 매뉴얼(52개 Q&A)을 재색인한다"는 온보딩 편의 로직을 갖고 있다.
어제(2026-08-07 앞선 세션) 이 문제를 한 번 발견해 `auto_index` 파라미터를 추가했지만,
**"전체 삭제" 버튼을 누른 직후의 재조회 한 번만 `auto_index=false`로 고쳤을 뿐, 페이지를
"그냥 열람"할 때 실행되는 일반 조회(`tab==="qa"/"list"` 진입 시 자동 로드)는 여전히 기본값
`auto_index=true`로 호출하고 있었다.** 즉:

- 삭제 버튼 클릭 직후 화면: 정상적으로 비어 있음(어제 고친 부분).
- **그 상태에서 페이지를 새로고침하거나 다른 탭에 갔다가 돌아오기만 해도**, "0건이니 자동
  재색인"이 다시 실행되어 기본 매뉴얼 52건이 부활 — 사용자가 "삭제가 안 된다"고 느낄 수밖에
  없는 상황이었다.

**왜 반복해서 이 문제를 놓쳤는가**: "삭제 버튼의 직후 동작"만 고치고 "이 데이터를 보여주는
조회 API의 다른 모든 호출 경로"를 함께 점검하지 않았기 때문 — 동일 데이터를 여러 지점에서
호출하는 코드베이스에서 반복되는 패턴(오늘 세션에서 doc_type 필터 누락이 4곳에서 반복된 것과
같은 종류의 실수: "한 곳만 고치고 다른 호출부는 놓침").

## 4. 수정

`frontend/app/settings/ai-assistant/docs/page.tsx`:

- `tab==="qa"/"list"` 진입 시 자동으로 실행되는 조회 effect를 `loadQa(false)`로 변경 —
  **단순 조회(GET)는 어떤 경우에도 더 이상 데이터를 변경하지 않는다**(부작용 제거, REST 원칙
  준수).
- "도우미 지식베이스" 탭에 문서가 0건일 때만 노출되는 **"기본 매뉴얼 불러오기(재색인)"** 버튼
  신설 — 온보딩용 재색인이 필요하면 사용자가 명시적으로 눌러야만 실행된다(`loadQa(true)`).

## 5. 부가 확인 — 탭 명칭 변경 미반영 재확인

사용자가 이전에 "지식베이스(통합)"이라는 이름이 헷갈린다고 지적했던 것이 실제로 반영되지
않았음을 재확인 — 탭 라벨을 **"도우미 지식베이스"**로 변경(고객 지식 베이스/도우미 지식
베이스 명명 규칙과 통일).

## 6. 실제 브라우저로 최종 재검증(수정 후)

1. `DELETE /api/knowledge-base/documents?owner=1001` 호출 → `{"deleted_chunks":52,
   "deleted_documents":0,"deleted_endpoints":0,"deleted_execution_logs":0}`(신규 하드 삭제
   응답 필드가 실서버에서 정상 반환됨을 재확인 — 어제 코드는 재시작 후 처음 실증).
2. 페이지 새로고침 → **"문서 0건" 유지**(더 이상 자동으로 채워지지 않음), 탭 라벨
   "도우미 지식베이스"로 정상 표시, "기본 매뉴얼 불러오기(재색인)" 버튼 노출 확인 —
   Playwright로 실제 렌더링 스냅샷까지 확보.

## 7. 검증

- `npx tsc --noEmit`/`npx eslint` 0에러.
- 실제 브라우저(Playwright)로 재현 → 원인 확정 → 수정 → 재검증까지 전 과정을 실제 화면으로
  직접 확인(코드 리뷰만으로 "고쳤다"고 결론짓지 않음).

## 8. 교훈

- **"삭제 직후" 상태만 확인하고 "그 이후 재방문/새로고침" 상태를 확인하지 않으면, GET
  조회 API에 숨어있는 부작용(auto-reseed 등)을 놓친다** — 이번처럼 "삭제됐다가 조회 시 다시
  채워지는" 유형의 버그는 단발성 액션 테스트로는 절대 못 잡고, 반드시 "그 상태에서 새로고침을
  반복"하는 시나리오까지 테스트해야 한다.
- 같은 데이터를 노출하는 API가 여러 호출 지점(이번엔 "삭제 후 재조회"와 "일반 페이지 진입
  조회" 2곳)을 갖고 있으면, 부작용 제거 수정은 **모든 호출 지점**에 일관되게 적용해야 한다 —
  하나만 고치고 나머지를 놓치는 실수가 오늘 세션에서만 벌써 여러 번(4번) 반복됐다.
- 사용자가 "여러 번 고쳤다는데 계속 재발한다"고 강하게 이의를 제기하면, 실제 브라우저를 열어
  똑같은 조작(그리고 그 이후의 자연스러운 후속 행동, 예: 새로고침)까지 재현해봐야 진짜 원인을
  찾을 수 있다 — 이번에 Playwright로 직접 재현하지 않았다면 "이미 고쳤다"고 잘못 결론지었을
  것이다.
