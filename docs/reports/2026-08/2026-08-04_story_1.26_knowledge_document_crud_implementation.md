## 문제 요약

도메인 비종속 지식베이스 플랫폼 로드맵(Story 1.26~1.29)의 1단계 — 마크다운/PDF/OpenAPI 문서를
웹에서 업로드·조회·수정·삭제할 수 있는 CRUD 기능이 이번 Story의 범위였다. 기존에는 매뉴얼 Q&A만
`.md` 파일 직접 편집 후 재색인으로만 갱신 가능했다(개발자 전용).

## 수행 내용

### 1. 아키텍처 설계 (코드 작성 전)

`self-service-ai-assistant-architecture.md`에 컴포넌트 다이어그램(mermaid)·`knowledge_documents`
테이블 스키마·API 계약표·업로드/삭제 시퀀스 다이어그램(mermaid)·참고문헌 매핑표를 신설(v0.15).
기존 3가지 검증된 패턴(`self_service_catalog_config` 버전관리, `SourceAdapter` 프로토콜,
`knowledge_service` 이중 계층)을 그대로 재사용하도록 설계해 신규 아키텍처 패턴 도입을 피했다.

### 2. 백엔드 구현

- **`src/booking/database.py`**: `knowledge_documents` 테이블 DDL 추가(`chunk_doc_ids_json`을
  신뢰 가능한 단일 소스로 삼아 ChromaDB 청크와의 정합성을 보장).
- **`src/common/knowledge_documents_db.py`**(신규): 문서 lifecycle CRUD(`create_document`/
  `get_document`/`list_documents`/`update_document`/`deactivate_document`) — `self_service_
  catalog_config_db.py` 패턴 재사용.
- **`src/ai_voicebot/self_service/document_adapters.py`**(신규): `SourceAdapter` 프로토콜(Story
  1.25)을 구현하는 `PdfDocumentAdapter`(pypdf 기반 페이지·문단 청킹)와 `OpenApiSpecAdapter`
  (JSON/YAML 파싱, endpoint별 Q&A 페어 변환).
- **`src/ai_voicebot/self_service/knowledge_documents.py`**(신규): 어댑터 선택 → `knowledge_
  service.add_knowledge()`/`delete_knowledge()` 호출 → DB 메타데이터 저장을 조합하는 오케스트
  레이션 레이어. DB 저장 실패 시 이미 색인된 ChromaDB 청크를 롤백하는 정합성 로직 포함.
- **`src/api/routers/knowledge_base_documents.py`**(신규 라우터): `POST/GET/PUT/DELETE
  /api/knowledge-base/documents` 5개 엔드포인트. `src/api/main.py`에 등록.
- **`requirements.txt`**: `pypdf==6.1.1` 명시(venv에 이미 설치되어 있음을 확인 후 pin).

### 3. 프론트엔드 구현

`frontend/app/settings/ai-assistant/docs/page.tsx`에 6번째 탭 "지식 업로드" 추가 — 파일/텍스트
업로드 폼(source_type별 조건부 UI: PDF는 파일 입력, markdown/openapi는 텍스트 영역) + 문서 목록
(태그·유형·청크 수·삭제 버튼). 기존 탭들의 카드/표 UI 패턴과 `apiJson()` 클라이언트를 그대로
재사용해 신규 npm 의존성 없이 구현.

  않았으므로 회귀 위험이 낮았고, 실제로 매뉴얼 Q&A 관련 테스트 전체가 그대로 통과함을 확인.
- **정적 검증**: `npx tsc --noEmit`/`npx eslint` 모두 통과(신규 프론트 코드 포함).
- **라우터 등록 확인**: `from src.api.routers import knowledge_base_documents as r`로 직접
  임포트해 5개 라우트가 정상 등록됨을 서버 기동 없이 확인.

## 발견 사항

- `pypdf`(6.1.1)가 이미 venv에 설치되어 있었다 — 별도 설치 없이 바로 사용 가능했다.
- PDF 어댑터 테스트 작성 중, 손으로 만든 최소 PDF 바이트가 pypdf의 엄격한 EOF 마커 검사를
  통과하지 못해 예외가 발생했다 — `pypdf.PdfWriter`로 실제 유효한 블랭크 페이지 PDF를 생성하는
  방식으로 테스트를 수정해 해결(교훈: PDF 파싱 테스트는 손수 작성한 바이트 대신 같은 라이브러리의
  Writer로 생성하는 것이 안전).

## 실서버 IV 검증 (2026-08-04, 사용자 서버 재시작 후 수행)

- 프로세스 시작 시각(14:05:52) 확인 후 `GET /openapi.json`으로 `/api/knowledge-base/documents`
  라우트가 실제로 등록되어 최신 코드가 반영됐음을 먼저 확인.
- **업로드(POST)** → OpenAPI 스펙 텍스트로 문서 업로드, `{"ok": true, "indexed_chunks": 1}` 확인.
- **목록(GET)** → `owner=9001` 필터로 업로드한 문서가 목록에 정확히 나타남을 확인.
- **단건 조회(GET /{id})** → 메타데이터(title/domain_tags/chunk_count) 정확히 반환됨을 확인.
- **수정(PUT)** → title/domain_tags 변경 → 재조회로 실제 반영됨을 확인(`version_no` 증가).
- **삭제(DELETE)** → `{"deleted_chunks": 1}` 확인 후 목록 재조회 시 완전히 사라짐(소프트 삭제
  정상 동작) 확인.
- **원시 로그 cross-check**(coding-standards.md §6 방법론): `logs/app.log`의
  `knowledge_document_registered`/`knowledge_document_deleted` 구조화 로그 이벤트가 API
  응답과 document_id·chunk 수까지 정확히 일치함을 확인 — API 자체 조작 가능성 배제.
- **프론트엔드 실브라우저 확인**: `http://localhost:3000/settings/ai-assistant/docs`에서 "지식
  업로드" 탭 클릭 → 업로드 폼(제목/도메인 태그/소스 유형/본문)과 문서 목록 테이블이 설계대로
  정상 렌더링됨을 스냅샷으로 확인.
- **결론**: AC1~7 전체 충족. Story 1.26 Status Review→**Done** 전환.
