## 5. 실서버 IV 검증 결과(2026-08-06) — call_context 버그 발견·즉시 수정

- 1차 재시작 후 `GET /intellidecision-manual?owner=9001` 실호출 결과 **모든 유형이
  `has_case=false`로 반환되는 실제 버그를 발견**했다. 원인: `get_self_service_rag_engine()`이
  실제 대화 턴 처리(`agent.py::process_utterance` 진입 시에만) 채워지는 `call_context`
  (ContextVar)에서 embedder/vector_db를 읽는데, 신규 엔드포인트는 대화 턴 밖에서 독립적으로
  호출되므로 컨텍스트가 비어 있어 RAG 검색 자체가 실행되지 않았다.
- **즉시 수정**: `get_intellidecision_manual()`에서 엔드포인트 진입 시 전역 AI Orchestrator
  (`get_ai_orchestrator()`)의 `.rag.embedder`/`.rag.vector_db`를 `set_call_context()`로 주입하고
  `finally`에서 `clear_call_context()`로 해제 — `knowledge_base_simulate.py::_get_isolated_agent`
  와 동일한 재사용 패턴(LLM 클라이언트는 이 Story의 "LLM 호출 없음" 제약상 의도적으로 미주입).
  단위테스트 8건은 모듈 자체를 모킹해 이 함정을 잡지 못했으므로 무수정, 재실행해도 그대로 통과.
- **2차 재시작 후 재검증**: 동일 엔드포인트 실호출 결과 유형 A/B/C/G(`rag_enabled=true`)가 모두
  `has_case=true`로 실제 매칭 문서(doc_id/유사도/related_domain/발췌문)와 hop 경로를 정상
  반환, 유형 D/E/F/H/I(`rag_enabled=false`)는 의도대로 `has_case=false` 유지(AC2/AC3/AC4).
  브라우저(Playwright)로 "AI 의사결정 로직" 탭 유형 A 카드에 "지식베이스 사례" 섹션이 실제
  문서 2건 + hop 칩으로 정상 렌더링됨을 확인(응답 지연 없음 — LLM 호출이 없다는 설계 그대로).
- **교훈**: `call_context.py`의 ContextVar 기반 의존성 주입(embedder/vector_db 등)은 실제 대화
  턴 처리 경로에서만 채워진다 — 그 경로 밖에서(독립 조회 API 등) 같은 헬퍼(`get_self_service_
  rag_engine()` 등)를 재사용하려면 반드시 전역 오케스트레이터 인스턴스에서 필요한 의존성을
  직접 주입해야 한다(`_get_isolated_agent` 패턴). 이번처럼 단위테스트가 해당 모듈을 모킹하면
  이 함정을 전혀 잡지 못하므로, 신규 API가 이런 헬퍼를 재사용할 때는 반드시 실서버 IV로
  실제 값이 채워지는지 확인할 것.
