### 2.2 원인 A — `help` 경로 LLM 출력 포맷 붕괴

- `llm_exchange`에 따르면 응답 예:  
  `저는 ["내일 날씨 안내","태풍 정보","기상감정서 발급","찾을 할 수 있어요. …`  
- 내부 메타데이터/목록이 **자연어 한 줄로 합성되면서 따옴표·대괄호가 잘리거나** 문장이 끊김(`"찾` → 실제로는 "찾아오는 길" 등).
- **근거**: `call_data_record_20260328.log` — `help_response_ok` 직후 동일 패턴의 `llm_exchange` / `tts_text_pushed`.

**대응(우선순위 높음)**  

1. `help` 전용 응답을 **구조화 출력(JSON 스키마)** 으로 생성한 뒤, TTS용으로만 **고정 템플릿**으로 렌더링.  
2. 또는 후처리로 `[` `]` `"` 비율·불완전 괄호를 검사하고, 실패 시 **캐시된 안전 멘트**로 폴백.  
3. `help_intent_rag_llm` 컨텍스트의 `items` 배열을 그대로 읽지 말고, **승인된 capability 문구**만 나열하도록 프롬프트 강화.

### 2.3 원인 B — 키워드 의도 분류 오분류 (`help` ← "어떤 일")

- 3번 턴: `intent_classify`에 **`path`: `keyword`**, **`intent`: `help`**.
- 코드상 `INTENT_KEYWORDS["help"]`에 **`"어떤 일"`** 이 포함되어 있음:

```57:64:sip-pbx/src/ai_voicebot/langgraph/nodes/classify_intent.py
    "help": [
        ...
        "어떤 일",
```

- 사용자 문장 **"기상청은 어떤 일을 하는 곳인가요?"** 는 기관 설명 질문인데, 부분 문자열 매칭으로 `help`에 걸림 → **능력 나열 플로우**로 가서 RAG 기반 설명 기회를 잃음.

**대응**  

1. `"어떤 일"` 단독 매칭 제거 또는 **주변 맥락 필수** (예: "무엇을", "뭘 할 수", "도와줄 수"와 함께일 때만).  
2. 부정 패턴: `하는 곳`, `기관`, `기상청은`, `무슨 일` 등이 있으면 `question` 우선.  
3. 키워드 매칭 전에 **짧은 LLM 분류** 또는 길이/패턴 기반 2단계.

### 2.4 원인 C — 1번 턴 STT 문맥 ("또는 …")

- 확정 텍스트가 **"또는"으로 시작** → 앞부분 누락 가능성(인사 직후 발화 경계, VAD, 이전 발화 잔류 등).  
- 의도 `help` 자체는 타당하나, **입력 품질**이 낮으면 RAG/LLM이 엉뚱한 요약을 할 수 있음.

**대응**: VAD/endpointing 튜닝, 인사 직후 **짧은 무음 가드**, 필요 시 **부분 발화 재확인** 질문.

### 2.5 원인 D — "내일" → 절대일 정규화 후 RAG 불일치

- STT: **"내일 날씨를 알려 주세요."**

2. 날씨·예보 intent는 **정규화 전 문장**으로 1차 검색.

4. 지식 베이스에 **"내일/모레" ↔ 상대일 표현** 메타데이터·동의어 보강.

## 3. RTP · 오디오 전달 (로그 기반)

### 3.1 관측된 구조적 요인

| 현상 | 로그 근거 | 해석 |
|------|-----------|------|
| 착신 RTP 미확정 구간 | `rtp_relay_worker_created` — `callee`: `0.0.0.0:0` | early bind / 더미 착신 단계에서 **착신 미디어 엔드포인트 미결** |
| AI 인수 타이밍 | `no_answer_timeout_activating_ai`, timeout **10s** | 사람 착신 전 **파이프라인·RTP 경로 전환** → 초반 불안정 가능 |
| STUN 반복 | `stun_binding_request_sent_to_caller` attempt 1~3 | NAT/대칭 RTP 환경에서 **바인딩 확정 전** 구간 존재 |

| 패킷 간격 | 첫 구간 약 **85ms** 등 간헐적 갭 | 지터; VAD/endpointing·버퍼 전 **불규칙 전달** |

### 3.2 “간헐적으로 RTP가 안 들리는 것처럼” 느껴질 수 있는 메커니즘

1. **AI takeover 직후** RTP 대상이 caller로 재지정되기 전·후 **짧은 공백**.  
2. **STT 입력 큐 적체**로 **발화 구간이 잘리거나** `stt_final` 경계가 어색해짐 (1번 턴과 연관 가능).  
3. **긴 LLM+RAG 지연**(예: help 그래프 **~9.8s**, 날씨 턴 **~10.4s**) 동안 사용자가 **말을 겹치면** 바지인으로 TTS가 끊기거나 STT가 재시작 → 청각상 “끊김”.  
4. 네트워크 지터와 별개로 **애플리케이션 측 큐·스레드(20ms TTS 송신 등)** 가 순간적으로 밀림.

### 3.3 권장 조치 (RTP/미디어)

1. Takeover 직후 **짧은 프리롤 버퍼** 또는 **STT 시작 지연** 옵션 검토.  
2. `caller_rtp_to_stt_input`에서 **큐 깊이 임계치** 초과 시 경고·메트릭.  
3. **대칭 RTP**, **advertised IP**, **early media vs AI 200 OK** 순서를 환경별로 점검 (로그의 bind IP `0.0.0.0`, `172.30.1.50` SDP와 실제 전달 경로 일치).  
4. 바지인: **파이프라인 안정화 전(예: 첫 TTS 완료 전)** 민감도 완화 옵션.
