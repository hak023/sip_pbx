## 3. 근본 원인 (Root Cause)

### 3.1 생산-소비 속도 불균형

**생산자 (TTS API → Output → PCM Queue)**:
- **속도**: 60~90ms/청크 (1.8초에 27개)
- **특성**: Google TTS는 스트리밍 미지원, 전체 오디오를 한 번에 생성 후 빠르게 프레임 푸시

**소비자 (RTP 송신 스레드 → 네트워크)**:
- **속도**: 500ms/청크 (25 패킷 × 20ms)
- **특성**: 실시간 오디오 재생을 위해 20ms 간격 유지 필수

**불균형**:
```
생산 속도: 66.7ms/청크
소비 속도: 500ms/청크
비율: 7.5배 차이 (소비가 생산보다 7.5배 느림)
```

### 3.2 큐 백로그 누적

**시간대별 큐 크기**:
```

15:29:08.161 → queue_size: 7   (+6, 483ms 경과)
15:29:08.658 → queue_size: 12  (+5, 497ms 경과)
15:29:09.157 → queue_size: 17  (+5, 499ms 경과)
15:29:09.476 → queue_size: 23  (+6, 319ms 경과)
```

**백로그 증가 패턴**:
- 약 500ms마다 **1개 청크 소비**, **5~6개 청크 생산**
- **순증가: +4~5개/500ms**
- 27개 청크 투입 완료 시 **23개가 큐에 대기 중**

### 3.3 왜 이전 수정이 불충분한가?

**이전 수정 (`_pcm_keepalive_queue_timeout_sec`)**:
```python
# ✅ 큐에 청크가 있으면 즉시 처리 (블로킹 방지)
if self._pipecat_pcm_queue is not None and self._pipecat_pcm_queue.qsize() > 0:
    return 0.02
```

**수정의 목적**:
- 큐가 **비었을 때** 1.25초씩 블로킹되는 문제 해결
- 큐에 데이터가 있으면 **즉시(0.02초) 대기 후 다음 청크 처리**

**한계**:
- 큐가 비어있지 않은 상황에서는 효과적
- 하지만 **각 청크를 처리하는 시간(500ms) 자체**는 줄이지 못함
- **RTP 실시간 전송 규격(20ms 간격)**을 준수해야 하므로, 더 빠르게 보낼 수 없음

### 4.2 중기 해결책 (추가 코드 수정)

#### 옵션 A: 적응형 버스트 전송 (Adaptive Burst Transmission)

큐 백로그가 일정 수준(예: 10개) 이상 쌓이면, 일시적으로 **패킷 간격을 단축**(예: 20ms → 10ms)하여 백로그를 빠르게 소진.

**장점**:
- 모든 오디오 데이터 전송 가능
- 단말 jitter buffer가 허용하는 범위 내에서 효과적

**단점**:
- 단말 jitter buffer 크기에 따라 패킷 손실 가능성
- 구현 복잡도 증가

**구현 예시**:
```python
# _pcm_sender_thread_main 내부
if self._pipecat_pcm_queue.qsize() > 10:
    interval_sec = 0.010  # 10ms (버스트 모드)
else:
    interval_sec = 0.020  # 20ms (일반 모드)
```

#### 옵션 B: 큐 크기 제한 + 오래된 청크 병합

큐 크기를 제한(예: 15개)하고, 초과 시 **오래된 청크 2개를 1개로 병합**.

**장점**:
- 큐 백로그 방지
- 일부 오디오 손실 최소화

**단점**:
- 병합 로직 복잡
- 여전히 일부 오디오 손실 발생

#### 옵션 C: TTS 스트리밍 방식 변경 (장기)

Google TTS 대신 **실시간 스트리밍을 지원하는 TTS**로 교체 (예: ElevenLabs, Azure TTS Streaming).

**장점**:
- 근본적 해결
- 생산 속도 = 소비 속도

**단점**:
- TTS 서비스 교체 필요
- 비용/품질 트레이드오프

2. **로깅 확인**

## 6. 추가 관찰

### 6.1 청크 처리 시간 (500ms/청크)

**왜 500ms가 걸리는가?**:
- 각 청크(16000 bytes)는 **25개 RTP 패킷**으로 변환
- 각 패킷은 **20ms 간격**으로 전송 (`_wait_until_send_deadline`)
- **총 시간**: 25 × 20ms = **500ms**

**이는 설계상 정상**:
- RTP 실시간 전송 규격을 준수
- 단말이 연속적인 오디오 스트림으로 인식하도록 함

### 6.2 왜 TTS가 이렇게 빠른가?

**Google TTS API 특성**:
- **스트리밍 미지원** (비실시간 합성)
- 전체 텍스트를 한 번에 합성 → 모든 오디오 프레임을 **일괄 반환**
- Pipecat이 이를 받아 **빠르게** Output으로 푸시

**대조**:
- **실시간 TTS** (예: Azure Streaming): 생성 속도 ≈ 재생 속도
- **Google TTS**: 생성 속도 >> 재생 속도
