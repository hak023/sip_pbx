## 3. 근본 원인 (여전히 존재)

### 3.1 생산-소비 속도 불균형 (지속)

**생산자 (TTS API → PCM Queue)**:
- **속도**: 60.5ms/청크 (현재), 66.7ms/청크 (이전)
- **특성**: Google TTS 일괄 생성 → 빠른 프레임 푸시

**소비자 (RTP 송신 스레드)**:
- **속도**: ~484ms/청크 (첫 청크), 500ms/청크 (이후)
- **특성**: 실시간 오디오 재생 위해 20ms 간격 준수 필수

**불균형 비율**:
```
생산 속도: 60.5ms/청크
소비 속도: 500ms/청크
비율: 8.3배 차이 (소비가 생산보다 8.3배 느림)
```

**이전 대비**: 불균형 비율은 거의 동일 (이전: 7.5배)

### 3.2 왜 개선되었는가?

**이전 문제점**:
1. 큐가 비었을 때 **1.25초씩 블로킹** → 백로그 누적 기회 증가
2. keepalive 간격 8.0초 → 긴 공백 후 급격한 청크 투입
3. `base_time` 타이밍 이슈 → RTP 타임스탬프 비연속성

**적용된 수정**:
1. ✅ **`_pcm_keepalive_queue_timeout_sec()` 수정**:
   ```python
   if self._pipecat_pcm_queue.qsize() > 0:
       return 0.02  # 즉시 소비
   ```
   - 효과: 큐에 데이터 있으면 블로킹 없이 즉시 처리
   - **백로그 누적 속도 감소** (23개 → 14개)

2. ✅ **keepalive 간격 단축** (8.0초 → 3.0초):
   - 효과: 긴 공백 후 급격한 투입 방지
   - **keepalive 갭에서의 뭉개짐 감소**

3. ✅ **`base_time` 재설정 타이밍 개선**:
   - 효과: RTP 타임스탬프 연속성 유지
   - **패킷 순서 문제 해소**

**종합**:
- **블로킹 제거**로 백로그 **증가 속도 감소**
- 하지만 **생산-소비 속도 차이 자체는 여전히 존재**
- 청크 수가 적을 때(16개)는 눈에 띄게 개선, **청크 수가 많을 때(27개+)는 여전히 백로그 가능**

## 4. 남은 문제 분석

### 4.1 "....까..........요....?" 끊김 원인

**가능성 1: 청크 경계에서의 미세 갭**
- 각 청크(25 패킷)가 500ms 소요
- 청크 간 전환 시 **큐 get → 패킷 생성 → 전송** 과정에서 수 ms ~ 수십 ms 지연
- 단말 jitter buffer가 이를 완전히 흡수하지 못할 수 있음

**가능성 2: 큐 백로그로 인한 패킷 타이밍 왜곡**
- 14개 백로그 = **7초 분량 오디오가 큐에 대기**
- RTP 타임스탬프는 연속이지만, **실제 전송 시각은 늦음**
- 단말이 타임스탬프 기준으로 재생하려다 **일부 패킷 드롭** 가능

**가능성 3: 특정 청크에서 간헐적 지연**
- `queue_size_after`가 증가하는 시점(33536: 1→1, 33545: 2, 33552: 3)
- 소비 스레드가 일시적으로 느려짐
- 이유: CPU 스케줄링, GC, 또는 다른 스레드 경쟁

## 5. 왜 여전히 약간 끊기는가?

### 5.1 단말 Jitter Buffer 한계

**Jitter Buffer 역할**:
- 네트워크 지연 변동성 흡수
- 패킷을 버퍼링했다가 일정한 간격으로 재생

**한계**:
- 버퍼 크기 제한 (일반적으로 50~200ms)
- **7초 분량(14개 청크) 백로그**는 버퍼 한계 초과
- 결과: 일부 패킷 **드롭** 또는 **재생 속도 왜곡**

### 5.2 실시간 재생 vs 전송 완료

**사용자 관점**:
- **16:19:36.273**: 첫 음성 들림 ("저는...")
- **16:19:37.241**: EndFrame (TTS 생성 완료)
- **16:19:37.241 + 1초**: "...어떤 도움을 드릴 수..." 재생 중
- **이 시점에 큐에 14개 청크 대기** → **7초 분량이 아직 전송 안됨**

**문제**:
- 사용자는 "...까요?" 부분을 들을 때
- 해당 음성이 **실제로는 수 초 전에 생성되었으나**
- **RTP 전송이 늦어서** 단말이 **늦게 받음**
- 단말이 타임스탬프 기준으로 재생하려다 **일부 건너뜀**

### 5.3 청크 경계 타이밍

**청크 전환 시 미세 지연**:
- 각 청크 완료 후 다음 청크 시작까지 수 ms 소요
- `queue.get(timeout=0.02)` + 패킷 생성 + RTP 헤더 구성
- 이 지연이 누적되면 **수십~수백 ms** 지연 가능

**로그 증거** (추정):
- 16:19:36.757: 청크 완료 + 다음 청크 시작 로그 **같은 타임스탬프**
- 실제로는 수 ms 지연이 있지만 로그 해상도 한계

## 6. 추가 개선 방안

### 6.1 큐 백로그 허용 임계값 설정

**목표**: 큐 크기를 **10개 이하**로 유지

**방법 A: 적응형 패킷 간격**

```python
# _pcm_sender_thread_main 내부
queue_size = self._pipecat_pcm_queue.qsize()
if queue_size > 10:
    interval_sec = 0.015  # 15ms (버스트 모드)
elif queue_size > 5:
    interval_sec = 0.018  # 18ms (중간)
else:
    interval_sec = 0.020  # 20ms (정상)
```

**장점**:
- 백로그 발생 시 **자동으로 속도 증가**
- 단말 jitter buffer 허용 범위 내(15~20ms)

**단점**:
- 복잡도 증가
- 단말에 따라 15ms 간격을 처리 못할 수 있음

**방법 B: TTS 청크 크기 증가**

```yaml
# config.yaml 또는 TTS 설정
tts_chunk_size: 32000  # 현재: 16000
```

**장점**:
- 청크 수 절반 감소 → 큐 오버헤드 감소
- 청크당 처리 시간 1000ms로 증가 → 투입 속도와 균형 개선

**단점**:
- 첫 음성 출력까지 지연 증가 (500ms → 1000ms)
- TTS API가 지원해야 함

### 6.2 로깅 기반 모니터링 강화

**현재 로그의 유용성**:
- ✅ `pcm_queue_size_after` 추적으로 백로그 가시화
- ✅ `rtp_pcm_chunk_to_packets`, `rtp_pcm_chunk_sent_complete` 로 패킷 흐름 추적
- ✅ `tts_rtp_trace_pcm_enqueued` 로 각 TTS 응답별 청크 상관

**추가 제안**:
- **경고 임계값**: `pcm_queue_size > 15` 시 `queue_backlog_warning` 이벤트
- **통화 종료 시 통계**: 최대 백로그, 평균 큐 크기, 백로그 지속 시간

```python
# rtp_relay.py
if queue_size > 15 and not self._queue_backlog_warned:
    structlog.get_logger().warning(
        "queue_backlog_warning",
        call_id=self._call_id,
        pcm_queue_size=queue_size,
        note="PCM 큐 백로그 임계값 초과 — 음질 저하 가능"
    )
    self._queue_backlog_warned = True
```
