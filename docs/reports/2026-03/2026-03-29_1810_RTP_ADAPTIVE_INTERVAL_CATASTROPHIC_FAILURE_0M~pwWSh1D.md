## 3. 근본 원인 (Root Cause)

### 3.1 수정 코드의 근본적 결함

`cumulative_ideal_time_sec` 도입 목적:
- 각 패킷의 실제 간격(`current_chunk_interval_sec`)을 누적하여 절대 시간 추적

**하지만 실패한 이유**:

#### 이유 1: 리셋 로직의 충돌

`rtp_relay.py` (line ~1890):

```python
if not getattr(self, "_rtp_new_segment_after_empty", False) and abs(current_error_ms) > 1000.0:
    # ...
    cumulative_ideal_time_sec = 0.0
```

**문제**:
- 타이밍 오차가 1초를 초과하면 `cumulative_ideal_time_sec`를 리셋
- 하지만 **리셋 직후에도 동일한 오차가 재누적**됨 (line 4550 → 4659: 2초 만에 447ms)
- **리셋이 문제를 해결하지 못하고 증상만 반복**

#### 이유 2: cumulative_ideal_time_sec의 잘못된 초기화

여러 곳에서 `cumulative_ideal_time_sec = 0.0`로 초기화:

1. 첫 PCM 수신 시 (line ~1587)
2. 새 세그먼트 후 (line ~1745)
3. Soft Resync 시 (line ~1778)
4. **타이밍 오차 1초 초과 시** (line ~1890)

**문제**:
- 초기화 시점마다 **이전에 누적된 실제 경과 시간이 사라짐**
- `ideal_target = base_time + cumulative_ideal_time_sec`에서 **cumulative가 0이 되면 base_time만 남음**
- 다음 패킷의 `ideal_target`이 **과거로 돌아가** 음수 sleep 발생 가능

#### 이유 3: 적응형 간격과의 상호작용

**적응형 간격 논리** (line 4243):

```json
{
  "new_interval_ms": 18,
  "prev_interval_ms": 20,
  "pcm_queue_size": 7
}
```

- 큐가 쌓이면 **간격을 줄여 소비 가속** (20ms → 12ms)
- 큐가 비면 **간격을 늘려 안정화** (12ms → 20ms)

**문제**:
- `cumulative_ideal_time_sec`는 간격 변화를 **정확히 누적해야 함**
- 하지만 **리셋 로직이 이를 방해**
- 리셋 후 `cumulative = 0.0`이 되면, **이전까지 소비한 시간이 모두 사라짐**
- 다음 패킷의 `ideal_target`이 **실제보다 훨씬 앞서게 됨** → 음수 sleep → 0으로 clamp → **즉시 전송** → **오차 재누적**

### 3.2 왜 이전보다 더 악화되었나?

#### 이전 버전 (수정 전)

```python
ideal_target = self._rtp_base_time + (self._rtp_packets_sent_total * current_chunk_interval_sec)
```

**문제**:
- `current_chunk_interval_sec`가 변하면 **과거 패킷까지 새 간격으로 재계산**
- 예: 100번째 패킷에서 12ms → 20ms 변경 시, `100 * 20ms = 2000ms`로 계산됨 (실제는 1200ms + 800ms = 2000ms가 아님)

**결과**:
- 타이밍 오차 누적
- **하지만 리셋 없이 계속 진행**

#### 현재 버전 (수정 후)

```python
ideal_target = self._rtp_base_time + cumulative_ideal_time_sec
cumulative_ideal_time_sec += current_chunk_interval_sec
```

**의도**:
- 각 패킷의 실제 간격을 누적하여 정확한 절대 시간 추적

**실제 동작**:
- 타이밍 오차가 1초 초과 시 **강제 리셋** (line 1890)
- 리셋 시 `cumulative_ideal_time_sec = 0.0`
- **다음 패킷의 `ideal_target`이 `base_time + 0.0`**
- **실제로는 이미 수백 패킷이 전송된 상태** → 음수 sleep
- **즉시 전송** → 오차 재누적 → 다시 리셋
- **무한 반복**

**결과**:
- **수정 전보다 훨씬 빠르게 타이밍 오차 누적**
- **리셋이 반복되어 음성이 중간중간 끊김**
- **사용자가 느낀 "전체적으로 완전 뭉개짐"**

## 5. 왜 수정이 실패했는가?

### 5.1 설계 오류: cumulative_ideal_time_sec의 리셋

**의도**:
- 절대 시간을 정확히 추적하기 위해 `cumulative_ideal_time_sec` 도입

**실제**:
- **리셋 로직이 이를 무력화**
- 리셋 시 `cumulative = 0.0`으로 되돌림 (line 1890)
- **절대 시간 추적의 의미가 상실**

### 5.2 구현 오류: 리셋 후 타이밍 계산

**리셋 직후** (line 4542):
- `base_time` = 새 시각 (예: `perf_counter()` 현재값)
- `cumulative_ideal_time_sec` = 0.0
- `packets_sent_total` = 1588 (그대로 유지)

**다음 패킷 전송 시** (line 4550):
- `ideal_target = base_time + 0.108` (cumulative가 0.108초)
- **하지만 실제로는 이미 1588개 패킷 전송됨** (31.76초 상당)
- `now - ideal_target` = **큰 양수** (이미 훨씬 지나감)
- `sleep_needed = ideal_target - now` = **큰 음수**
- **음수 sleep → 0으로 clamp → 즉시 전송**
- **오차 재누적**

### 5.3 적응형 간격의 모순

**목적**:
- PCM 큐 백로그에 따라 간격 조정하여 안정화

**실제**:
- **타이밍 오차가 누적되면 강제 리셋**
- 리셋 후 **cumulative가 0으로 돌아가** 타이밍 기준 상실
- **적응형 간격이 오히려 불안정성을 증폭**

## 7. 비교: 수정 전 vs 수정 후

### 수정 전 (단순 곱셈)

```python
ideal_target = base_time + (packets_sent_total * current_chunk_interval_sec)
```

**문제**:
- 간격 변경 시 과거 패킷까지 새 간격으로 재계산
- 타이밍 오차 누적

**장점**:
- **리셋 없음**
- **계속 진행**
- **손실률 상대적으로 낮음** (이전 리포트에서 20~30%)

### 수정 후 (누적 추적)

```python
ideal_target = base_time + cumulative_ideal_time_sec
cumulative_ideal_time_sec += current_chunk_interval_sec
```

**의도**:
- 각 패킷의 실제 간격을 누적하여 정확한 추적

**실제**:
- **리셋 로직이 누적값을 파괴**
- **리셋 후 타이밍 기준 붕괴**
- **손실률 46.8%** (거의 2배 증가)

## 8. 즉시 조치 필요사항

### 8.1 긴급 조치

1. **백엔드 즉시 재시작**
   - `config.yaml` 변경사항 반영 (`enabled: false`)
   - **적응형 간격 완전 비활성화**

2. **코드 롤백 필요**
   - `cumulative_ideal_time_sec` 로직 제거
   - **수정 전 버전으로 복원** (단순 곱셈 방식)
   - 수정 전 버전이 **차라리 나음** (손실률 20~30% < 46.8%)

### 8.2 근본 해결책

적응형 간격 자체가 **근본적으로 결함이 있음**:

1. **절대 시간 추적과 상충**
   - 간격이 변하면 절대 시간 계산이 복잡해짐
   - 리셋 로직과 충돌

2. **RTP의 본질적 특성 무시**
   - **RTP는 일정한 간격을 기대** (20ms)
   - **간격을 동적으로 변경하면 jitter buffer가 혼란**

#### 권장 해결책

**Option 1: 적응형 간격 완전 제거**

- **고정 20ms 간격**
- **PCM 큐 백로그는 큐 크기 조정으로 해결**
- **jitter buffer 안정성 최우선**

**Option 2: 구간별 고정 간격**

- 응답마다 **간격을 한 번만 결정** (백로그 기반)
- **응답 도중에는 절대 변경하지 않음**
- **리셋 로직 제거**

**Option 3: 전문 RTP 라이브러리 사용**

- `pjsua`/`pjmedia` 또는 `gstreamer`
- **검증된 타이밍 로직**
- **직접 구현의 한계 인정**

## 9. 기술 부채 (Technical Debt)

### 9.1 현재 코드의 근본적 문제

1. **복잡도 폭발**
   - `cumulative_ideal_time_sec` 추가
   - 리셋 로직 4곳 (`line 1587, 1745, 1778, 1890`)
   - 각 리셋마다 초기화 로직
   - **유지보수 불가능**

2. **테스트 불가능**
   - 타이밍 오차가 언제 1초를 초과할지 **예측 불가**
   - 리셋이 언제 발생할지 **비결정적**
   - **재현 어려움**

3. **로직 충돌**
   - 적응형 간격 vs. 절대 시간 추적
   - 리셋 vs. 누적 추적
   - **상호 모순**

### 9.2 권장 조치

**즉시**:
1. 백엔드 재시작 (config.yaml 반영)
2. 고정 20ms 간격으로 복원
3. 테스트 통화

**단기**:
1. `cumulative_ideal_time_sec` 로직 완전 제거
2. 단순 곱셈 방식으로 롤백
3. 안정성 확인

**중장기**:
1. 전문 RTP 라이브러리 도입 검토
2. 또는 구간별 고정 간격 방식 재설계
3. 적응형 간격은 **영구 보류**

### 10.4 교훈

- 수정 전 버전의 문제 (20~30% 손실)를 해결하려다가
- **오히려 더 심각한 문제 (46.8% 손실)**를 초래
- **단순한 해결책 (고정 간격)이 복잡한 해결책 (적응형 간격)보다 나음**
