## 2. 비활성화 이유

### 2.1 발견된 버그 (call_id: 7vV6sKS5nD)

**증상**:
- ❌ **80% 오디오 손실** (2120 패킷 → 425 패킷만 전송)
- ❌ **817ms Jitter Spike** (정상 20ms의 40배)
- ❌ **타이밍 오차 773ms** 누적
- ❌ 사용자 피드백: "오다가" 부분 미청취

**근본 원인**:
```python
# src/media/rtp_relay.py:1755 (수정 전)
ideal_target = self._rtp_base_time + (
    self._rtp_packets_sent_total * current_chunk_interval_sec
)
```

- 현재 간격(`current_chunk_interval_sec`)을 전체 누적 패킷에 곱함
- **이전 패킷의 실제 간격(12~18ms) 무시**
- → 타이밍 오차 누적 → 817ms sleep → 패킷 손실

### 2.2 안정성 우선

**판단**:
- 적응형 간격 로직 자체는 **정상 작동** (큐 백로그에 따라 12~20ms 동적 조정)
- 하지만 **타이밍 계산 버그**로 인해 실운영 불가
- 버그 수정은 **완료**되었으나, **테스트 전까지는 고정 20ms가 더 안전**

**비활성화 효과**:
- ✅ **고정 20ms 간격** 사용
- ✅ 817ms 갭 발생 안 함 (타이밍 계산 단순화)
- ✅ 80% 손실 해소
- ⚠️ 백로그는 여전히 발생 가능 (14~18개)

## 4. 현재 상태 (비활성화)

### 4.1 동작 방식

**고정 20ms 간격**:
- PCM 큐 백로그 무관
- 모든 패킷을 **20ms 간격**으로 전송
- 타이밍 계산: `ideal_target = base_time + (packets_total × 0.020)`
- → **단순하여 버그 없음**

**장점**:
- ✅ 안정적 (검증됨)
- ✅ 타이밍 오차 없음
- ✅ Jitter Spike 없음

**단점**:
- ⚠️ 백로그 해소 느림 (14~18개 유지)
- ⚠️ 전송 시간 약간 김 (25% 더 소요)

### 4.2 운영 가능성

**현재 설정** (`enabled: false`):
- ✅ **운영 가능** (안정적)
- 오디오 품질: **양호**
- 백로그: 14~18개 (허용 범위)

**수정 후 재활성화** (`enabled: true`):
- ⚠️ **테스트 필요** (817ms 갭 재발 여부 확인)
