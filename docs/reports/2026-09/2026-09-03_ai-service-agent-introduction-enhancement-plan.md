## 1. 작성 목적

현재 소개서는 배경, 1차 PoC 기반, 착신전환 시나리오, 세 핵심 기술이라는 큰 흐름을 갖췄다. 그러나 핵심 기술 장은 판단표와 예시를 제시하는 수준에 머물러, 기존 자료에 축적된 작동 원리와 운영 효과를 충분히 전달하지 못한다. AICC 비교도 표 한 장으로 끝나 있어, 왜 이 PoC가 소규모 사업자와 고객사별 운영 환경에 적합한지 설득력이 약하다.

이번 개정은 문서의 분량을 단순히 늘리는 작업이 아니다. 임원·사업 책임자가 다음 세 가지를 한 번에 이해하도록 소개서를 다시 다듬는다.

1. 기존 Builder 중심 AICC를 구축·변경·운영할 때 어떤 부담이 생기는가
2. IntelliDecision, N-hop RAG, Dynamic Tool Wrapper가 그 부담을 각각 어떻게 줄이는가
3. 지식 품질, 권한, 승인, API 제약을 갖춘 범위에서만 동작하는 PoC임을 어떻게 투명하게 설명할 것인가

## 3. 개정 원칙

### 3.1 독자 관점

각 기술 장은 기술 명칭부터 설명하지 않는다. 먼저 고객센터 운영자가 겪는 문제를 제시하고, 해당 기술이 착신전환 시나리오에서 어떤 판단 또는 조치를 수행하는지 보여 준다. 그 다음에 운영자가 무엇을 수정하고 무엇을 확인할 수 있는지 설명한다.

### 3.2 표현 경계

- 비교 대상은 모든 AICC가 아니라 **업무 Flow를 사전에 설계하는 Builder 중심 AICC**로 한정한다.
- "어떤 질문도 정확히 답한다" 같은 전면적 보장은 사용하지 않는다. 지식·권한·승인 정책 범위 안에서 안내, 추가 확인, 실행, 이관 중 적절한 다음 행동을 고른다고 표현한다.
- 실제 서비스 매뉴얼과 PoC 검증용 OpenAPI 계약을 분명히 구분한다.
- OpenAPI를 등록해도 모든 API가 실행되는 것은 아니다. 접속 정보, 인증, 허용 메서드, 업무 규칙, 승인, 사후 검증 조건이 충족될 때만 실행한다.
- 외부 기업의 공개 성과는 시장 사례의 사실로만 인용하며 PoC 성과나 예상 절감 효과로 옮겨 적지 않는다.

### 3.3 문체 기준

| 피할 표현                     | 교정 방향                                                                            |
| ----------------------------- | ------------------------------------------------------------------------------------ |
| "운영 투명성이다"             | 관리자가 답변 근거와 실행 이력을 보고 원본 문서를 바로 고칠 수 있다고 구체화         |
| "기능을 제공한다"             | 대기 시간을 줄인다, 변경 전 확인을 강제한다, 잘못된 실행을 막는다처럼 결과 동사 사용 |
| "~할 수 있는지 검증한다" 반복 | 문단 본문은 작동 결과를 설명하고, 절 마지막에서만 PoC 검증 항목을 정리               |
| 추상적인 병렬 나열            | 판단 순서와 주체를 드러내는 짧은 문장으로 분리                                       |
| "무조건", "모든 질문"         | 지식·정책·권한 범위와 이관 기준을 함께 제시                                          |

## 5. 핵심 기술별 보강 설계

### 5.1 IntelliDecision - 대화마다 다음 행동을 다시 고르는 계층

**문제 제기**: 고객은 "가능한가요?"라고 묻다가 "설정해 주세요"로 바꾸고, 번호를 정정하거나 실행을 취소한다. Builder 중심 AICC는 이 변형마다 Flow와 상태 전이를 미리 추가해야 한다.

**추가할 설명**:

1. 고객 발화를 안내, 실행, 포괄 도움, 정정, 취소, 모호성 해소, 일괄 처리, 범위 밖, 반복의 9가지 판단 유형으로 다룬다.
2. 유형 이름만 고르는 것이 아니라 이전 대화에서 확인한 값, 아직 필요한 값, 적용 권한과 실행 위험을 함께 비교한다.
3. 판단 결과에 따라 RAG 검색, 추가 질문, 승인 요청, 도구 실행, Undo, 사람 이관 중 한 경로를 선택한다.
4. 관리자는 어떤 유형으로 판단했는지와 어떤 지식·도구가 이어졌는지 확인해 정책이나 지식을 보완할 수 있다.

**착신전환 관통 예시**:

```text
┌─────────────┐   ┌───────────────────────────────────┐   ┌──────────────────┐
│ 고객 발화    │ → │ IntelliDecision                    │ → │ 다음 응답·행동    │
├─────────────┤   ├───────────────────────────────────┤   ├──────────────────┤
│ 가능한가요?  │   │ 안내 요청 · KB-01/03 검색         │   │ 가능 여부·화면 안내│
│ 설정해 주세요│   │ 실행 요청 · 전환 번호 누락        │   │ 번호 입력 요청     │
│ 번호를 바꿀게요│ │ 정정 요청 · 10초 조건은 유지      │   │ 승인 문구만 갱신   │
│ 취소해 주세요│   │ 복원 요청 · 실행 이력·Undo 확인   │   │ 복원 또는 이관     │
└─────────────┘   └───────────────────────────────────┘   └──────────────────┘
```

**PoC 검증 기준**: 같은 세션에서 안내→실행→정정→취소가 이어져도 이미 확인한 정보는 유지하고, 변경된 정보와 안전 조건만 다시 확인하는지 검증한다.

### 5.2 N-hop RAG - 문서 조각을 업무 맥락과 다음 행동으로 연결

**문제 제기**: 일반 RAG는 질문과 유사한 문장을 찾는 데 강하지만, 고객센터 답변에는 사용 가능 조건, 기존 규칙 충돌, 화면 위치, 실행 가능 여부가 함께 필요하다. 문서 한 조각만 인용하면 고객은 다음 행동을 알 수 없다.

**추가할 설명**:

1. 1-hop은 질문과 가장 가까운 원본 카드에서 기능 가능 여부와 기본 조건을 찾는다.
2. 2-hop은 같은 업무 도메인의 규칙과 우선순위를 확인해 충돌 가능성과 예외를 찾는다.
3. 3-hop은 화면 경로와 승인된 API 계약을 연결해 고객이 직접 할 일 또는 AI가 준비할 일을 결정한다.
4. 답변은 "가능 여부 → 적용 조건 → 화면 위치 → 다음 행동" 순서로 조합한다.
5. UI가 바뀌면 화면 카드, 업무 규칙이 바뀌면 정책 카드만 바꾼다. 답변 원문과 연결 경로를 확인할 수 있으므로 수정 지점을 추측하지 않는다.
6. 확장 깊이와 연결 가능한 관계는 정책으로 제한한다. 관련 없는 문서를 무제한으로 따라가 답변을 부풀리지 않는다.

**관계형 시각 자료**:

```text
질문: "10초 뒤 전환은 어디서 설정하나요?"

  [KB-01 무응답 시간] ──같은 착신 제어 업무──> [KB-02 규칙 우선순위]
             │                                      │
             └────설정 화면 안내 필요───────────────> [KB-03 메뉴 경로]
                                                        │
                                                        ▼
       "10초를 선택할 수 있습니다. 기존 활성 규칙의 우선순위를 확인한 뒤,
        설정 > 착신 제어 > 착신전환 대상에서 대상 번호를 등록하세요."
```

**PoC 검증 기준**: 답변마다 사용 카드와 연결 단계가 기록되고, 화면·규칙·계약 가운데 하나가 변경돼도 해당 원본만 수정해 다음 응답에 반영할 수 있는지 확인한다.

### 5.3 Dynamic Tool Wrapper - 등록된 API를 통제된 실행 도구로 전환

**문제 제기**: 고객이 "설정해 주세요"라고 말한 뒤 다시 상담원에게 넘기면 셀프서비스가 끝나지 않는다. 반대로 AI가 API를 무제한 호출하면 권한 오용과 잘못된 변경 위험이 생긴다.

**추가할 설명**:

1. OpenAPI 문서에서 엔드포인트, 입력값, 응답 형식, 접속 주소와 인증 정보를 읽어 실행 후보를 만든다.
2. 조회는 필요한 정보 확인에 쓰고, 쓰기 메서드는 관리자가 승인한 경우에만 AI의 도구 후보에 노출한다.
3. 실행 전에는 업무별 적용 범위와 권한, 업무 규칙, 필수 입력값, 변경 전 상태를 확인한다.
4. AI는 변경 내용을 고객에게 평문으로 요약하고 명시적 승인을 받은 뒤에만 호출한다.
5. 호출 뒤에는 응답 메시지만 보지 않고 원격 상태를 다시 조회한다. 사전 상태와 복원 API가 준비된 경우에만 Undo를 제안한다.
6. 인증 정보가 없거나, 허용 메서드가 아니거나, 사후 검증에 실패하면 실행 완료로 안내하지 않고 추가 확인 또는 이관으로 전환한다.

**실행 흐름 시각 자료**:

```text
OpenAPI 업로드
     │
     ▼
엔드포인트·입력값·인증 방식 추출
     │
     ▼
허용 메서드만 Tool 후보로 등록 ── 미승인 쓰기 요청 → 안내 또는 이관
     │
     ▼
본인 회선·업무 규칙·변경 전 상태 확인
     │
     ▼
고객 최종 승인 → 외부 API 호출 → 원격 상태 재조회 → 실행 이력·Undo 조건 기록
```

**PoC 검증 기준**: 승인하지 않은 쓰기 요청이 도구 후보로 노출되지 않는지, 승인한 변경은 실행 전·후 상태와 이력을 대조할 수 있는지, 복원 불가능한 API에는 Undo를 약속하지 않는지 확인한다.

## 6. AICC 비교 재설계

### 6.1 비교 범위

비교 대상은 범용 AICC 전체가 아니라 **전문 엔지니어가 업무별 대화 Flow, 상태 전이, API 결과 분기를 사전에 구성하는 Builder 중심 AICC**다. 생성형 AI와 지식 검색, API 연동을 제공하는 최신 AICC도 있으므로 기존 AICC를 일괄적으로 단순하거나 열등한 방식으로 규정하지 않는다.

### 6.2 본문에 반영할 비교표

| 비교 축     | Builder 중심 AICC                            | 지능망 AI Service Agent PoC                                         | 고객·운영 효과                             |
| ----------- | -------------------------------------------- | ------------------------------------------------------------------- | ------------------------------------------ |
| 초기 구축   | 업무별 Flow, 예외, 상태 전이를 설계하고 시험 | 지식 문서·API 계약·승인 정책을 등록하고 공통 판단 구조를 적용       | 작은 업무부터 빠르게 검증                  |
| 비정형 발화 | 미리 만든 분기 밖의 표현은 추가 설계가 필요  | IntelliDecision이 목적·맥락·누락 정보를 다시 판단                   | 고객이 정해진 질문에만 맞춰 말할 부담 축소 |
| 지식 변경   | 답변·분기·시나리오 테스트를 함께 수정        | 원본 카드의 업무 규칙·화면 안내·정책을 수정하고 근거를 재확인       | UI와 정책 변경에 더 빠르게 대응            |
| API 연동    | 기능별 중계 로직과 성공·실패 분기 설계       | OpenAPI 계약에서 후보를 만들고 승인·사전 상태·사후 검증을 공통 적용 | 연결 방식의 반복 작업 감소                 |
| 고객별 적용 | 고객사마다 Flow 구축 프로젝트가 누적         | 고객사별 지식·권한·API를 분리 등록                                  | 동일 구조를 여러 고객사에 재사용           |
| 운영 개선   | Flow와 프롬프트, 로그를 함께 추적            | 답변 근거 카드와 실행 이력에서 수정 지점을 확인                     | 운영자가 지식 중심으로 개선                |

### 6.3 반드시 함께 적을 한계

- 이 PoC는 복잡한 업무 Flow 설계를 줄이는 방향이지, 모든 예외 설계와 운영 책임을 없애는 제품이 아니다.
- 고위험 변경, 법적 판단, 지식이 없는 요청, 복원할 수 없는 작업은 사람의 확인 또는 이관이 필요하다.
- 지식 문서의 정확성, API 계약의 품질, 권한 정책의 완전성이 응대 품질과 실행 안전성을 결정한다.

## 7. 시장 사례 편집 방향

본문 대표 사례는 **Zendesk AI Agent와 Babbel**로 압축한다. Babbel은 반복 문의 유형을 먼저 분석해 자동화 우선순위를 정했고, 구독 상태·구독 관리·언어 변경 요청을 대상으로 AI 상담사를 운영했다. 이후 구독 관리 API를 열어 Zendesk AI와 백엔드 시스템을 연동했으며, 개인정보 요청처럼 개별 판단이 필요한 문의는 사람에게 남겼다. 지식 기반 응대, 대화 중 의도·복잡도 판단, 백엔드 API 실행, 사람 이관을 한 운영 사례에서 함께 보여 주므로 세 핵심 기술의 대표 사례로 적합하다.

Zendesk가 공개한 Babbel의 지표는 AI 자동화율 50% 이상, 상담사 온보딩 기간 67% 단축, 메시징·채팅 채널 비중 45%다. 45%는 고객 접점 중 메시징·채팅이 차지하는 비중을 뜻한다. 모든 수치는 Zendesk가 공개한 고객 사례이며 PoC 성과나 예상 성과로 사용하지 않는다.

Google Dialogflow CX와 OpenAI GPT Actions는 본문을 늘리지 않고 각주 또는 "참고한 시장 모델" 표로 축약한다. Dialogflow CX는 Builder 중심 Flow 방식의 비교 근거로, GPT Actions는 OpenAPI 기반 자연어 실행의 선행 사례로 남긴다.

## 9. 작업 순서와 검토 기준

1. 현재 소개서와 상세 참고 자료집에서 핵심기술별 사실·근거·한계를 대조한다.
2. 5~7장을 공통 구조로 확장하고, 세 기술이 착신전환 시나리오에서 이어지는 문장을 재작성한다.
3. 8장을 대표 시장 사례 1건과 간결한 참고 표로 재편한다.
4. 9장을 Builder 중심 AICC 비교와 PoC 한계까지 포함하는 사업 비교 섹션으로 확장한다.
5. CS 후보 업무를 세 기술 조합과 연결하고, PoC 이후의 적용 순서를 설명한다.
6. 아래 국문 보고서 문체 기준으로 전체 문장을 전면 교정한다.
7. 소개서, INDEX, 완료 리포트의 버전·링크·검증 기록을 맞춘다.
8. Markdown 진단, 링크·헤더 구조, 중복 문단, `git diff --check`를 확인한다.

## 10. 사용자 검토 요청

이 계획은 다음 결정을 전제로 한다.

1. 본문 시장 사례는 Zendesk AI Agent와 Babbel 1건으로 압축한다.
2. AICC 비교는 Builder 중심 AICC를 대상으로 하며, 최신 AICC 전체를 낮춰 평가하지 않는다.
3. 핵심 기술의 설명은 10초 무응답 착신전환 단일 시나리오를 계속 사용한다.
4. Dynamic Tool Wrapper는 업무별 권한·승인 정책·사후 검증 기준을 적용하며, 특정 회선 유형으로 적용 범위를 한정하지 않는다.

검토가 승인되면 이 계획을 기준으로 정식 소개서, INDEX, 9월 완료 리포트를 순서대로 개정한다.

## 11. 국문 보고서 문체 교정 기준

국립국어원의 공공언어 개선 원칙과 정부·공공기관의 보고서 작성 관행을 참고해, 소개서를 설명문이 아니라 의사결정용 보고서로 다듬는다. 핵심은 문장을 멋있게 꾸미는 데 있지 않다. 독자가 첫 문장에서 결론을 파악하고, 다음 문장에서 근거와 조건을 확인하게 만드는 데 있다.

| 원칙               | 적용 방식                                                                                                                  | 교정 예시                                                                                                              |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| 결론 우선          | 문단 첫 문장에 판단이나 업무 결과를 둔다. 배경 설명은 뒤에 붙인다.                                                         | "Dynamic Tool Wrapper는 승인된 업무를 실행 도구로 바꾼다. OpenAPI 문서에서 입력값과 호출 방식을 읽고 정책을 적용한다." |
| 사실과 판단 분리   | 외부 사례·CS 수치·PoC 목표를 한 문장에 섞지 않는다. 수치에는 출처와 의미를 붙인다.                                         | "Babbel의 자동화율은 Zendesk 공개 기준 50% 이상이다. 이 수치는 본 PoC의 예상 효과가 아니다."                           |
| 한 문장 한 메시지  | 원인, 방법, 결과를 한 문장에 나열하지 않는다. 긴 문장은 둘 이상의 문장으로 나눈다.                                         | "AI는 전환 번호를 확인한다. 값이 없으면 번호만 다시 묻는다."                                                           |
| 주어와 책임 명시   | "구성된다", "처리된다"보다 고객·AI·관리자·시스템 중 행동 주체를 쓴다.                                                      | "관리자는 허용 메서드를 승인한다. AI는 승인된 도구만 선택한다."                                                        |
| 쉬운 우리말 우선   | 불필요한 영문식 명사화와 추상어를 줄이고, 꼭 필요한 기술 용어는 처음 한 번만 풀어 쓴다.                                    | "실행 가능 여부 판단" → "실행해도 되는지 확인"                                                                         |
| 동일 용어 유지     | 고객사, 지식 카드, 업무 규칙, 실행 계약, 승인 정책처럼 핵심 명사를 고정한다. 같은 대상을 문단마다 다른 말로 부르지 않는다. | "API 계약", "API 명세", "실행 계약"을 문맥에 따라 임의로 섞지 않음                                                     |
| 조건을 숨기지 않음 | PoC의 한계와 실행 전제는 각 주장 가까이에 둔다. 결론에서만 단서로 몰아넣지 않는다.                                         | "복원 API가 없으면 Undo를 제안하지 않는다."                                                                            |

교정 대상에서는 "제공한다", "가능하게 한다", "기반으로", "통해", "검증한다"의 기계적 반복을 줄인다. 다만 기술적 사실을 정확히 전달하는 경우에는 억지로 다른 표현으로 바꾸지 않는다. 문체의 목적은 화려함이 아니라 짧고 정확한 판단 전달이다.
