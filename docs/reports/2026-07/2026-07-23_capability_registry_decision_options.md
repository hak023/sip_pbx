# 능력 레지스트리(제안 2) 방향 결정을 위한 상세 리포트 — 옵션 비교 및 권장안

**작성일**: 2026-07-23
**목적**: [Story 1.17(Draft)](../../stories/1.17.capability-registry-rag-plan.story.md)에
남겨둔 5개 결정 사항에 대해, 실제 코드를 추가로 조사한 근거를 바탕으로 옵션별 장단점과
권장 방향을 제시한다. **이 문서는 의사결정 지원용이며 코드 변경은 없다.**

---

## 0. 추가 조사에서 발견한 중요 사실 — 기존 계획을 수정해야 하는 이유

Story 1.17 초안 작성 당시에는 "완전히 새로운 능력 레지스트리 모듈+API"를 가정했다. 이번에
`src/api/routers/settings_ai_assistant.py`를 다시 확인한 결과, **도메인 기반 능력 정보는
이미 프론트엔드에 노출되어 있음**을 발견했다:

- `GET /catalog`: 도메인별 `writable`(쓰기 가능 여부), `writable_fields`, `destructive`,
  `related_manual_domains`를 이미 반환한다(프론트엔드 "AI 변경 가능 설정" 탭이 이미 사용 중).
- `GET /screen-graph`: 도메인별 화면 안내 정보를 이미 반환한다("화면 안내" 탭이 이미 사용 중).

**즉, "설정 조회/자동설정/화면 안내" 3개 능력 카테고리는 이미 프론트엔드에 실시간으로
노출되고 있어 새로 만들 필요가 없다.** 실제로 비어 있는 부분은 **Tool 기반 능력**
(이용 통계 조회, 통화 이력 NLQ 3종, 온보딩 체크리스트, 그리고 Story 1.16에서 추가된 실행
취소)뿐이다 — 이 5가지는 `settings_catalog`/`screen_graph`가 다루는 "도메인" 개념이 아니라
독립적인 Tool이라 지금까지 프론트엔드 어디에도 노출된 적이 없다.

**이 발견은 Story 1.17의 범위를 상당히 축소시킨다.** 아래 권장안은 이 축소된 범위를 반영한다.

## 1. 캐시 무효화 연동 방식

| 옵션                                                    | 설명                                                                                                                                                                      | 장점                                                                                                         | 단점                                                                                      |
| ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------- |
| A. `catalog_config_loader.invalidate_cache()`에 훅 추가 | 능력 레지스트리 캐시를 카탈로그 캐시와 같은 시점에 무효화                                                                                                                 | 일관성 보장                                                                                                  | 캐시가 2단이 되어(카탈로그 캐시 + 능력 캐시) 무효화 누락 시 디버깅 어려움                 |
| B. 별도 TTL 캐시(예: 60초)                              | 구현 간단                                                                                                                                                                 | 무효화 로직 자체가 없어 실수 리스크 적음                                                                     | 카탈로그가 막 바뀐 직후 최대 TTL만큼 낡은 응답 가능(Epic 2 FR20 "즉시 반영" 원칙과 충돌)  |
| **C. 캐시 없음 — 매 요청 재계산 (권장)**                | `settings_catalog.list_domains()` 등은 이미 `catalog_config_loader.get_cached_config()`로 캐시된 데이터를 읽는 **순수 인메모리 연산**(DB I/O 없음)이라 추가 캐시가 불필요 | 무효화 버그 자체가 발생할 수 없음(가장 단순·안전), Epic 2 FR20("서버 재시작 없이 즉시 반영")을 자동으로 만족 | 매 프롬프트 조립마다 도메인 순회 연산이 발생하나, 도메인 수가 7개 수준이라 비용 무시 가능 |

**권장: 옵션 C.** 이미 존재하는 캐시(Epic 2) 위에 또 캐시를 얹으면 "캐시의 캐시" 무효화 문제가
생긴다. 데이터 원본이 이미 저렴하게 캐시되어 있으므로, 그 위의 집계 함수는 캐시 없이 매번
계산해도 성능에 영향이 없다(NFR1 지연 예산에 실질적 영향 없음 — 7개 도메인 순회는 마이크로초
단위).

## 2. Tool 기반 능력의 "예시 발화" 소스

| 옵션                                     | 설명                                                                                                                                                               | 장점                                                                                   | 단점                                                                                                                                        |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| **A. 정적 매핑(코드에 하드코딩) — 권장** | `SELF_SERVICE_TOOLS`의 각 Tool에 대응하는 예시 발화 1개를 코드 상수로 관리(예: `_TOOL_EXAMPLE_PHRASES = {"get_self_service_stats": "이번 달 AI 몇 번 응대했어?"}`) | Tool 개수가 9개로 적어 유지보수 부담 작음, 환각 리스크 없음(사람이 검증한 문구만 노출) | Tool 추가 시 이 매핑도 함께 갱신해야 함(단, 이미 `SELF_SERVICE_TOOLS` 추가 시 테스트 3개 파일도 갱신하는 기존 관례와 동일한 부담)           |
| B. 매뉴얼 Q&A와 자동 연결                | 매뉴얼 Q&A의 질문 문구를 예시로 재사용                                                                                                                             | 별도 유지보수 불필요해 보임                                                            | 실제로는 Tool과 매뉴얼 Q&A가 1:1 대응하지 않음(매뉴얼은 설정 방법 위주, Tool은 조회/통계/이력), 매핑 규칙을 새로 설계해야 해 오히려 더 복잡 |

**권장: 옵션 A.** Tool이 9개뿐이고 자주 늘어나지 않으므로(신규 Tool 추가는 이미 회귀 테스트
갱신이 필요한 무거운 변경), 정적 매핑의 유지보수 비용은 낮다. 반대로 매뉴얼 연결은 "동적화"를
명분으로 오히려 새로운 매핑 계층을 만드는 역설이 있어 기각한다.

## 3. 유형 C(도움 요청) 응답 품질 리스크

**우려**: 구조화된 dict를 그대로 프롬프트에 넣으면 LLM이 어색하게 나열식으로 답할 수 있다.

**권장 완화책**: "원시 데이터를 프롬프트에 그대로 넣지 않는다." 대신 기존 정적 문구와 동일한
문체의 텍스트를 **Python 포맷터 함수**가 조립해서 넣는다(이미 `_format_rag_context()`,
`_format_onboarding_section()`, `_format_screen_guidance()`가 동일한 패턴 — "동적 데이터 →
사람이 읽기 좋은 텍스트 블록" 변환 후 프롬프트 삽입). 즉 LLM에게 "이 데이터를 요약해서
답하라"고 시키는 게 아니라, **Python 코드가 이미 자연스러운 한국어 문장 형태로 변환한 텍스트**를
프롬프트에 넣으므로 Story 1.15의 정적 문구와 체감 품질 차이가 거의 없어야 한다.

**필수 검증**: 실서버에서 하드코딩 버전(현재)과 동적 버전을 동일 질문("뭘 할 수 있어?") 5회씩
비교해, 응답에 최소 3개 카테고리+구체 예시가 포함되는 비율이 유지되는지 확인한다(Story 1.15
AC2 기준 유지). 저하되면 포맷터 함수의 텍스트 조립 방식을 조정한다(코드 배포 없이 되돌릴 수
있어야 하므로, **동적 버전 롤아웃 시 정적 버전 문자열을 완전히 삭제하지 말고 fallback 상수로
남겨 즉시 되돌릴 수 있게 할 것**을 권장).

## 4. 프론트엔드 UI 설계

§0에서 확인했듯 도메인 기반 능력(조회/쓰기/화면안내)은 이미 `catalog`/`screen` 탭에 노출되어
있다. 따라서:

| 옵션                                                 | 설명                                                                                              | 장점                                                                               | 단점                                                                                                         |
| ---------------------------------------------------- | ------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| A. 완전히 새로운 5번째 탭("AI가 할 수 있는 일")      | 모든 능력(도메인+Tool)을 한 화면에 재구성                                                         | 한눈에 보기 좋음                                                                   | `catalog`/`screen` 탭과 내용이 상당 부분 중복 — 유지보수 포인트 2배, "어느 화면이 최신 정보인지" 혼란 리스크 |
| **B. 기존 탭에 "Tool 기반 능력" 섹션만 추가 — 권장** | 실제 공백(통계/통화이력 NLQ/온보딩/실행취소 4~5종)만 신규 노출, 도메인 정보는 기존 탭 그대로 사용 | 중복 없음, 구현 범위 최소(신규 탭 아님, 작은 위젯/섹션 1개), 정보 소스 일원화 유지 | "능력 총정리" 한 화면 조망은 안 됨(다만 탭 4개를 넘나들면 확인 가능)                                         |

**권장: 옵션 B.** `qa` 탭 상단(또는 새 소단면)에 "AI가 대화로 도와드릴 수 있는 것" 같은 작은
안내 블록을 추가해 Tool 5종(통계/통화이력 검색/최다발신/미응답조회/실행취소)을 간단히 나열한다.
데이터는 신규 초경량 엔드포인트(`GET /capabilities/tools`, 정적 배열 반환 — DB 조회조차 불필요)
또는 프론트엔드 상수로도 충분하다(변경 빈도가 매우 낮으므로 API 왕복이 필수는 아님 — 이 부분은
백엔드 API로 할지 프론트 상수로 할지 후속 논의 필요).

## 5. 매뉴얼 §9 축소 범위

**권장: 완전 삭제가 아니라 축소.** §9는 "능력 나열"을 완전히 걷어내고, 다음 두 문장 정도로
줄인다: "이 AI에게 무엇을 물어볼 수 있는지는 상황에 따라 계속 늘어납니다. 가장 정확한 답을
들으시려면 '뭘 할 수 있어?'라고 직접 물어보세요." — 실제 능력 열거는 유형 C(프롬프트 동적
생성)가 전담하고, 매뉴얼은 "직접 물어보라"고 유도하는 메타 안내만 남긴다. 완전 삭제하면
RAG가 이 주제 관련 검색에서 완전히 빈 결과를 낼 수 있어(질문 표현에 따라), 최소한의 안전망으로
축소판을 유지하는 편이 안전하다.

## 종합 권장 설계 (Story 1.17 초안 대비 축소·구체화)

```
[변경 전 계획] 신규 큰 모듈(capabilities.py) + 신규 큰 API + 신규 5번째 탭 + 캐시 계층
[권장 설계]   ① settings_catalog/screen_graph 재사용 포맷터 함수(캐시 없음, self_service_agent.py 내부)
              ② Tool 5종 정적 예시 매핑(작은 상수, tools.py 또는 신규 초소형 모듈)
              ③ 프론트엔드는 신규 탭 대신 기존 qa 탭에 작은 섹션 추가
              ④ 매뉴얼 §9는 축소(삭제 아님)
```

이 축소된 설계는 **기존 인프라(Epic 2 캐시, /catalog·/screen-graph API, 기존 포맷터 함수 패턴)를
최대한 재사용**해 신규 코드량과 회귀 리스크를 크게 낮춘다. 다만 최종 결정은 사용자 판단에
맡기며, 원래 Story 1.17 초안의 "완전한 신규 레지스트리" 방향을 원한다면 그 방향으로도 진행
가능하다(다만 §0에서 지적한 중복 문제는 어떤 방향을 택하든 반드시 인지하고 있어야 한다).
