## 1. 요청 배경

사용자가 다음 3가지를 리서치·리포트 요청함:
1. AI가 대화에서 더 스마트하게 IntelliDecision을 판단하도록 강화할 여지가 있는지.
2. IntelliDecision 유형(현재 A/B/C)을 추가로 확장할 여지가 있는지 — GitHub 등 외부 자료 리서칭.
3. 위 강화를 위해 지식베이스(RAG)를 더 스마트하게 구성할 필요가 있는지.

## 2. 리서치 방법 및 범위 — 중요 사전 확인

**외부 리서치 시도와 한계**: `github_repo`/`github_text_search` 도구로 RasaHQ/rasa,
langchain-ai/langchain, microsoft/BotBuilder-Samples 저장소를 검색 시도했으나, 저장소 인덱싱이
준비되지 않았거나("Github repo index not yet") 검색 결과가 비어 있어(2개 이상의 서로 다른
접근으로 재시도 후에도 실패) 실시간 GitHub 코드 검색은 이번 세션에서 결과를 얻지 못했다.
**추측으로 근거를 지어내지 않기 위해**, 대신 이 저장소에 **이미 존재하는 검증된 리서치 문서**
(`docs/design/INTENT_TAXONOMY_RESEARCH.md`)를 근거로 삼았다 — 이 문서는 Google Dialogflow,
Amazon Alexa(Dialog Acts/표준 Built-in Intents), Rasa(chitchat/fallback/conversation repair),
Just AI Aimylogic(Built-in Intents), 콜센터 인텍트 분류, ISO 24617-2(대화 행위 국제 표준)를
근거로 이미 조사되어 있으며, 실제로 그 결과가 `classify_intent.py`의 일반 고객 응대 경로에
`greeting/farewell/affirm/deny/gratitude/doubt/positive_reaction/negative_reaction/chitchat/
repeat/clarification/help/question/complaint/transfer/out_of_scope/nlu_fallback` 17종으로
이미 구현되어 있음을 코드로 확인했다.

**핵심 발견**: 셀프서비스 세션은 `classify_intent.py`에서 **LLM 분류 자체를 완전히 스킵**하고
(`is_self_service_session=True` → 즉시 `intent="self_service"` 반환, `classify_intent.py`
263행 부근) `self_service_agent_node` 전용 프롬프트로 직행한다. 즉, **위 17종 일반 대화 제어
의도(반복 요청·명확화·정정 등)를 위해 이미 검증된 인프라가 셀프서비스 세션에는 전혀 재사용되지
않고 있다** — self_service_agent.py는 오직 유형 A/B/C(설정 관련 발화 + 포괄적 도움 요청)만
다루며, "다시 말해줘", "그게 아니라" 같은 대화 제어 발화에 대한 명시적 처리가 없다. 이것이
이번 리서치의 핵심 결론이다.

## 3. 현재 셀프서비스 IntelliDecision의 실제 공백 (코드 기준 확인)

`self_service_agent.py`를 직접 재검토한 결과, 유형 A/B/C 외에 아래 상황들이 명시적 규칙 없이
LLM의 "알아서 잘 답하기"에만 의존하고 있음을 확인했다:

| 상황                                                                                            | 현재 처리                                                                                                                      | 실제 리스크                                                                                                         |
| ----------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------- |
| 유형 B 확인 발화 도중 사용자가 **다른 값/도메인으로 정정**("아니 그거 말고 채팅 자동응답 꺼줘") | 항목 12-b에 "아니요/정정 요청이면 다시 확인하고 호출하지 마세요"만 있고, **새 대상으로 재확인하라는 지시가 없음**              | LLM이 "취소"로만 해석하고 새 요청을 별도 turn으로 다시 처리해야 해서 왕복이 늘어남                                  |
| 방금 바꾼 설정을 **되돌리기**("방금 바꾼 거 원래대로 돌려줘")                                   | 관련 Tool 없음. `self_service_config_changes` 이력 테이블은 있지만 **조회만 가능**, 자동 되돌리기 Tool 없음                    | 사용자가 "이전 값이 뭐였는지" 직접 알아야 재요청 가능 — 되돌리기 위한 왕복 대화가 김                                |
| 어떤 도메인인지 **모호**("그거 설정 좀 바꿔줘" — "그거"가 뭔지 불명확)                          | 항목 없음. LLM이 맥락으로 추측하거나 매뉴얼 RAG로 대충 답할 위험                                                               | 잘못된 도메인으로 확인 발화가 나갈 위험(오작동 리스크 — 유형 B는 실제 쓰기까지 이어지므로 특히 중요)                |
| 한 발화에 **여러 설정을 동시 요청**("알림도 끄고 페르소나 설명도 바꿔줘")                       | Tool 루프가 최대 4라운드까지 순차 호출 가능(`_MAX_SELF_SERVICE_TOOL_ROUNDS`)하나, **확인 발화를 어떻게 묶어서 할지 지시 없음** | 항목별로 따로따로 확인 발화가 나가 대화가 불필요하게 길어질 수 있음                                                 |
| 지원하지 않는 기능 요청("결제 플랜 바꿔줘" 등 카탈로그 미등록/제외 목록 항목)                   | Tool 호출 후 `excluded: true` 오류를 안내하는 수준(항목 12-b)                                                                  | **왜** 안 되는지(비가역적 항목이라서 등 이유)를 설명하는 지시가 약함 — 사용자가 "왜 안 돼?"라고 재질문하게 됨       |
| 음성 채널에서 "다시 말해줘"(TTS 재생 실패/못 들음)                                              | 일반 대화 능력에 의존(명시 규칙 없음)                                                                                          | 일반 고객 응대 경로(`repeat` intent, `repeat_response_node`)에는 이미 있는 기능이 셀프서비스에는 없음 — 일관성 결여 |

## 4. 제안 1 — IntelliDecision 신규 유형 후보 (우선순위별)

기존 `INTENT_TAXONOMY_RESEARCH.md`의 그룹 B(반응/피드백)·그룹 C(일상 대화/제어) 개념을
셀프서비스의 "설정 변경 확인→실행" 흐름에 맞게 재해석해 아래 유형을 제안한다. **A/B/C와
동일하게 Tool 호출이 필요 없는 것은 기본 프롬프트에, Tool 호출이 필요한 것은 확장 지시에
배치**하는 기존 설계 원칙을 그대로 따른다.

| 유형  | 명칭                               | 트리거 예시                              | 근거(리서치)                                                      | 구현 난이도                                           | 우선순위                         |
| ----- | ---------------------------------- | ---------------------------------------- | ----------------------------------------------------------------- | ----------------------------------------------------- | -------------------------------- |
| **D** | 정정(Correction)                   | 유형 B 확인 발화 중 "아니 그거 말고 ~"   | Rasa conversation repair의 Correction 패턴                        | 낮음(프롬프트 규칙만 추가)                            | **높음**                         |
| **E** | 실행 취소/롤백(Undo)               | "방금 바꾼 거 되돌려줘", "원래대로 해줘" | 자체 도메인 특화(셀프서비스 변경 이력 테이블 활용)                | 중간(신규 Tool 필요: `undo_last_self_service_change`) | **높음**                         |
| **F** | 모호성 해소(Disambiguation)        | "그거 설정 좀 바꿔줘"(대상 불명확)       | Rasa clarification, ISO 24617-2 Allo-Feedback                     | 낮음(프롬프트 규칙 — 되묻기 지시)                     | **높음**                         |
| **G** | 일괄 처리(Batch)                   | "알림도 끄고 페르소나 설명도 바꿔줘"     | 실무 UX 패턴(다중 슬롯 확인 묶음 처리)                            | 중간(확인 발화 병합 로직)                             | 중간                             |
| **H** | 범위 외 설명(Out-of-scope Explain) | "결제 플랜도 바꿔줘"(제외 목록 항목)     | 콜센터 인텐트 분류의 self-serviceable vs non                      | 낮음(프롬프트 규칙 — 이유 설명 강화)                  | 중간                             |
| **I** | 반복 요청(Repeat, 음성 채널)       | "다시 말해줘", "뭐라고 했지?"            | Alexa `AMAZON.RepeatIntent`, 일반 경로의 `repeat` intent와 일관성 | 낮음(프롬프트 규칙 — 직전 AI 턴 재요약)               | 낮음(음성 채널 비중에 따라 조정) |

**즉시 구현 권장(낮은 난이도·높은 가치)**: D, F, I는 프롬프트 규칙 추가만으로 가능해
Story 1.15와 동일한 패턴(기본 시스템 프롬프트에 추가, LLM 판단 우선, 별도 분류 LLM 호출 없음,
NFR1 지연 예산 보호)으로 다음 세션에 바로 착수 가능하다고 판단한다.

**신규 Tool이 필요한 항목(E)**: `self_service_config_changes` 테이블에 이미 이전값(`old_value`)이
기록되고 있으므로(Story 1.9), "가장 최근 변경 1건을 이전 값으로 되돌리는" Tool은 기존 데이터
구조를 그대로 재사용해 구현 가능하다 — 단, 되돌리기도 "실행성" 발화이므로 유형 B와 동일하게
확인 발화 후 실행하는 원칙을 유지해야 한다(변경을 되돌리는 것도 여전히 쓰기 작업).

**채택하지 않는 방향**: 사용자 감정(불만/좌절) 전용 유형은 이번에는 제안하지 않는다 — 셀프서비스
세션은 이미 HITL을 트리거하지 않는 관리자 세션(Story 1.3 설계 결정)이라, 좌절 감지 후 갈 수 있는
목적지가 마땅치 않고(사람 개입 큐가 없음), 잘못 판단 시 불필요하게 사과만 반복하는 리스크가
더 크다고 판단했다(NFR1 지연 예산·환각 방지 원칙에 비추어 낮은 ROI).

## 5. 제안 2 — 지식베이스(RAG) 스마트 구성 개선안

Story 1.15에서 실제로 겪은 문제(매뉴얼 §9가 "향후 지원되는 기능"이라는 미래형 서술로 방치되어
있던 stale 콘텐츠)를 근본적으로 재발 방지하려면, **사람이 수작업으로 매뉴얼 텍스트를 유지하는
현재 구조 자체가 구조적 위험**이다. Epic 2(Story 2.1~2.8)가 이미 "설정 카탈로그/Screen Graph를
DB 기반 동적 메타데이터로 전환"한 것과 동일한 철학을 매뉴얼 §9(능력 소개)에도 적용할 것을
제안한다.

### 5.1 문제의 근본 구조

```
[현재] settings_catalog.py(7개 도메인, 코드) ─┐
       screen_graph.py(화면 정보, 코드)        ├─ 서로 무관 ─→ 사람이 수작업으로
       tools.py(SELF_SERVICE_TOOLS, 코드)     ─┘             self-service-manual-content.md §9를
                                                              별도로 작성 → 코드가 바뀌어도
                                                              §9는 자동으로 안 바뀜(stale 위험)
```

### 5.2 제안: "능력 레지스트리(Capability Registry)" 도입

`settings_catalog.list_domains()`/`get_domain_schema()`, `screen_graph.list_all_screens()`,
`tools.SELF_SERVICE_TOOLS`를 조합해 **실행 시점에 동적으로 능력 요약 텍스트를 생성**하는
경량 함수(예: `self_service/capabilities.py::describe_dynamic_capabilities()`)를 신설한다.

- 유형 C(도움 요청) 응답에 사용하는 카테고리 목록을 프롬프트에 정적으로 하드코딩하는 대신,
  이 함수가 생성한 **실시간 텍스트**를 시스템 프롬프트 변수로 주입한다(현재 `rag_context`,
  `onboarding_section`처럼 `{capability_section}` 변수 추가).
- 이렇게 하면 Epic 2의 카탈로그 핫 리로드(FR20 — 서버 재시작 없이 즉시 반영)가 적용될 때
  **능력 안내 문구도 자동으로 최신 상태를 유지**한다 — 매뉴얼 §9를 사람이 매번 갱신할 필요가
  구조적으로 사라진다(Story 1.15에서 발견된 stale 문제의 재발 방지).
- 매뉴얼 §9는 "동적 생성 텍스트로 대체되지 않는 나머지 설명"(예: 셀프서비스 모드 진입 방법
  등 정적인 안내)만 남기고, 능력 목록 자체는 레지스트리가 단일 진실 소스(Single Source of
  Truth)가 되도록 역할을 분리한다.

### 5.3 RAG 검색 자체의 개선 여지 (참고, 이번 범위는 아님)

- **쿼리 재작성(Query Rewriting) 부재**: 메인 파이프라인은 `rewrite_query` 노드가 있으나
  셀프서비스 RAG(`self_service/rag.py`)는 사용자 발화를 그대로 검색어로 사용한다. "뭐 할 수
  있어?"처럼 짧고 모호한 질문은 임베딩 유사도가 낮게 나올 수 있어(Story 1.15에서 실제로 우려한
  지점), 셀프서비스 전용 경량 쿼리 확장(예: "이 서비스에서 할 수 있는 기능·능력·사용법"으로
  키워드 보강)을 고려할 수 있다. 다만 이번 리서치에서는 유형 C 프롬프트 규칙(Story 1.15)이
  이미 RAG 성패와 무관하게 항상 동작하도록 설계되어 있어 **긴급도는 낮음**으로 판단한다.
- **메타데이터 태깅 확장**: `manual_indexer.py`의 `{domain: xxx}` 태그(Story 2.8)를 반복/정정/
  모호성 해소 같은 "대화 제어형 Q&A"에도 별도 태그(예: `{type: repair}`)로 구분해 두면, 향후
  유형 D/E/F 관련 매뉴얼 콘텐츠가 늘어날 때 검색 필터링에 활용할 수 있다(현재는 setting
  도메인 태그만 존재).
