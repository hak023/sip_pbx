## 1. Story 1.14 — persona 등 문자열 값 필드 Gemini 빈 응답: 근본 원인 수정

### 배경

Epic 2 통합 QA(Story 2.7)에서 발견한 결함③(persona.description 등 문자열 값 필드의 확인→실행
2턴 흐름에서 Gemini가 6/6회 빈 candidate를 반환)에 대한 후속 조사 Story.

### 1차 시도(재시도 완화책) 및 사용자 피드백

최초에는 "top_k=1(그리디 디코딩)이라 동일 입력 재시도는 항상 같은 결과가 나온다"는 결정론적
실패 가설을 세웠다. 그러나 `logs/app.log`를 재분석한 결과, 동일 `call_id` 내에서 재시도 로그
개수가 3회 미만인 사례(즉 재시도 도중 회복된 사례)가 다수 발견되어 **이 가설은 기각**했다.
실패는 결정론적이 아니라 확률적이라는 결론에 따라 재시도 횟수를 2→4로 늘리는 완화책을 우선
구현했는데, **사용자가 "재시도로 증상만 가리지 말고 원천적인 실패 원인을 찾아 해결하라"고
정확히 지적**해, 완화책은 방어망으로 유지한 채 근본 원인 조사를 이어갔다.

### 근본 원인 규명 및 수정 (이번 리포트의 핵심)

`update_self_service_setting` 도구의 `value` 파라미터는 도메인마다 실제 타입이 제각각(불리언/
enum 문자열/자유 문자열)이라 Python 함수 시그니처에 `value: Any`로 선언되어 있다. 실제
Pydantic이 생성하는 JSON Schema를 직접 출력해 확인한 결과, `value` 필드는
`{"title": "Value"}`처럼 **`type` 키 자체가 없었다**.

`booking_gemini_fc.py::_json_schema_to_glm_schema()`(JSON Schema → Gemini `glm.Schema` 변환기)의
기존 코드:

```python
if st in ("object", "") or "properties" in schema:
    return glm.Schema(type_=glm.Type.OBJECT, ...)
```

`st = schema.get("type") or ""`이므로 "명시적 object 선언"과 "타입 정보 자체가 없음(Any)"을
**똑같이 취급**해, `value` 필드를 **프로퍼티 0개짜리 OBJECT**로 Gemini에 잘못 선언하고 있었다.
즉 Gemini function-calling 모델은 "`value`는 반드시 빈 객체여야 한다"는 스키마를 받았는데,
실제로는 문자열/불리언 값을 채워야 하는 상황이었다. 이 스키마 불일치가 짧은 값(`true`/`false`,
`"none"`)에서는 우연히 통과되고 긴 자유 문자열에서는 제약 디코딩이 막혀 완전히 빈 candidate로
이어졌다고 강하게 추정된다 — 관측된 모든 증거(도메인이 아니라 값 타입과 상관관계, 확률적이지만
문자열 값에서 압도적으로 높은 실패율, Epic 2와 무관)와 정합적이다.

**수정**: `st in ("object", "")` 분기를 `st == "object" or (st == "" and "properties" in schema)`로
좁혀, 타입 정보가 없고 `properties`도 없는 필드는 OBJECT가 아니라 STRING으로 변환하도록 했다
(Gemini 스키마에 진짜 "Any" 타입이 없으므로 가장 관대한 원시 타입인 문자열을 사용 — 기존
`tools.py::_coerce_value()`가 이미 문자열→불리언 등 후처리를 담당하므로 호환된다). 실제
`update_self_service_setting_tool`을 `_langchain_tools_to_glm_tool()`로 변환해 `value` 파라미터
타입이 STRING(이전: OBJECT)으로 바뀌었음을 직접 확인했다.

  메시지)으로 대응 가능한 수준으로 판단한다.

## 2. Story 2.8 — 매뉴얼-도메인 매핑 동적화

### 구현 내용

1. `manual_indexer.py::_SECTION_PATTERN`에 선택적 `domain_tag` 그룹을 추가해
   `## N. 제목 {domain: xxx}` 형식의 명시적 태그를 인식하도록 정규식을 확장했다.
2. `parse_manual_qa_with_meta()`가 태그를 우선 사용하고, 태그가 없는 섹션은 기존
   `_section_title_to_domain()` 키워드 매칭으로 폴백하도록 수정(점진적 마이그레이션 허용).
3. `docs/product/self-service-manual-content.md`의 9개 섹션(1~9, 부록 제외) 전체에 태그를
   추가했다. 각 태그 값은 기존 키워드 매칭이 산출하던 도메인과 동일하게 맞춰 회귀를 방지했다.

### 검증

- 신규 단위 테스트 5건(`TestParseManualQaWithMetaDomainTag`) — 태그 인식, 폴백, 태그 우선순위,
  미매칭, 혼합(일부만 태그) 케이스 모두 검증.
- 실제 매뉴얼 파일을 `load_manual_qa_with_meta()`로 직접 파싱해 52건 Q&A 전체가 그대로 추출되고
  (개수 회귀 없음), 9개 섹션 모두 올바른 도메인으로 매핑되며, 섹션 제목에서 태그 문자열이 깔끔히
  제거됨을 확인(사용자/프론트엔드에 태그 문자열이 노출되지 않음).
- 태그 값이 기존 키워드 매칭 결과와 동일해, 이미 ChromaDB에 색인된 기존 데이터와도 재색인 없이
  일관성이 유지된다(IV1 충족).
