# Story 1.20 스파이크 검증 — IntelliDecision 판단 근거 캡처 방식 결정

**작성일**: 2026-07-29
**작업 유형**: 스파이크 검증(실제 Gemini API 호출, 프로덕션 코드 미반영)

## 관련 문서

- [1.20.intellidecision-rationale-capture-spike.story.md](../../stories/1.20.intellidecision-rationale-capture-spike.story.md)
- `scripts/spike_intellidecision_rationale_capture.py`(신규, 독립 스크립트)

## 검증 방법

`scripts/spike_intellidecision_rationale_capture.py`로 3개 후보 방식을 실제 `gemini-2.5-flash`
API 호출로 검증했다(`config.yaml`의 운영 모델과 동일). 대표 발화 3종(탐색성 A/실행성 B/도움요청 C)을
사용했다.

## 결과

### 후보 (a) 구조화 출력(`response_schema`) + FunctionCall 동시 요청

**3/3 즉시 실패 — API 레벨에서 명시적으로 차단됨**:

```
ClientError: 400 INVALID_ARGUMENT. {'error': {'code': 400,
'message': "Function calling with a response mime type: 'application/json' is unsupported",
'status': 'INVALID_ARGUMENT'}}
```

Gemini API가 `tools`(FunctionDeclaration)와 `response_mime_type=application/json`
(`response_schema`)을 같은 요청에 함께 지정하는 것을 **아예 지원하지 않는다**는 사실을 실제
호출로 확인했다(추측이 아니라 API 자체의 명시적 오류 메시지). 이 방식은 **기각**한다.

### 후보 (b) 센티널 태그 후행 파싱

**15회 시도 중 성공 0회(0%)** — 모델이 센티널 태그(`<<INTELLIDECISION:{...}>>`) 지시를
한 번도 따르지 않았다(응답 텍스트에 태그 자체가 아예 나타나지 않음, 태그 유출도 0건이었으나
이는 애초에 태그를 생성하지 않았기 때문). 이는 2026-07-29에 근본 수정한 "conversation_history
오염발 메타 JSON 유출" 결함 조사 당시 확인된 것과 같은 클래스의 문제 — **LLM이 부가 지시(원 응답
+ 추가 형식)를 안정적으로 따르지 않는다**는 것을 실측으로 재확인했다. 신뢰성이 0%로 실용
불가능한 수준이라 **기각**한다(프롬프트 튜닝으로 개선 여지가 있을 수 있으나, 이 정도로 낮은
초기 성공률은 투명성 기능의 신뢰 기반으로 삼기에 부적합하다고 판단).

### 후보 (c) 경량 별도 분류 호출

**3/3 정상 동작**, 추가 지연 실측:

| 발화        | 1차 응답 생성 | 2차 분류 호출(추가) | 추가 비율 |
| ----------- | ------------- | ------------------- | --------- |
| 탐색성(A)   | 1.33s         | 0.94s               | 41%       |
| 실행성(B)   | 1.70s         | 0.85s               | 33%       |
| 도움요청(C) | 1.42s         | 0.66s               | 32%       |

3개 유일하게 기술적으로 동작하는 방식이지만, **동기적으로(await) 연결하면** 사용자 응답 지연이
평균 약 0.8초(30~40%) 늘어나 NFR6(추가 왕복 지연 최소화)를 직접적으로 위반한다.

## 최종 결정

**후보 (c)를 채택하되, 동기 호출이 아니라 "비동기 백그라운드 실행(fire-and-forget)"으로
변형해 적용한다.**

- 사용자에게 보여줄 응답이 생성·전송된 **이후**, `asyncio.create_task()`로 분류 호출을
  백그라운드에서 실행하고 결과가 나오면 로그·DB에 기록한다.
- 사용자 응답 경로는 이 백그라운드 태스크를 **전혀 기다리지 않는다** — 따라서 체감 지연은
  0에 가깝다(NFR6 충족). 백그라운드 태스크가 실패(타임아웃, 예외)해도 사용자에게 이미 전달된
  응답에는 영향이 없다(FR30 요구사항 자동 충족).
- 트레이드오프: 판단 근거가 사용자 응답보다 **약 0.7~0.9초 늦게** 기록된다(프론트엔드 "최근
  판단 이력"에는 실시간이 아니라 근사 실시간으로 반영됨) — 투명성 기능의 성격상 수용 가능한
  지연으로 판단(실시간 확인 요구사항이 PRD에 명시되어 있지 않음).
- (a)/(b)는 코드베이스에 반영하지 않는다.

## Story 1.21 반영 필요 사항

- `decision_rationale.py`는 "응답 전송 후 비동기 백그라운드 분류 호출" 구조로 구현한다
  (`asyncio.create_task` + 예외 흡수 wrapper).
- 분류 호출 프롬프트는 이번 스파이크의 "유형 목록 + 발화 + AI 응답 → 유형 코드 1글자" 패턴을
  재사용하되, Story 1.21에서 `reasoning_summary`(근거 요약)까지 함께 받도록 프롬프트를
  확장한다.
- 분류 실패(빈 응답, 파싱 실패)는 `matched_type=unknown`으로 기록한다(AC2 요구사항).
