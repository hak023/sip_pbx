## 문제 요약

`intellidecision_policy.py`(Story 1.18)는 유형 A~I의 응대 전략(Tool 필요 여부 등)만 데이터화되어
있었고, "이 유형일 때 RAG 검색이 어떻게 매칭될 예정인지"는 코드에 암묵적으로만 존재해 운영자가
대화 실행 전에 예측할 방법이 없었다.

## 수정 내용

1. **`intellidecision_policy.py`**: `IntentTypeSpec`에 `rag_enabled`/`rag_source_scope`/
   `rag_strategy_hint` 필드 추가, 유형 A~I 9종 전체에 값 지정(A/C는 `rag_enabled=True`,
   D/E/F/H/I는 `rag_enabled=False`·`rag_strategy_hint="none"` — 실제 코드가 신규 정보 없이
   기존 컨텍스트·이력만으로 처리하는 유형).
2. **`settings_ai_assistant.py`**: `IntentTypeOut`/`GET /intellidecision-policy` 응답에 3개 필드
   노출 — 사전 예측을 API로 확인 가능.
3. **`self_service_agent.py`**: 기존 RAG 검색 완료 지점에 `self_service_rag_matched` structlog
   이벤트(검색 쿼리·매칭 문서 ID·점수·related_domain) 추가 — 매칭 결과가 있을 때만 발생, 판단/
   응답 로직은 전혀 변경하지 않음(순수 관측 로깅).
4. **프론트엔드**: "AI 의사결정 로직" 탭의 유형 카드에 `RAG: vector`/`RAG: hybrid`/`RAG 미사용`
   배지와 매칭 범위(`rag_source_scope`) 문구 추가.

## 중요 설계 한계 (다음 세션 IV 검증 시 확인 필요)

현재 `self_service_agent_node`는 IntelliDecision 유형이 확정되기 전에 이미 RAG 검색을 실행하는
구조다. 따라서 `rag_enabled=False`는 "코드가 검색 자체를 건너뛴다"는 뜻이 아니라 "이 유형에서는
검색 결과가 응답에 실질적으로 반영되지 않는다"는 설계 의도의 사전 예측이다. 실서버 IV 검증
시 유형 E/D 발화에서도 `self_service_rag_matched` 로그가 남는지 관찰해 이 가정을 재검증할 것을
권고한다(Story 1.24 Dev Notes에 동일 내용 기록).
