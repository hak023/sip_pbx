**작성일**: 2026-07-20
**버전**: 1.1 (Epic 2 Story 2.1~2.7 Branch L 추가 및 결함③ 반영, 2026-07-21)
**상태**: 실행 완료(2026-07-21, Epic 1 + Epic 2 통합 실서버 검증)
**대상**: Story 1.1~1.13 (Epic 1) + Story 2.1~2.7 (Epic 2: 설정 카탈로그/Screen Graph 동적화)
**테스트 방식**: `POST /api/self-service/test/converse` — **STT 이후 ~ TTS 이전** 구간
(`ConversationAgent.process_utterance`)을 실제 LLM·RAG·Tool-calling까지 포함해 텍스트
입력→텍스트 출력으로 그대로 실행한다. 음성 파이프라인의 STT/TTS 자체는 검증 대상이 아니며,
그 사이의 "이해→검색/실행→응답 생성" 로직만 검증한다(기존 QA 방식과 동일 원칙 유지).

## 0. 원칙

- 자연어 입력 하나당 케이스 하나. **입력문구 → 실제 출력문구(테스트 후 기록) → tool_trace** 3가지를
  모두 기록해 기대문구/기대 Tool 호출과 대조한다.
- 판정은 "무엇을 답했는가"뿐 아니라 **"어떤 Tool을 호출했는가"**(`tool_trace`의 `self_service_tool_start`/
  `done`, `self_service_auto_config_applied`/`rejected` 등)까지 포함한다.
- 쓰기(Story 1.8) 테스트는 실제로 설정을 변경한다. QA 전용 owner(9001/9002/9003)로만 실행한다.
- 핵심 케이스는 `logs/call_data_record_YYYYMMDD.log` 원시 로그와 `call_id`로 교차검증한다(API
  응답 자체의 조작/누락 가능성을 배제하기 위함).
- **단순 단발 질의응답 외에, 여러 Tool이 한 세션에서 이어지는 다중 턴 연계 시나리오(Branch K)를
  반드시 포함한다** — 실제 사용자는 한 통화 안에서 여러 목적을 순차적으로 요청하기 때문이다.

  `POST /api/client-log` 실패가 반복 기록되고, `/dashboard`는 "연결 중…" 상태가 계속 유지되는
  것으로 보아 **실시간 WebSocket(Socket.IO, 포트 8001) 연결이 근본적으로 수립되지 못하고 있다**.
  포트 자체는 열려 있고(`Test-NetConnection` 성공) 백엔드도 `python-socketio` `AsyncServer`로
  정상 구현되어 있어(`src/websocket/server.py`), 포트 미기동 문제는 아니다 — 인증 토큰 거부,
  handshake 프로토콜 불일치, 또는 별도 `ws-server`(Node.js, `sip-pbx/ws-server/`) 프로세스와의
  충돌 등 좀 더 깊은 원인이 있을 것으로 추정되나 **이번 세션에서는 확정하지 못했다**(self_service
  Epic 범위를 벗어나는 별도 플랫폼 이슈로 판단, 별도 조사 필요).
- **자동화 도구 한계 가능성**: Playwright의 클릭 "안정성(stable)" 판정은 실제 사용자 클릭보다
  훨씬 엄격하다(연속 프레임 동안 요소 위치가 변하지 않아야 함). WS 재연결 시도가 컴포넌트를
  자주 리렌더링시킨다면 실제 사용자 클릭에는 영향이 없어도 자동화 클릭만 실패할 수 있다 —
  즉 **실사용자에게 실제로 클릭이 안 되는 문제인지는 이번 조사만으로 확정할 수 없다**(수동
  브라우저 테스트로 별도 확인 필요).
- **Story 1.11/1.12 자체 영향**: 없음. 백엔드 Screen Graph API(I1)와 `self_service_agent_node`
  연계(I2)는 이 문제와 무관하게 정상 동작함을 별도로 확인했다.
- **후속 조치 필요(self_service Epic 범위 밖, 별도 트랙 권장)**: WebSocket 인증/handshake 흐름
  점검, 그리고 실사용자 관점의 수동 클릭 테스트로 실제 영향 여부 확인.

## 3-1. 추가 개선: 대화 안내에서 API/URL 경로 대신 메인화면 클릭 경로 사용 (2026-07-20)

**배경**: Branch C2/H1/H4 등의 실측 응답을 보면 AI가 "/settings/chat-relay 화면에서", "설정 >
착신 제어에서" 등 **raw 프론트엔드 라우트를 그대로 대화에 노출**하고 있었다. 전화·문자로 대화
중인 사용자는 URL/API 경로를 알 수도, 알 필요도 없다 — "메인화면에서 어떻게 이동해야 하는지"를
설명해야 한다.

**원인**: `screen_graph.py::describe_screen_for_conversation()`이 `entry.route`(예:
`/settings/chat-relay`)를 그대로 "화면 위치: {route}" 형태로 시스템 프롬프트에 주입하고 있었다.

**조치**: `ScreenEntry`에 `nav_hint` 필드를 신규 추가하고, 실제 프론트엔드 메뉴 구조
(`frontend/components/AppHeader.tsx::SETTINGS_NAV`/`MAIN_NAV`)를 조사해 도메인별로 **메인화면
기준 클릭 경로**를 등록했다(예: ai-escalation → "화면 상단 메뉴의 '설정' 버튼을 누른 뒤
'조직·채팅' 항목의 'AI 에스컬레이션'을 선택하세요"). `describe_screen_for_conversation()`이
`route` 대신 `nav_hint`를 사용하도록 수정했고, `route`는 프론트엔드 "화면 안내" 탭의 클릭
이동용으로만 남겨두었다(그 화면은 사람이 직접 보고 클릭하는 시각적 UI이므로 raw route가
적절함 — 대화체 안내와는 성격이 다름).

**검증 상태**: 단위 테스트(`test_self_service_screen_graph.py`) 갱신 후 전체 self_service 테스트
스위트 회귀 없음 확인. **2026-07-20 서버 재시작 후 실서버로 검증 완료**: owner 9003으로 "채팅
자동응답 설정 좀 보여줘"를 질의한 결과, 응답이 "이 설정은 '설정' 메뉴에서 '조직·채팅' 항목의
'채팅·SIP MESSAGE'를 선택하시면 확인하고 변경하실 수 있습니다"로 나와 raw route(`/settings/chat-relay`)
노출 없이 메인화면 기준 클릭 경로만 언급됨을 확인했다.
