## Story

**As a** AI 도우미의 실제 응대 결과를 확인하려는 테넌트 관리자,
**I want** "최근 판단 이력" 목록의 각 항목이 유형 판정 → RAG 검색 → hop 확장 → 화면안내/Tool 판단 →
응답 생성으로 이어지는 순서도(flowchart)로 표시되기를,
**so that** 시뮬레이션 없이 프론트엔드에서 실제 대화 결과만 보고도 AI가 왜 그렇게 응대했는지
이해할 수 있다.

## Acceptance Criteria

1. "최근 판단 이력" 섹션(Story 1.22 UI)의 각 이력 항목을 펼치면, 해당 실제 대화 턴에 대한
   flowchart가 표시된다 — 단계: ①유형 판정(A~I, `self_service_decision_log`의 실제 판정 결과)
   ②RAG vector 검색(실제 매칭 근거) ③`knowledge_graph.traverse_graph()` hop 확장(실제 발생한
   경우만) ④화면안내/Tool 필요 여부 판단(실제 판단 결과) ⑤응답 생성(실제 응답 텍스트).
2. flowchart에 표시되는 모든 데이터는 `self_service_decision_log`/`call_data_record`에 실제
   기록된 값만 사용한다 — 시뮬레이션 API(`knowledge_base_simulate.py`)는 이 화면에서 호출하지
   않는다(NFR10). 특정 단계 데이터가 로그에 없으면 "정보 없음"으로 표시하고 임의로 채우지 않는다.
2-1. 데이터 소스는 Story 1.39에서 신설되는 실제 채팅 패널(`GlobalSmsDock` 상시 노출)을 통해
   발생한 대화도 포함한다 — 즉, 관리자가 본인에게 메시지를 보내 테스트한 대화도 이 순서도에
   그대로 나타나야 한다.
3. RAG vector 검색 결과와 hop 확장 결과, 화면안내 hop 활용 여부를 각각 구분된 색상/구간으로
   표시한다(기존 AC 계승).
4. 유형 C(하이브리드 다중 도메인) 이력은 병렬 분기 형태로 표시된다(Story 1.33 AC3 계승).
5. 조회 성능: 이력 목록 API 응답에 flowchart 렌더링에 필요한 필드가 포함되어 있어야 하며, 항목당
   추가 API 호출이 필요하다면 N+1 호출을 피하도록 설계한다.
