## Story

**As a** AI 도우미의 실제 응대 결과를 확인하려는 테넌트 관리자,
**I want** 채널(음성 통화 vs 채팅)에 맞는 올바른 기준으로 묶인 대화 세션 안에서, 여러 차례
주고받은 발화들이 유형(A~I) 사이를 어떻게 옮겨 다녔는지, 각 턴에서 RAG/hop/화면안내/Tool
판단이 어떻게 이어졌는지 하나의 순서도로 이어붙여 보여주기를,
**so that** 단발성 질문-답변 하나만 봐서는 알 수 없는 "대화를 통해 사용자 의도를 좁혀가는"
IntelliDecision의 실제 동작 방식을, 통화든 문자든 관계없이 프론트엔드에서 이해할 수 있다.

## Acceptance Criteria

1. **세션 그룹핑 키는 채널에 따라 다르게 정의한다**(단일 call_id 그룹핑은 채팅에서 성립하지
   않음을 반영):
   - 음성 통화: 기존과 동일하게 `call_id` 하나 = 세션 하나(통화 시작~종료까지 자연스럽게 여러
     턴이 동일 call_id를 공유하므로 별도 조치 불필요).
   - 채팅/SIP MESSAGE: `call_id`는 메시지(트랜잭션) 1건마다 새로 발급되므로 세션 키로 쓸 수
     없다. 대신 **`(owner, caller_number)` 조합 + 시간 윈도우**(예: 마지막 턴으로부터 N분
     이내 후속 메시지는 같은 세션으로 간주, N은 튜닝 가능한 설정값)로 세션을 정의한다.
2. **`self_service_decision_log`에 `caller_number`(또는 `thread_id`) 컬럼을 신규 추가**한다 —
   현재 이 테이블은 채팅 세션을 그룹핑할 수 있는 필드 자체가 없으므로, 이 Story의 세션 그룹핑
   기능이 성립하려면 선행 스키마 변경이 반드시 필요하다(`self_service/decision_rationale.py`의
   캡처 호출부에 caller_number 전달 배선 포함).
3. "최근 판단 이력" 섹션은 개별 턴(Q&A 1건) 목록이 아니라 **위 1번 기준으로 정의된 세션 단위**로
   재구성된다 — 세션 하나를 펼치면, 그 세션에 속한 턴들이 시간 순서대로 이어진 flowchart가
   표시된다(턴이 1개뿐인 세션도 지원하되, 여러 턴 세션이 이 Story의 핵심 시나리오).
4. 각 턴은 개별 노드가 아니라 **①유형 판정(A~I) ②RAG 검색 ③hop 확장 ④화면안내/Tool 판단
   ⑤응답 생성**의 5단계 서브플로우로 표시하고, 턴과 턴 사이는 "유형 전환 엣지"로 연결한다 —
   예: 턴1(유형 A: 탐색) → 턴2(유형 C: 포괄적 도움) → 턴3(유형 E: 실행 확정)처럼 유형이 이동한
   경로 자체가 시각적으로 드러나야 한다.
5. 유형이 턴 간에 바뀌지 않고 유지된 구간(같은 유형 내에서 후속 질문)과, 실제로 다른 유형으로
   전환된 구간을 시각적으로 구분한다(예: 유지 구간은 얇은 연결선, 전환 구간은 강조된 화살표).
6. flowchart에 표시되는 모든 데이터는 `self_service_decision_log`/`call_data_record`에 실제
   기록된 값만 사용한다 — 시뮬레이션 API(`knowledge_base_simulate.py`)는 이 화면에서 호출하지
   않는다(NFR10). 특정 턴/단계 데이터가 로그에 없으면 "정보 없음"으로 표시하고 임의로 채우지 않는다.
7. 데이터 소스는 Story 1.39에서 신설되는 실제 채팅 패널(`GlobalSmsDock` 상시 노출)을 통해 발생한
   멀티턴 대화도 포함한다 — 관리자가 본인에게 여러 차례 메시지를 주고받으며 만든 세션(같은
   caller_number+시간 윈도우 내)이 이 세션 단위 flowchart에 그대로 나타나야 한다.
8. RAG vector 검색 결과와 hop 확장 결과, 화면안내 hop 활용 여부는 각 턴의 서브플로우 내에서
   구분된 색상/구간으로 표시한다(기존 AC 계승).
9. 유형 C(하이브리드 다중 도메인) 턴은 해당 턴의 서브플로우 내에서 병렬 분기 형태로 표시된다
   (Story 1.33 AC3 계승).
10. 조회 성능: 세션 목록 조회 시 그룹핑된 요약(턴 수, 유형 전환 경로 요약, 최종 유형)만 먼저
   보여주고, 특정 세션을 펼칠 때만 해당 세션의 전체 턴 상세를 조회하는 2단계 로딩으로
   설계한다 — 세션 수가 많아져도 목록 조회가 느려지지 않도록 한다.

## Dev Notes

- 이 Story는 시뮬레이터를 전제로 하지 않는다 — Story 1.32의 `hop_path` 직렬화 로직 자체는
  재사용 가능하지만, 데이터 출처는 반드시 실제 대화 로그여야 한다.
- **핵심 설계 포인트(2026-08-05 재수정)**: "한 건의 질의/응답"이 아니라 "하나의 세션 안에서
  유형이 이동하는 과정"이 이 Story가 보여줘야 하는 핵심 가치다. 단, 세션의 정의 자체가
  채널마다 다르다 — **음성은 call_id가 이미 세션 경계이지만, 채팅/MESSAGE는 call_id가
  트랜잭션 단위라 세션 경계가 될 수 없다.** 이 구분을 놓치면 채팅 세션에서 이 Story의 목적이
  다시 무의미해지므로, Task 1(스키마)·Task 2(채널별 그룹핑 로직)를 최우선으로 검증할 것.
- 시간 윈도우 임계값(채팅 세션 경계 판단)은 실측 데이터(실제 사용자가 얼마나 빨리/느리게 후속
  메시지를 보내는지) 없이 정하기 어려우므로, 1차로는 넉넉한 기본값(예: 30분)으로 시작하고
  IV 검증 중 조정 여지를 열어둘 것 — 과도하게 좁으면 정상 대화도 여러 세션으로 쪼개지고,
  과도하게 넓으면 관계없는 대화가 한 세션으로 합쳐질 위험이 있다.
- 신규 npm 의존성 도입 전, Story 1.18의 순수 SVG 접근이 이번에도 통하는지 먼저 검토할 것 — 다만
  이번엔 노드 수가 "유형 9개 고정"이 아니라 "세션당 턴 수 × 5단계"로 가변적이므로, 턴 수가 많은
  세션에서도 레이아웃이 무너지지 않는지(가로 스크롤/접기 등) 별도 검토가 필요하다.
