## Story

**As a** AI 도우미의 실제 응대 결과를 확인하려는 테넌트 관리자,
**I want** 한 번의 대화 세션(call_id) 안에서 여러 차례 주고받은 발화들이 유형(A~I) 사이를 어떻게
옮겨 다녔는지, 각 턴에서 RAG/hop/화면안내/Tool 판단이 어떻게 이어졌는지 하나의 순서도로 이어붙여
보여주기를,
**so that** 단발성 질문-답변 하나만 봐서는 알 수 없는 "대화를 통해 사용자 의도를 좁혀가는"
IntelliDecision의 실제 동작 방식을 프론트엔드에서 이해할 수 있다.

## Acceptance Criteria

1. "최근 판단 이력" 섹션은 개별 턴(Q&A 1건) 목록이 아니라 **동일 call_id로 묶인 세션 단위**로
   재구성된다 — 세션 하나를 펼치면, 그 세션에 속한 턴들이 시간 순서대로 이어진 flowchart가
   표시된다(턴이 1개뿐인 세션도 지원하되, 여러 턴 세션이 이 Story의 핵심 시나리오).
2. 각 턴은 개별 노드가 아니라 **①유형 판정(A~I) ②RAG 검색 ③hop 확장 ④화면안내/Tool 판단
   ⑤응답 생성**의 5단계 서브플로우로 표시하고, 턴과 턴 사이는 "유형 전환 엣지"로 연결한다 —
   예: 턴1(유형 A: 탐색) → 턴2(유형 C: 포괄적 도움) → 턴3(유형 E: 실행 확정)처럼 유형이 이동한
   경로 자체가 시각적으로 드러나야 한다.
3. 유형이 턴 간에 바뀌지 않고 유지된 구간(같은 유형 내에서 후속 질문)과, 실제로 다른 유형으로
   전환된 구간을 시각적으로 구분한다(예: 유지 구간은 얇은 연결선, 전환 구간은 강조된 화살표).
4. flowchart에 표시되는 모든 데이터는 `self_service_decision_log`/`call_data_record`에 실제
   기록된 값만 사용한다 — 시뮬레이션 API(`knowledge_base_simulate.py`)는 이 화면에서 호출하지
   않는다(NFR10). 특정 턴/단계 데이터가 로그에 없으면 "정보 없음"으로 표시하고 임의로 채우지 않는다.
5. 데이터 소스는 Story 1.39에서 신설되는 실제 채팅 패널(`GlobalSmsDock` 상시 노출)을 통해 발생한
   멀티턴 대화도 포함한다 — 관리자가 본인에게 여러 차례 메시지를 주고받으며 만든 세션이 이 세션
   단위 flowchart에 그대로 나타나야 한다.
6. RAG vector 검색 결과와 hop 확장 결과, 화면안내 hop 활용 여부는 각 턴의 서브플로우 내에서
   구분된 색상/구간으로 표시한다(기존 AC 계승).
7. 유형 C(하이브리드 다중 도메인) 턴은 해당 턴의 서브플로우 내에서 병렬 분기 형태로 표시된다
   (Story 1.33 AC3 계승).
8. 조회 성능: 세션 목록 조회 시 call_id로 그룹핑된 요약(턴 수, 유형 전환 경로 요약, 최종 유형)만
   먼저 보여주고, 특정 세션을 펼칠 때만 해당 세션의 전체 턴 상세를 조회하는 2단계 로딩으로
   설계한다 — 세션 수가 많아져도 목록 조회가 느려지지 않도록 한다.
