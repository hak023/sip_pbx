# Story 1.6: 설정 조회 Tool (읽기 전용, 전체 도메인)

## Status

Done(2026-07-20/21 `master-qa.md` Branch C로 실서버 검증까지 완료)

## Story

**As a** 테넌트 관리자,
**I want** "지금 알림 설정이 어떻게 되어 있어?"처럼 물어보면 현재 값을 답변받기를,
**so that** 대시보드에 접속하지 않고도 현재 상태를 확인할 수 있다.

## Acceptance Criteria

1. `get_self_service_settings(domain)` Tool이 **설정 카탈로그(Story 1.4)에 등록된 모든 도메인**의 현재 값을 조회해 구조화된 값을 반환한다(카탈로그 조회 함수를 LangGraph Tool로 노출하는 얇은 래퍼).
2. 카탈로그에 등록되지 않은 도메인/필드 조회 요청 시 "확인해드릴 수 없는 항목"으로 안내한다.
3. 조회 결과는 실제 설정값과 100% 일치한다(프론트엔드와 동일 데이터 소스 사용, FR10).

### Integration Verification

- **IV1**: 이 Tool이 Story 1.4의 카탈로그 조회 함수만 호출하며 별도 조회 로직을 중복 구현하지 않는다.

## ⚠️ 구현 중 발견된 사실 — Story 1.2/1.5에는 아직 실제 Tool-calling 루프가 없었음

Dev Notes와 Task 2는 "Story 1.2/1.5에서 이미 구성된 LLM+Tool 루프"가 있다고 가정했으나, 실제로 Story 1.2/1.3/1.5의 `self_service_agent_node`는 `bind_tools()` 없이 프롬프트 텍스트만으로 LLM을 호출하는 구조였다(RAG 참고 정보와 온보딩 체크리스트도 모두 프롬프트 삽입으로만 전달되었음). 본 Story에서 **이 노드에 직접 첫 실제 Tool-calling 루프를 도입**했다:

- `booking_agent_node`와 달리 Gemini 네이티브 function calling 폴백은 두지 않았다 — 설정 조회는 읽기 전용이라 위험도가 낮고, `bind_tools` 미지원/실패 시 기존 프롬프트 기반 플로우(Story 1.2/1.3/1.5)로 그대로 폴백하면 충분하다고 판단했다(스코프 축소, Dev 판단).
- 이 단순화된 루프는 Story 1.7/1.8이 실제 설정 변경(쓰기) 통계/자동설정 Tool을 추가할 때 그대로 확장해 재사용할 수 있는 기반이 된다.
