## Story

**As a** AI 도우미가 각 유형(A~I)을 어떻게 판단하고 응대하는지 이해하고 싶은 테넌트 관리자,
**I want** "AI 의사결정 로직" 탭에서 실제 질문을 입력해 시뮬레이션을 돌리지 않고도, 유형별 정의와
실제 업로드된 지식베이스 기반 사례 설명을 바로 확인하기를,
**so that** LLM 호출 비용/대기시간 없이 즉시, 그리고 실제 데이터에 기반한 신뢰할 수 있는 설명을
얻을 수 있다.

## Acceptance Criteria

1. "AI 의사결정 로직" 탭에서 기존 Story 1.32의 "질문을 입력해 시뮬레이션 실행" UX를 제거한다
   (실시간 LLM 호출 없음).
2. 유형 A~I 각각에 대해: 정의/트리거 조건(`GET /intellidecision-policy`의 `trigger_examples` 등
   기존 정책 메타데이터 재사용, 신규 API 불필요)과 함께, **실제 업로드된 지식베이스에서 추출한
   사례 설명**을 정적으로 표시한다 — 예: "이런 질문이 들어오면 → 이 지식베이스 문서가 매칭되고
   → 이런 hop이 확장되어 → 이렇게 응답한다"를 실제 KB 데이터 기반으로 사전 계산해 보여준다.
3. 사례 설명에 사용되는 hop 경로는 Story 1.28 `traverse_graph()`를 사전(또는 조회 시점에) 호출해
   산출하되, 이는 어디까지나 "지식베이스 구조 설명"이지 실시간 대화 시뮬레이션이 아니다 — 응답
   생성(LLM 호출)은 발생하지 않는다.
4. KB에 특정 유형에 대응하는 문서/사례가 없으면 "아직 사례가 없습니다"로 명확히 표시하고, 임의로
   지어내지 않는다.
5. 실제 응대를 확인하고 싶은 사용자는 Story 1.39의 실제 채팅 패널로 안내하는 링크/버튼을 제공한다
   (매뉴얼과 실제 채팅의 역할 분리를 명확히 함).

### 실서버 IV 검증 결과(2026-08-06) — 버그 발견·즉시 수정

- 1차 재시작 후 `GET /intellidecision-manual?owner=9001` 실호출 결과 전 유형이 `has_case=false`로
  반환되는 실제 버그를 발견했다. **원인**: `get_self_service_rag_engine()`이 실제 대화 턴
  처리(`agent.py::process_utterance` 진입 시만) 진입 시만 채워지는 `call_context`(ContextVar)에서
  embedder/vector_db를 읽는데, 이 엔드포인트는 대화 턴 밖에서 독립적으로 호출되어
  컨텍스트가 비어있어 RAG 검색 자체가 실행되지 않았다.
- **수정**: `settings_ai_assistant.py::get_intellidecision_manual()`에서 엔드포인트 진입 시 전역
  AI Orchestrator(`get_ai_orchestrator()`)의 `.rag.embedder`/`.rag.vector_db`를 `set_call_context()`로
  주입하고 `finally`에서 `clear_call_context()`로 해제(`knowledge_base_simulate.py::
  _get_isolated_agent`와 동일한 재사용 패턴, LLM 클라이언트는 미주입 — 이 Story는 LLM 호출이
  없어야 하므로 의도적으로 제외). 단위테스트 8건 재실행 그대로 통과(모듈 자체는 무수정).
- **재검증(사용자 2차 재시작 후)**: 동일 엔드포인트 실호출 결과 유형 A/B/C/G(`rag_enabled=true`)는
  모두 `has_case=true`로 실제 매칭 문서(doc_id/유사도/related_domain/발출문구)와 hop 경로가
  정상 반환되고, 유형 D/E/F/H/I(`rag_enabled=false`)는 의도대로 `has_case=false`로 유지됨을
  확인(AC2/AC3/AC4). 브라우저(Playwright)로 "AI 의사결정 로직" 탭 유형 A 카드에 "지식베이스
  사례" 섹션이 실제 문서 2건+hop 칩으로 정상 렌더링됨을 확인(AC2/AC3).
- **교훈**: `call_context.py` ContextVar 기반 의존성 주입(embedder/vector_db 등)은 실제 대화
  턴 처리 경로에서만 채워지므로, 그 경로 밖에서(독립 읽기 전용 API 등)이 같은 헬퍼(예:
  `get_self_service_rag_engine()`)를 재사용할 때는 반드시 전역 오케스트레이터 인스턴스에서 필요한
  의존성을 직접 주입해야 함(`_get_isolated_agent` 패턴). 단위테스트는 해당 모듈을 모킹해서
  이 함정을 전혀 못 잡았다 — 실서버 IV가 이번에도 유일한 발견 경로였다.
