## 재설계 배경(2026-08-06)

최초 구현은 "qa/catalog/screen을 유형별로 나눠 나열하고, 항목을 클릭해야 상세(hop 경로 등)를
보는" 리스트+상세 2단 구조였다. 사용자가 실제 화면을 보고 "이건 원하는 방향이 아니다 — RAG
지식베이스마다 hop이 존재해서 지식베이스와 hop을 연계해서 보여줄 수 있는 건데, 지금은 유형별로
따로 보여주고 클릭해야 연결을 본다"고 지적했다. 후속 확인 결과 사용자가 원한 것은 **hop
그래프의 연결 성분(connected component) 단위로 Q&A/설정/화면안내를 미리 그룹핑해, 클릭 없이
요약 표로 먼저 보여주는 것**이었다(아코디언으로 상세만 펼침). 이에 따라 Story 1.48의 산출물
(`UnifiedKnowledgeList`/`UnifiedKnowledgeDetailPanel`, 클릭 기반 리스트+상세)을 폐기하고
`KnowledgeClusterTable` 단일 컴포넌트로 대체했다.

## Story
As a 테넌트 관리자,
I want hop(지식 그래프)으로 실제 연결된 매뉴얼 Q&A/설정/화면 안내를 그룹으로 미리 묶어서
표(아코디언)로 보고, 클릭 없이 요약을 먼저 확인하기를,
so that "이 지식이 어떤 설정·화면과 연결되는지"를 유형별로 흩어진 화면을 오가지 않고 한 번에
파악할 수 있다.

## Acceptance Criteria
1. 매뉴얼 Q&A/설정 카탈로그/화면 안내가 hop 그래프의 연결 성분(같은 클러스터) 단위로 그룹핑되어
   표시된다 — 클러스터 판별은 각 도메인의 hop 경로(`GET /domain-hop-path`)를 조회해 Union-Find로
   계산한다.
2. 각 그룹은 클릭하지 않아도 도메인 라벨과 Q&A/설정/화면/hop 단계 수 요약이 보이고, 상세(원문·
hop 경로·필드 등)는 아코디언(`<details>`)으로 펼쳐서 본다. 펼친 내부는 "매뉴얼 Q&A"/
"설정"/"화면 안내" 같은 카테고리 소제목 상자로 나누지 않고, Q&A → 화면 안내 → 설정
순으로 이어 붙여 "연결된 정보 하나"로 읽히게 한다(2026-08-06 사용자 재피드백 반영).
3. hop 연결이 없는 항목도 자신의 도메인만으로 구성된 단일 그룹으로 표시된다(제외하지 않음).
4. `policy` 탭 데이터(의도 유형/수동 케이스/의사결정 세션)는 이번 그룹 테이블 대상에서
   제외된다(Story 1.48 AC4와 동일 원칙, 별도 탭 유지).
5. 검색창으로 도메인 라벨·Q&A 제목·설정 도메인·화면 제목 기준 필터링이 된다.
6. `npx tsc --noEmit` 0 에러.

### 2026-08-06 재수정 — 카테고리 박스 제거 + 탭 데치러

사용자가 구현 결과를 보고 "그냥 하나의 페이지에 다 몰아넣으면 어떻게하니"라며 구체 예시(같은
도메인의 Q&A/화면안내/설정이 하나로 이어붙어 보여야 한다)를 들어 재지적했다. 실제로
반영해야 할 2가지:

1. **표시 병합**: `KnowledgeClusterTable`의 각 그룹 본문에서 "매뉴얼 Q&A"/"설정"/
   "화면 안내" 굴드 소제목과 개별 테두리 박스를 제거하고, Q&A → 화면 안내 → 설정 순서로
   하나의 흐름(divide-y 가로줄만 구분)로 이어 붙임. 사용자가 직접 예시로 보여준 형태(제목 →
   질문 → 답변 → 화면명+도메인+링크+설명+필드 → 설정명+배지+필드)과 동일한 순서로 맞춤.
   `ScreenRaw`에 `fields` 추가해 화면 안내의 입력 필드(radio 등)도 함께 노출.
2. **탭 데치러리**: `qa`/`catalog`/`screen`/`kb` 탭 버튼을 탭바에서 제거(코드/데이터 로딩은
   그대로 남겨둠, 회귀 위험 최소화) — 지식 "항목"으로 서로 중복되는 화면을 한 페이지에 계속
   느는 것을 막기 위해 `list`/`policy`/`upload` 3개만 노출.

`npx tsc --noEmit` 재검증 0에러.

### 2026-08-06 브라우저 실검증 — 전체 도메인이 하나로 뭉치는 중대 버그 발견·수정

사용자가 "서버 재시작 안 했는데 브라우저에서 봐도 동일하다"고 지적해, 통합 브라우저 도구로
`localhost:3000/settings/ai-assistant/docs`를 owner=9001로 직접 열어 확인했다(상세:
[owner=9001 검증 리포트](../reports/2026-08/2026-08-06_kb_cluster_owner9001_verification.md) §6).

**발견**: 13개 도메인 전부가 단 1개 그룹으로 뭉쳐 표시됨(Q&A 9건·설정 7건·화면 6건·hop
83단계). **근본 원인**: Union-Find가 hop 그래프의 `writable: catalog_domain→intent_type`
간선까지 그대로 union했는데, 이 간선은 거의 모든 도메인이 공통 IntelliDecision 유형
(A/C/F/H/I 등)으로 연결되는 **공유 허브**라 서로 무관한 도메인들이 전이적으로 하나의
거대 클러스터로 합쳐졌다.

**수정**: 클러스터링과 그룹 hop 표시 모두 `edge_type === "rendered_by"`(도메인→화면 연결)만
사용하도록 필터링. 브라우저 재확인 결과 11개 그룹으로 정상 분리되고, "AI 에스컬레이션" 그룹을
펼쳐보면 사용자가 제시한 예시(Q&A→화면 안내→설정 순서, 정확한 필드까지)와 일치함을 확인.

`npx tsc --noEmit` 재검증 0에러. 브라우저 실행 확인 완료(owner=9001).
