## 상세 설계 요약 (전문은 [Architecture §2.3.1](../architecture/voice-latency-turn-taking-architecture.md#231-smart-turn--barge-in-부활-상세-설계-2026-07-27-사용자-결정-부활-확정) 참고)

1. **삽입 지점**: `SmartTurnProcessor`는 `vad_wrapped`↔`stt` 사이, barge-in 판단 로직은
   `SmartBargeInProcessor`(구형 프레임 후킹)를 그대로 쓰지 말고 **`SmartBargeInStrategy`의 판단
   로직만 추출**해 pipecat의 `user_turn_strategies` API(커스텀 `UserTurnStrategy`)로 통합할 것을
   권고 — 기존 `MinWordsUserTurnStartStrategy`와 동일 통합 지점을 사용해 이중 계층을 피한다.
2. **중복 제거 권고**: `SmartBargeInStrategy.min_words`(기본 3)는 `MinWordsUserTurnStartStrategy
   (min_words=3)`와 동일 판단을 이중 수행하므로, 부활 시 **`min_words=0`으로 비활성화하거나
   파라미터를 제거**하고 Stage 1(키워드)·Stage 3(LLM 판단) 2단계로 단순화한다.
3. **FR 매핑**: FR6(잡음/짧은 발화 무시) → Smart Turn 최소 길이 체크 + barge-in 키워드/맞장구
   필터. FR7(LLM 사고 중 발화 합산) → 이미 별도 메커니즘으로 충족(Story 5.3, 무관). FR8(임계값
   조정) → VAD/Smart Turn 임계값 튜닝(Story 5.4). FR9는 PRD 원문 재확인 필요(추측 금지, Story
   5.4 착수 시 확인). FR12(A/B 검증) → 실통화 영향이므로 사용자 승인 필수.
4. **사전 검증 필요 리스크**(구현 착수 전 반드시 확인):
   - Smart Turn 모델(`LocalSmartTurnAnalyzerV3`) 추론 시간 실측 — Epic 6로 확보한 지연 개선분을
     새 병목이 상쇄할 위험.
   - `SmartBargeInProcessor`가 참조하는 `LLMFullResponseStartFrame` 등 pipecat 프레임이 현재
     고정된 `pipecat-ai` 버전에서 여전히 유효한지 확인.
   - `LLMClient.judge_barge_in()`은 Story 6.1에서 이미 `google-genai`로 전환 완료라 추가
     마이그레이션 불필요(확인만 하면 됨).
5. **롤아웃 전략**: self-service Story 2.6 패턴(베이스라인 확보 → 변경 → 재검증 → 저하 시
   롤백) + `config.yaml` feature flag(예: `turn_taking.smart_turn_enabled`)로 즉시 롤백 가능한
   구조를 Story 5.4에서 도입할 것을 권고.

## Dev Agent Record

### 설계 근거(2026-07-27)

- `pipeline_builder.py`를 직접 읽어 `MinWordsUserTurnStartStrategy(min_words=3)`가
  `PipelineTask(user_turn_strategies=...)`로 실제 연결되어 있음을 재확인(Story 5.1 조사 결과와
  일치). 이 통합 지점이 barge-in 판단 로직을 다시 넣기에 가장 자연스러운 위치임을 확인했다.
- `smart_turn_processor.py`/`barge_in_strategy.py` 코드를 전체 읽고, 두 클래스 모두 이미 완성도
  높게 작성되어 있어(3단계 필터, 통계 수집 등) **재작성이 아니라 통합 방식만 바꾸면 재사용
  가능**하다고 판단했다.
- `LLMClient.judge_barge_in()`이 Story 6.1에서 이미 마이그레이션된 것을 확인해, barge-in 부활이
  Epic 6와 충돌하지 않음을 검증했다.
