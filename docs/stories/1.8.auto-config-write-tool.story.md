# Story 1.8: 범용 자동설정 Tool (쓰기 + 제외 목록)

## Status

Done(2026-07-20/21 `master-qa.md` Branch F로 실서버 검증까지 완료 — 제외 목록/보안 우회 방어 F3/F4 포함 PASS)

## Story

**As a** 테넌트 관리자,
**I want** 대화로 "알림 꺼줘", "페르소나 응답 문구 바꿔줘" 같은 요청을 하면 AI가 확인 후 실제로 반영해주기를,
**so that** 어떤 설정 화면을 열지 않고도 원하는 대로 바꿀 수 있다.

## Acceptance Criteria

1. `settings_catalog.py`(Story 1.4에서 구축된 레지스트리)에 **변경 함수**가 도메인별로 추가 등록된다.
2. `update_self_service_setting(domain, field, value)` Tool이 카탈로그에 등록된 스키마를 동적으로 조회하여 필수/옵션 값을 확인하고, **반드시 확인 발화**를 거친 뒤 실행한다(booking_agent와 동일 원칙).
3. 카탈로그의 **명시적 제외 목록(destructive 항목)**에 있는 항목에 대한 변경 요청은 거부되고 이유가 안내된다(NFR4). 제외 목록 밖 항목은 변경 함수 등록만으로 기본 자동설정 가능하다.
4. 변경 시 변경 이력(도메인, 필드, 이전값, 새값, 시각, call_id)이 로깅된다(FR8).
5. 신규 설정 도메인이 카탈로그에 등록되면 코드 추가 변경 없이 Tool이 이를 인식해 조회·자동설정에 반영한다(FR11).

### Integration Verification

- **IV1**: 자동설정 Tool이 프론트엔드 설정 화면과 동일한 서비스 함수를 호출하여, 프론트엔드에서 확인 시 즉시 반영된 값이 보임을 확인한다(CR4).
- **IV2**: 제외 목록에 있는 항목에 대한 강제 시도(프롬프트 인젝션 유사 테스트 포함)가 실제 설정 변경으로 이어지지 않음을 확인한다.
- **IV3**: 7개 도메인 각각에 대해 최소 1개 필드의 조회·자동설정 왕복 테스트가 통과한다(카탈로그 커버리지 검증).

## ⚠️ 구현 중 발견된 사실

1. **7개 도메인 중 3개만 실제 쓰기 가능** — AC5/IV3은 암묵적으로 7개 도메인 모두 쓰기를 전제하는 듯 보이지만, 실제 코드를 확인한 결과 다음과 같은 이유로 4개 도메인은 "단일 필드=값" 갱신 모델에 맞는 실제 변경 함수가 없거나 데이터 구조가 맞지 않았다:
   - `call-control`: 착신 규칙은 여러 건의 목록데이터(개별 규칙 ID 필요) — 단일 필드 갱신으로 표현 불가
   - `contacts`: 연락처도 여러 건의 목록데이터(개별 연락처 ID 필요) — 동일한 이유로 부적합
   - `general`: 테넌트 프로필(`TENANTS_DATA`)이 **정적 하드코딩 Python 리스트**라 실제 변경 함수가 코드에 전혀 없음
   - `integrations`: Google Calendar 연동은 OAuth 리디렉션이 필요한 액션이지 단순 값 설정이 아님

   이러므로 본 Story는 **3개 도메인(persona, ai-escalation, chat-relay)만 쓰기 지원**하고, 나머지 4개는 `config/self_service_exclusions.yaml`에 명시적으로 등록해 안전하게 거부되도록 했다. IV3("7개 도메인 조회·자동설정 왕복")는 쓰기 가능한 3개는 왕복, 나머지 4개는 "안전하게 거부됨"을 검증하는 것으로 대체했다.

2. **`destructive` 플래그(Story 1.4)와 실제 쓰기 허용 여부는 별개** — Story 1.4에서 `ai-escalation`/`chat-relay`/`call-control`/`general`/`integrations`는 모두 `destructive=True`로 등록되어 있었다. 만약 이 플래그를 그대로 제외 기준으로 쓨다면 `ai-escalation`/`chat-relay`(Story의 핵심 예시인 "알림 꺼줘", "에스컬레이션 방식 바꿀줘")도 모두 차단된다. 본 Story에서는 `destructive` 플래그를 "안전측 기본값 신호"로만 참고하고, 실제 쓰기 허용 여부는 도메인별로 재검토해 **새로운 제외 목록(`config/self_service_exclusions.yaml`)** 로 세분화하기로 판단했다(근거: Story 본문이 직접 언급한 사용 사례와 일치).

3. **`migrations/*.sql` 폴더는 실제로 사용되지 않는다** — Task 3이 제안한 `migrations/00XX_self_service_config_changes.sql` 경로를 따르려다 코드를 확인한 결과, 이 폴더는 **PostgreSQL 문법**(UUID, plpgsql)이며 어떤 Python 코드에서도 참조되지 않는 미사용/레거시 경로임을 확인했다. 실제 운영 SQLite DB(`call_records`, `chat_relay_settings` 등이 있는 실제 DB)의 스키마는 `src/booking/database.py`의 `_DDL`(CREATE TABLE) + `_MIGRATIONS`(ALTER TABLE 리스트)이며 `init_db()`가 서버 기동 시 실행한다. 따라서 `self_service_config_changes` 테이블을 **`src/booking/database.py`의 `_DDL`에 추가**했다(실제로 반영되는 유일한 방법).
