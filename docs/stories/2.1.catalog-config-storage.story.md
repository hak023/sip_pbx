# Story 2.1: 카탈로그/Screen Graph 설정 저장소 설계 및 구현

## Status

Done

## Story

**As a** 개발자,
**I want** 설정 카탈로그·Screen Graph의 메타데이터를 저장할 DB 스키마와 안전한 함수 참조 방식을,
**so that** 이후 Story들이 이 저장소를 기반으로 동적 로딩·업로드 기능을 구현할 수 있다.

## Acceptance Criteria

1. 신규 SQLite 테이블(`self_service_catalog_config` 등)이 `src/booking/database.py`의 `_DDL` 관례에 따라 추가된다(기존 `self_service_config_changes`와 동일 파일 공유, 신규 DB 엔진 도입 없음).
2. 각 레코드는 버전 번호·활성 여부(`is_active`)·업로드 시각·업로드 주체를 포함해, 버전 이력 조회와 롤백(이전 버전 재활성화)이 가능한 구조여야 한다.
3. `get_fn`/`update_fn`은 여전히 Python 코드에 정의하되, **함수명 문자열 → 콜러블** 화이트리스트 레지스트리(`_GET_FN_REGISTRY`/`_UPDATE_FN_REGISTRY`)로 별도 분리한다. DB 설정은 이 화이트리스트에 있는 이름만 참조할 수 있으며, 등록되지 않은 이름을 참조하면 검증 실패로 거부된다(임의 코드 실행 방지 — 보안 핵심 설계).
4. 기존 `_CATALOG`/`_SCREEN_REGISTRY`의 현재 값을 1회성 마이그레이션 스크립트로 신규 테이블에 시드(seed)한다 — 이관 직후에는 기존과 동일한 동작을 보장해야 한다(IV1).

### Integration Verification

- **IV1**: 마이그레이션 직후 기존 `test_self_service_settings_tool.py`/`test_self_service_screen_graph.py` 전체가 회귀 없이 통과한다(값이 이관되었을 뿐 동작은 동일해야 함).
- **IV2**: 화이트리스트에 없는 함수명을 참조하는 설정을 강제로 넣으면 로딩이 거부되고 명확한 오류가 남는다(보안 검증 케이스).

- [x] **Task 3: 함수 화이트리스트 레지스트리 신설** — `settings_catalog.py`에 `_GET_FN_REGISTRY`/`_UPDATE_FN_REGISTRY` 추가(`get_fn_whitelist_names()`/`update_fn_whitelist_names()` 헬퍼 포함). `screen_graph.py`는 실행 가능한 콜러블이 전혀 없는 순수 데이터 구조(route/title/description/nav_hint/fields)이므로 화이트리스트 대상이 없음을 확인 — 이 도메인은 Story 2.3에서 DB 로더로 전환 시에도 보안 화이트리스트가 불필요함을 명시.
- [x] **Task 4: 마이그레이션 스크립트 작성** — `scripts/self_service_catalog_migrate_seed.py` 신규 작성. `_CATALOG`/`_SCREEN_REGISTRY`의 현재 값을 읽어 `config_kind="catalog"`/`"screen_graph"` 각각 version 1로 시드 후 활성화. get_fn/update_fn은 화이트리스트 역조회(`_reverse_lookup`)로 문자열 이름으로 변환해 저장. 멱등성 확인(이미 활성 버전 있으면 skip, `--force`로 재실행 가능) — 실제 개발 DB(`data/booking.db`)에 실행하여 seed 및 재실행 skip 동작 모두 확인함.
- [x] **Task 5: 단위 테스트** — `test_self_service_catalog_config_db.py`(DB CRUD/버전 이력/롤백/kind별 독립 버전 시퀀스, 10개), `test_settings_catalog.py::TestFunctionWhitelistRegistry`(카탈로그의 모든 get_fn/update_fn이 화이트리스트에 등록되어 있는지 전수 검증 + 화이트리스트 이름 목록 검증, 5개) 작성 및 통과.

### Completion Notes

- 신규 테이블은 `config_json` 단일 TEXT 컬럼(JSON 직렬화)으로 설계해 카탈로그/Screen Graph처럼 서로 다른 구조를 하나의 테이블·하나의 버전 관리 메커니즘으로 수용했다 — Story 2.2/2.3에서 스키마 변경 없이 재사용 가능.
- `activate_version()`은 신규 활성화와 롤백(이전 버전 재활성화)에 동일하게 사용되는 단일 함수로 구현 — "현재 kind의 모든 행을 비활성화 후 지정 버전만 활성화"라는 단순 불변조건만 지키면 되므로 별도 롤백 API가 불필요함을 확인.
- `settings_catalog.py`의 `_GET_FN_REGISTRY`/`_UPDATE_FN_REGISTRY`는 함수 **정의는 그대로 코드에 두고** 이름→콜러블 매핑만 추가하는 순수 부가(additive) 변경이라, 기존 `_register()`/`call_update_fn()` 등 외부 동작에는 전혀 영향이 없음(IV1 충족 확인).
- Task 3 관련 스코프 결정: `screen_graph.py`는 실행 가능한 함수가 없는 순수 데이터(route/title/description/nav_hint/fields)이므로 화이트리스트 레지스트리 자체가 불필요 — AC3 문구상 두 파일 모두 언급되어 있으나, 실제로는 `settings_catalog.py`에만 해당되는 보안 장치이며 이는 설계 문서(Epic 2 아키텍처 §핵심 설계 결정)의 "Screen Graph는 100% 안전하게 외부화 가능" 원칙과 일치한다.
- 마이그레이션 스크립트를 실제 개발 DB(`data/booking.db`)에 대해 실행해 seed 성공, 값 왕복(내용 확인), 재실행 시 skip(멱등성)까지 3단계 모두 라이브로 검증했다.
- IV2(화이트리스트 미등록 함수명 거부)의 실질적인 **로더 단** 검증(`catalog_config_loader.py::validate_config()`)은 Story 2.2 구현 범위다. Story 2.1에서는 그 전제 조건인 "화이트리스트 레지스트리가 `_CATALOG`의 모든 실제 함수를 정확히 커버하는지"를 `TestFunctionWhitelistRegistry`로 검증했다(레지스트리 자체의 정합성 보장 — 로더의 거부 로직 검증은 다음 스토리로 이연).
