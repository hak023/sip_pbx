# Story 1.15: IntelliDecision 유형 C(포괄적 도움 요청) — 능력 안내 응대 추가

## Status

Done (코드/문서 반영 완료, 실서버 IV1 재검증은 다음 서버 재시작 시 필요 — 아래 QA Results 참고)

## Story

**As a** 테넌트 관리자,
**I want** "AI야 너 뭘 할 수 있어?"처럼 특정 기능을 콕 집지 않고 포괄적으로 도움을 요청해도
셀프서비스 AI가 실제로 제공하는 기능을 예시와 함께 구체적으로 안내받기를,
**so that** 어떤 질문·요청을 해야 할지 몰라 헤매지 않고 바로 원하는 기능을 사용할 수 있다.

## 배경

기존 IntelliDecision(FR12, Story 1.10)은 설정 변경 관련 발화를 **유형 A(탐색성)** 와
**유형 B(실행성)** 두 가지로만 구분했다. 그런데 두 유형 모두 "이미 특정 기능·설정 하나"를
전제로 한 발화만 다룬다(예: "그런 기능도 있어?", "알림 꺼줘"). "AI가 뭘 할 수 있어?"처럼
대상이 특정되지 않은 **포괄적** 질문은 이 두 유형 어디에도 명시적으로 대응하지 않았다.

실제 코드(`self_service_agent.py`)를 확인한 결과, 이런 포괄적 질문은 매뉴얼 RAG 검색에
맡겨졌고, `docs/product/self-service-manual-content.md` §9의 관련 Q&A("셀프서비스 AI
도우미에게 무엇을 물어볼 수 있나요?")조차 "향후 지원되는 기능이 추가되면..."이라는 **미래형
서술로 작성되어 있어, 실제로는 Epic 1/2(Story 1.1~2.8)에서 이미 구현된 7개 능력 카테고리
(설정 조회 7개 도메인, 자동설정 3개 도메인, 온보딩 체크리스트, 통계 조회, 통화 이력 NLQ 3종,
화면 안내, 매뉴얼 Q&A)를 정확히 반영하지 못하는 stale 콘텐츠였다.** RAG가 이 Q&A를 못 찾는
경우(임베딩 유사도가 낮은 질문 표현)에는 일반 폴백 문구("제가 알지 못하는 내용입니다")만
나가는 완전한 공백도 있었다.

## Acceptance Criteria

1. IntelliDecision에 **유형 C(포괄적 도움 요청)** 를 신설한다 — 사용자가 특정 도메인/기능을
   특정하지 않고 "뭘 할 수 있어?", "어떤 도움을 줄 수 있어?" 등으로 물으면 이 유형으로 응대한다.
2. 유형 C 응답은 실제로 구현된 능력(설정 조회/자동설정/통계 조회/통화 이력 NLQ/온보딩 안내/
   매뉴얼 Q&A) 중 최소 3개 카테고리를 **구체적 예시 발화**와 함께 안내해야 하며, 존재하지 않는
   기능을 지어내지 않는다.
3. 유형 C 규칙은 Tool 호출이 필요 없는 순수 안내이므로 `_SELF_SERVICE_SYSTEM_PROMPT_TEMPLATE`
   (기본 시스템 프롬프트)에 추가되어, bind_tools/Gemini 네이티브 FC/프롬프트 전용 폴백 **3개
   경로 모두**에서 항상 적용되어야 한다(Tool 바인딩 성공 여부와 무관하게 동작).
4. 유형 A/B 판단 지시(`_TOOL_USAGE_INSTRUCTION` 항목)에 유형 C와의 경계를 명시해, LLM이 포괄적
   질문을 유형 A로 오분류해 매뉴얼 텍스트 단편만 반환하지 않도록 한다.
5. 매뉴얼 RAG 소스(`self-service-manual-content.md` §9)의 "무엇을 물어볼 수 있나요" Q&A를
   미래형 서술("향후 지원되는 기능이 추가되면")에서 현재 실제로 동작하는 기능 목록 기준으로
   최신화한다(회귀 없이 RAG가 이 질문에 맞더라도 정확한 답을 하도록 이중 방어).

### Integration Verification

- **IV1**: 실서버에서 "AI야 너 뭘 할 수 있어?" 계열 발화를 셀프서비스 세션(owner=착신자와
  동일 번호)으로 3회 이상 반복 실행해, 매번 최소 3개 이상의 실제 기능 카테고리가 구체적 예시와
  함께 안내되고 존재하지 않는 기능이 언급되지 않는지 확인한다. **서버 재시작 필요 — 사용자
  승인 후 다음 세션에서 진행.**
- **IV2**: 기존 유형 A/B 시나리오(Story 1.10/2.6 QA 16건)를 재실행해 유형 C 추가로 인한 회귀가
  없는지 확인한다(문서 검토 결과 유형 A/B 프롬프트 지시는 그대로 유지, 신규 규칙만 추가되어
  회귀 리스크는 낮음 — 실서버 재검증 시 IV1과 함께 확인 권장).
- **IV3**: 매뉴얼 콘텐츠(§9) 변경 사항이 실제 ChromaDB(`doc_type=self_service_manual`)에
  반영되려면 `manual_indexer.py::index_self_service_manual(..., force=True)` 재색인이 필요하다
  (기존 색인은 owner당 1회만 수행되는 멱등 구조라 자동 반영되지 않음). **재색인은 실제 테넌트
  데이터에 영향을 주므로 사용자 승인 후 유지보수 시점에 수행할 것을 권장한다.**

## Dev Notes

- 유형 C는 Tool 호출이 필요 없는 **순수 안내형 응답**이므로, Tool-calling 바인딩 성공 여부에
  따라 조립 방식이 갈리는 `_TOOL_USAGE_INSTRUCTION`이 아니라 항상 적용되는
  `_SELF_SERVICE_SYSTEM_PROMPT_TEMPLATE`(기본 프롬프트)에 추가했다 — 이렇게 해야 bind_tools
  실패 시 프롬프트 전용 폴백 경로(현재 프로덕션에서 실제로 쓰이는 경로, repo 메모 §LLM
  클라이언트 아키텍처 참고)에서도 동일하게 동작한다.
- `.github/copilot-instructions.md`의 "의도 분류는 키워드 매칭보다 LLM 판단을 우선한다" 원칙을
  그대로 따라, 별도의 정규식 키워드 힌트나 분류 전용 LLM 호출을 추가하지 않고 기존 메인 LLM
  호출의 시스템 프롬프트 지시만으로 유형 C를 판단하도록 설계했다(Story 2.6에서 확정한 방향과
  일관).
- 매뉴얼 콘텐츠(§9) 최신화는 RAG가 이 Q&A를 우연히 찾아내는 경우에 대한 **이중 방어**다 —
  프롬프트 규칙(Task 1)이 주 경로이고, 매뉴얼 갱신은 RAG 검색 결과에 이 Q&A가 포함될 때도
  일관되게 정확한 답을 보장하기 위함이다.
