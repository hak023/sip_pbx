## Acceptance Criteria

3. DB 조회 실패 시(테이블 없음 등) 안전하게 폴백하거나 명확한 오류를 반환하고, 최소한 서버 기동 자체는 실패하지 않아야 한다.

### Completion Notes

- **핵심 설계**: `_CATALOG`(기존 `_register()` 호출 결과)를 삭제하지 않고 그대로 남겨 하드코딩 폴백으로 쓴다. `_get_effective_catalog()`가 매 호출마다 먼저 DB 활성 구성(`catalog_config_loader.get_cached_config`)을 확인하고, 있으면 화이트리스트로 해석해 `DomainEntry` 딥션너리를 동적으로 구성하고, 없거나 비어있거나 실패하면 즉시 정적 `_CATALOG`로 폴백한다(AC3).
- **캐시이중화 설계**: `catalog_config_loader`자체가 활성 버전이 바뀌지 않는 한 동일 `config_json` 딥션너리 객체를 재사용하므로, `settings_catalog.py`는 `id(raw_config)` 비교만으로 `DomainEntry` 재구성 필요 여부를 판단한다(DB 조회 빈도뿐 아니라 딥션너리 재구성 빈도도 함께 캐싱 — NFR6).
- **화이트리스트 거부 정책**: `get_fn_ref`가 화이트리스트에 없으면 해당 도메인 전체를 건너뛴다(조회조차 위험). `update_fn_ref`만 없으면 조회는 유지하고 쓰기만 비활성화(`update_fn=None` → 기존 `call_update_fn()`의 `domain_not_writable` 경로가 그대로 작동).
- **예기치 않은 회귀(중요)**: Story 2.1에서 이미 실제 개발 DB(`data/booking.db`)에 마이그레이션 스크립트로 카탈로그를 시드해둘 상태였기 때문에, `_get_effective_catalog()`가 실수로 정적 `_CATALOG` 대신 DB 시드값(동일한 값이다)을 리턴하게 되면서, `monkeypatch.setitem(catalog._CATALOG, ...)`로 직접 `_CATALOG`를 조작하던 기존 단위 테스트 2건(`test_self_service_auto_config.py`/`test_settings_catalog.py`)이 실제로 실패했다. 근본원인: 테스트가 개발 DB 상태에 암묵적으로 의존하게 된 것(공유 환경 오염). 해결: `tests_new/unit/conftest.py`에 오토유즈 픽스처를 추가해 `catalog_config_loader.get_cached_config`를 기본 None으로 고정함으로써, 별도로 동적 로딩 자체를 검증하는 테스트만 이 픽스처를 개별 재정의해 우회하도록 했다. 이로써 유니트 테스트가 실제 개발 DB 파일 상태에서 하돈되지 않게 격리되었다.
- IV1 충족 확인: 전체 회귀 275개 통과(신규 테스트 포함), 기존 테스트 로직 자체는 한 줄도 수정하지 않았음(conftest 추가만으로 해결).
