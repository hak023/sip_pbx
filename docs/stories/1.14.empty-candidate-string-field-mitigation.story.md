# Story 1.14: 자동설정 문자열 값 필드 확인→실행 흐름 Gemini 빈 응답 — 근본 원인 수정

## Status

Done

## Story

**As a** 테넌트 관리자,
**I want** 페르소나 설명처럼 내가 직접 문장으로 불러주는 값을 바꿀 때도 확인→실행 흐름이 안정적으로 동작하기를,
**so that** "응 맞아"라고 답했는데 엉뚱한 인사말만 돌아오는 일이 재발하지 않기를 바란다.

## 배경

Epic 2 Story 2.7 통합 QA 중 `persona.description`을 자연어 문자열로 변경하는 확인→긍정 2턴
흐름에서 긍정 턴이 **6/6회 모두** Gemini의 완전히 빈 candidate(`finish_reason=STOP`, 텍스트도
함수 호출도 없음)로 실패하는 것을 발견했다. 카탈로그를 전혀 수정하지 않은 원본 상태에서도 동일
재현되어 Epic 2와 무관함을 확인했고, 같은 시점 chat-relay의 boolean 값 필드
(`message_ai_reply_enabled`)나 ai-escalation의 enum 값 필드(`escalation_mode`)는 안정적으로
성공하는 반면, chat-relay의 문자열 값 필드(`message_ai_reply_prefix`)도 persona.description과
동일하게 실패했다. 즉 **도메인이 아니라 "확인 질문에 사용자가 직접 입력한 자연어 문자열 값이
포함되는가"가 실패율과 상관관계가 있는 것으로 추정**됐다.

### 1차 시도(재시도 완화책) — 사용자 피드백으로 재작업

최초 대응은 "재시도 횟수를 2→4로 늘리고, 소진 시 명확한 안내 메시지를 반환"하는 완화책이었다.
그러나 사용자가 "재시도로 증상만 가리지 말고 원천적인 실패 원인을 찾아 해결하라"고 정확히
지적해, 이 완화책을 유지한 채로 근본 원인 조사를 이어갔다.

### 근본 원인 규명

`update_self_service_setting` 도구의 `value` 파라미터는 도메인마다 타입이 제각각(불리언/enum
문자열/자유 문자열)이라 Python 함수 시그니처에서 `value: Any`로 선언되어 있다. 실제 생성되는
Pydantic JSON Schema를 직접 출력해 확인한 결과, `value` 필드는 `{"title": "Value"}`처럼
**`type` 키 자체가 없었다**(Pydantic이 `Any` 타입에는 타입 제약을 넣지 않기 때문).

`booking_gemini_fc.py::_json_schema_to_glm_schema()`(JSON Schema → Gemini `glm.Schema` 변환기)의
기존 코드는 다음과 같았다:

```python
if st in ("object", "") or "properties" in schema:
    return glm.Schema(type_=glm.Type.OBJECT, properties=props_map, ...)
```

`st = schema.get("type") or ""` 이므로, **"명시적으로 object로 선언된 경우"와 "타입 정보 자체가
없는 경우(Any)"를 똑같이 취급**해 `value` 필드를 **프로퍼티 0개짜리 OBJECT**로 Gemini에
선언해 버리고 있었다. 즉 Gemini function-calling 모델은 "`value`는 반드시 빈 객체여야 한다"고
알고 있는데, 실제로는 문자열이나 불리언 값을 채워야 하는 상황이었던 것이다.

이 스키마 불일치가 짧은 값(`true`/`false`, `"none"`)에서는 우연히 허용되거나 모델이 스스로
보정해 넘어가는 경우가 있었지만, 긴 자유 문자열(예: `"친절한 카페 매니저입니다"`)을 빈 객체
스키마에 맞춰 넣어야 하는 상황에서는 모델이 유효한 출력을 전혀 생성하지 못하고(제약 디코딩이
막힘) 완전히 빈 candidate를 반환하는 것으로 강하게 추정된다 — 관측된 모든 증거(도메인이 아니라
값의 타입과 상관관계, 확률적이지만 문자열 값에서 압도적으로 높은 실패율, Epic 2와 무관)와 정합적이다.

## Acceptance Criteria

1. **(근본 원인 수정)** `_json_schema_to_glm_schema()`가 `type` 키가 없고 `properties`도 없는
   필드(Python `Any`)를 더 이상 OBJECT로 취급하지 않고 STRING으로 변환한다. 명시적으로
   `type: object`이거나 `properties`가 있는 경우는 기존과 동일하게 OBJECT로 유지된다(회귀 없음).
2. `_MAX_EMPTY_CANDIDATE_RETRIES`를 2에서 4로 유지(근본 원인 수정 후에도 완전히 사라지지
   않을 수 있는 그 외 일반적 API 신뢰성 이슈에 대한 방어망으로 유지).
3. 재시도를 모두 소진했을 때 빈 문자열 대신 사용자가 재시도할 수 있음을 알 수 있는 명확한 안내
   메시지(`_FALLBACK_RETRY_EXHAUSTED`)를 반환한다.
4. 진단 로그(`self_service_agent_gemini_fc_empty_candidate`)에 `has_quote_or_bracket_in_history`
   신호를 유지해, 근본 원인 수정 이후에도 잔여 실패가 있는지 관찰할 수 있게 한다.
5. 신규 단위 테스트로 `_json_schema_to_glm_schema()`의 수정 전/후 동작 차이(Any 타입 → STRING,
   명시적 object/array/boolean/enum은 기존과 동일)를 회귀 방지 테스트로 고정한다.
