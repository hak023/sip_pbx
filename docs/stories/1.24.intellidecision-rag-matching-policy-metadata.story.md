## Story

**As a** 셀프서비스 AI 도우미를 운영·유지보수하는 개발자·운영자,
**I want** IntelliDecision 유형(A~I)마다 RAG 검색이 활성화되는지·어떤 범위·전략으로 매칭되는지를
대화 실행 전에도 표로 확인하고, 실제 실행 시점의 매칭 결과(문서 ID·점수·관련 도메인)도 로그로
남기를,
**so that** "이 유형의 발화가 오면 RAG가 어떻게 동작할 예정인지"를 사전에 예측하고, 실제 매칭
결과와 대조해 예측이 맞았는지 검증할 수 있다.

## Acceptance Criteria

1. `intellidecision_policy.py::IntentTypeSpec`에 `rag_enabled: bool`, `rag_source_scope: str`,
   `rag_strategy_hint: str`(`"vector"`/`"hybrid"`/`"none"`) 필드가 추가되고, 유형 A~I 9종
   전체에 값이 채워져 있다(빈 문자열/None 없음).
2. 유형 A(탐색성)/C(포괄적 도움 요청)는 `rag_enabled=True`이고, 유형 E(실행 취소)는
   `rag_enabled=False`, `rag_strategy_hint="none"`이다(실제 코드 동작과 일치 — E는 RAG 검색 없이
   변경 이력 테이블만 조회).
3. `GET /api/settings/ai-assistant/intellidecision-policy` 응답의 각 유형 항목에
   `rag_enabled`/`rag_source_scope`/`rag_strategy_hint`가 포함된다.
4. `self_service_agent_node`의 RAG 검색 호출부는 검색 결과가 1건 이상일 때
   `self_service_rag_matched` structlog 이벤트로 검색 쿼리·매칭 문서 ID 리스트·점수 리스트·
   related_domain 리스트를 기록한다. 이 로깅 추가는 판단/응답 로직을 전혀 변경하지 않는다
   (순수 관측 추가, 기존 동작과 100% 동일).
5. 프론트엔드 "AI 의사결정 로직" 탭의 유형 카드에 RAG 매칭 배지(`RAG: vector`/`RAG: hybrid`/
   `RAG 미사용`)와 `rag_enabled`인 경우 매칭 범위(`rag_source_scope`) 문구가 표시된다.
6. 신규/갱신 단위 테스트가 전체 통과하고, 기존 self_service 관련 회귀 테스트가 그대로 통과한다.
7. `npx tsc --noEmit`/`npx eslint`가 신규 프론트엔드 코드에 대해 오류 없이 통과한다.

## Dev Notes

- **필드 기본값 설계**: `rag_enabled=True`, `rag_source_scope="self_service_manual(owner)"`,
  `rag_strategy_hint="vector"`를 dataclass 기본값으로 둔 이유는, 실제 코드 동작상 대부분의 유형이
  현재 매뉴얼 RAG(owner 필터 + 벡터 검색)를 그대로 거치기 때문이다(기존 `self_service_agent_node`가
  유형과 무관하게 항상 RAG 검색을 먼저 수행 — Story 1.24는 이 사실을 레지스트리에 **사후 반영**한
  것이며, 코드의 실제 RAG 호출 조건을 바꾸지 않았다). D/E/F/H/I처럼 실제로는 신규 정보 없이
  기존 컨텍스트·Tool·이력만으로 처리되는 유형에만 `rag_enabled=False`를 명시했다.
- **"사전 예측"과 "실제 동작"의 정합성 한계(중요, 후속 검증 필요)**: 현재 `self_service_agent_node`
  코드는 IntelliDecision 유형이 확정되기 **전에** 이미 RAG 검색을 실행한다(유형 분류와 RAG 검색이
  같은 턴에 병렬적으로 일어나는 구조). 따라서 이번 Story의 `rag_enabled=False` 필드는 "이 유형에서는
  RAG 검색 결과가 응답에 실질적으로 반영되지 않는다"는 **설계 의도를 문서화한 사전 예측**이며,
  "코드가 실제로 RAG 검색 자체를 건너뛴다"는 뜻은 아니다. 이 차이를 프론트엔드 문구에서도 명확히
  했다(§3.3 리서치의 "예측과 실측을 대조 검증"이 필요한 이유이기도 하다 — Task 6 IV 검증에서
  실제로 유형 E/D 발화 시 `self_service_rag_matched` 로그가 남는지도 함께 관찰해 이 가정을
  검증할 것을 다음 세션에 권고한다).
- **로깅 이벤트를 기존 이벤트에 추가하지 않고 신규 이벤트로 분리한 이유**: 기존
  `self_service_agent_rag_search_done`은 항상 발생하는 요약 로그(hit_count/elapsed)이고,
  `self_service_rag_matched`는 매칭 문서가 있을 때만 상세 정보(쿼리·문서ID·점수)를 남기는
  상세 trace다. 두 이벤트를 분리해 항상 발생하는 로그의 크기를 늘리지 않으면서도 필요할 때
  drill-down 가능하게 했다(리서치 §2.1 LangSmith/Langfuse trace 패턴 참고).
