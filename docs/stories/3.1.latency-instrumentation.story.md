## Story

**As a** 운영자,
**I want** 발화 종료 시점부터 AI의 첫 응답 오디오가 나가는 시점까지의 전체 지연을 하나의 지표로
확인하고 싶다,
**so that** 응답이 느릴 때 어느 구간이 원인인지 추측이 아니라 로그로 즉시 알 수 있다.

## Acceptance Criteria

1. 발화 종료(T0, VAD stop + Smart Turn 완료) ~ TTS 첫 오디오가 RTP 송신 큐에 들어가는 시점(T5)까지의
   총 지연이 `call_data_record` 로그에 단일 필드(`response_latency_total_sec`)로 기록된다.
   [Source: PRD FR1]
2. 중간 구간(T0→T1 STT 확정, T1→T2 그래프 진입, T2→T3 LLM 첫 문장, T3→T4 TTS 첫 청크, T4→T5 RTP 큐
   진입)도 각각 별도 필드로 함께 기록되어 원인 구간을 바로 특정할 수 있다.
3. 기존에 이미 존재하는 계측(`agent_elapsed`, `llm_gen_elapsed_sec`, `llm_first_sentence_elapsed_sec`,
   TTS `"TTS first chunk yielding"` 로그)은 중복 계측하지 않고 재사용한다.
4. 신규 계측 추가로 인한 응답 지연 증가가 5ms를 넘지 않는다(NFR3).

### Integration Verification

- **IV1**: 계측 코드 추가 전/후로 동일 시나리오 10회 반복 시 `response_latency_total_sec` 자체의
  변동(계측 오버헤드)이 5ms 이내임을 확인한다.
- **IV2**: HITL/아웃바운드/템플릿 응답 등 기존 분기에서도 계측 필드가 예외 없이 기록됨을 확인한다
  (일부 필드가 해당 없음(N/A)일 수는 있으나 예외 발생은 금지).

### 조사 결과(2026-07-24) — AC 1~3은 이미 구현되어 있음 확인

- `src/common/ai_response_latency_compare.py`가 **이미 실제 파이프라인에 살아있는**(죽은 코드 아님,
  `rag_processor.py`/`rtp_transport.py`에서 import하여 호출) 턴 단위 지연 계측 모듈임을 확인함.
  - `begin_turn`(턴 시작) → `mark_stt_final`(T1) → `mark_llm_start` →
    `apply_llm_first_sentence_timing`(T3) → `mark_llm_complete` → `mark_tts_text_pushed` →
    `mark_first_audio_and_compare`(T5, `rtp_transport.py`에서 실제 RTP 솔송 시점에 호출)
  - `ai_response_latency_compare` 로그 이벤트가 이미 `ms_stt_final_to_first_audio_actual`
    (AC1의 `response_latency_total_sec`와 동등) 및 구간별 소요시간(AC2)을 함께 기록하고 있었음.
  - 추가로 "첫 문장 즉시 TTS 전송이었다면"의 **가상 지연**까지 비교해 미리 계산해두고 있어
    Epic 4(TTFT) 의사결정에 직접 활용 가능.
- **결론**: AC1~AC3(총 지연 단일 지표, 구간별 분해, 기존 계측 재사용)은 **이미 만족되어 있었음**.
  초기 조사(이전 세션) 단계에서 이 모듈을 발견하지 못한 것은 조사 누락이었다(`src/common/`까지
  전수 grep하지 않았음) — 향후 유사 작업 시 `src/common/`도 반드시 조사 범위에 포함할 것.
