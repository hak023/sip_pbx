## Story

**As a** 셀프서비스 지식 구조를 확장하려는 개발자,
**I want** `knowledge_graph.py`가 고정된 3단 체인이 아니라 노드/엣지 타입을 등록 가능한 범용
그래프 구조이길 원하고,
**so that** 신규 지식 유형(업로드 문서, API 엔드포인트, 절차 단계)이 늘어나도 그래프 순회 로직
자체를 매번 다시 작성하지 않고 확장할 수 있다.

## Acceptance Criteria

1. `knowledge_graph.py`에 **노드 타입 레지스트리**가 도입된다 — 기존 4종
   (`manual_qa`/`catalog_domain`/`frontend_screen`/`intent_type`)에 더해 `document`(Story
   1.26 업로드 문서), `api_endpoint`(OpenAPI 엔드포인트), `procedure_step`(다단계 절차 단위)
   노드 타입이 예약·등록 가능해야 한다(§5.1).
2. **엣지 타입 레지스트리**가 도입된다 — 기존 `relates_to`/`rendered_by`/`writable`에 더해
   `depends_on`(절차 단계 간 순서), `documents`(API 문서 ↔ 실제 Tool/엔드포인트 매핑)이 예약
   가능해야 한다.
3. `traverse(start_node, *, max_hops)`가 하드코딩된 3단 체인 호출이 아니라, 노드/엣지 등록
   테이블을 실제로 순회하는 그래프 탐색 함수로 재작성된다 — `max_hops`를 3~4단계로 늘려도
   코드 수정 없이 동작해야 한다(현재는 파라미터가 사실상 무시됨, §2.1 현황 진단 참고).
4. `intellidecision_policy.py`의 `rag_strategy_hint`에 `"graph_local"`(Microsoft GraphRAG의
   Local Search 개념 차용, §3.11) 값이 추가되고, 최소 1개 유형(예: 유형 A)에 실제로 적용된다.
5. 기존 2-hop 순회 결과(화면→writable 여부→적용 가능 유형)는 리팩터링 전후 **1바이트도 다르지
   않아야 한다**(Story 1.25/2.3의 "리팩터링 전후 직접 비교" 검증 패턴 재사용) — 순수 일반화이며
   기존 동작에 회귀가 없어야 한다.
6. Full GraphRAG 수준의 자동 엔터티 추출·Leiden 클러스터링은 이번 Story 범위에 포함하지
   않는다(§6 Non-Goal, 명시적 스키마 기반 소규모 그래프 유지).

## Dev Notes

- **왜 이 Story가 Story 1.26 이후에 와야 하는가**: `document` 노드 타입을 실제로 그래프에
  연결하려면 업로드된 문서가 실제로 존재해야 하므로, Story 1.26(CRUD)이 선행되어야 이 Story의
  AC5를 실질적으로 검증할 수 있다.
- **회귀 검증 방법론**: Story 1.25(`SourceAdapter` 일반화)·Story 2.3(Screen Graph 정적→DB
  전환)이 사용한 "리팩터링 전후 결과를 스크립트로 직접 바이트 단위 비교"하는 패턴을 그대로
  재사용한다.
- **GraphRAG Local Search 차용의 범위**: Full GraphRAG의 커뮤니티 클러스터링·자동 엔터티
  추출은 채택하지 않는다 — "질문 유형에 따라 다른 그래프 순회 전략(hop 수·시작 노드)을
  선택한다"는 **개념만** 차용한다(§3.11).
