## Story

**As a** 개발자,
**I want** `streaming_tts_processor.py`가 실제로 파이프라인에 연결되어 사용 중인지 확정하고 싶다,
**so that** Epic 4에서 이를 재사용할지 신규 구현할지, 또는 죽은 코드로 제거할지 근거를 가지고
결정할 수 있다.

## Acceptance Criteria

1. `pipeline_builder.py`(및 legacy `orchestrator/`, `pipecat_service` 등 진입 경로 전체)를 grep/read로
   전수 조사해 `streaming_tts_processor.py`의 `StreamingTTSGateway`(또는 동등 클래스)가 실제로
   `Pipeline([...])` 조립에 포함되는지 확정한다.
2. 포함되지 않는다면 "죽은 코드"로 판정하고, 제거 여부(또는 Epic 4에서 재활용) 결정 근거를 문서에
   기록한다(추측이 아닌 코드 검증 결과로).
3. 포함된다면 어떤 조건(config 플래그 등)에서 활성화되는지, 현재 운영 설정값이 무엇인지 확인한다.

## Dev Agent Record

### 조사 결과 (2026-07-24)

- `grep_search`로 저장소 전체(`sip-pbx/src/**`)에서 `StreamingTTSGateway`(클래스명) 및
  `streaming_tts_processor`(모듈명) 참조를 전수 검색.
- **`StreamingTTSGateway` 참조는 자기 자신의 정의부(`streaming_tts_processor.py`)와
  `tts_end_frame_forwarder.py`의 주석 1건뿐** — 실제 `import`/인스턴스화 코드는 **0건**.
- `pipeline_builder.py`, `orchestrator/ai_orchestrator.py`, `factory.py` 어디에도
  `streaming_tts_processor` 모듈을 import하는 코드가 없음(legacy 경로 포함 전수 확인).
- **판정(AC2): 죽은 코드(dead code) 확정.** 현재 어떤 config/실행 경로로도 활성화되지 않는다.
- **결정**: Epic 4(Story 4.1)에서 대안 C(기존 `StreamingTTSGateway` 재사용)는 **채택하지 않는다** —
  이미 파이프라인에 없으므로 "재사용"이 아니라 "신규 도입"과 동일한 리스크(미검증 코드)를 지님.
  대안 B(rag_processor.py가 LLM 스트림을 직접 구독)를 우선 검토 대상으로 확정한다. 파일 자체의
  삭제 여부는 Epic 4 구현 완료 후 별도 판단(구현 참고용으로 당장은 보존).
