## Story

**As a** 테넌트 관리자,
**I want** AI가 내 발화를 어떤 유형(탐색성/실행성/도움요청 등)으로 판단해서 어떻게 응대했는지가
기록되기를,
**so that** 나중에 프론트엔드에서 확인할 수 있고(Story 1.22), AI 응대가 왜 그렇게 나왔는지
투명하게 알 수 있다.

**전제 조건(충족됨)**: Story 1.20 스파이크 검증 결과, **"응답 전송 후 비동기 백그라운드
분류 호출(fire-and-forget)"** 방식이 최종 채택되었다([스파이크 리포트](../reports/2026-07/2026-07-29_story_1.20_intellidecision_rationale_capture_spike.md)).
구조화 출력(후보 a)은 API가 FunctionCall과 동시 지원하지 않아 기각되었고, 센티널 태그
후행 파싱(후보 b)은 실측 성공률 0%로 기각되었다.

## Acceptance Criteria

1. `self_service_agent_node`의 응대 흐름마다(Tool-calling 경로 + 프롬프트 전용 폴백 경로 모두)
   Story 1.20에서 확정된 방식(**응답 전송 후 비동기 백그라운드 분류 호출**)으로 판단 근거
   (유형 코드 A~I, 근거 요약, 관련 도메인/화면)를 캡처한다. 백그라운드 호출은
   `asyncio.create_task()`로 생성되며, 사용자에게 응답을 전송하는 경로는 이 태스크를
   `await`하지 않는다(즉, 판단 근거 기록은 사용자 응답보다 약 0.7~0.9초 늘어 기록될
   수 있음, Story 1.20 스파이크 실측치).
2. 캡처 실패(모델 호출 실패, 파싱 실패, 타임아웃 등)가 발생해도 **사용자에게 보여줄 실제 응답
   생성·전송 흐름에는 영향을 주지 않는다**(구조적으로 자동 충족됨 — 백그라운드 태스크이므로
   응답 경로와 물리적으로 분리됨, 예외는 태스크 내부에서 흑수하고 `matched_type=unknown`으로
   기록, FR30 요구사항).
3. 캡처 성공 시 `call_data_record` 로그에 `self_service_intellidecision_rationale` 이벤트로
   기록되고, 별도 SQLite 테이블(`self_service_decision_log`, owner/call_id/timestamp/
   matched_type/reasoning_summary/related_domain 컬럼)에도 저장된다.
3-1. 원본 발화 전문(全문)은 저장하지 않고 근거 요약(reasoning_summary, 200자 이내로 절단)만
   저장한다(개인정보 최소 노출 원칙, FR30 명시).
4. `GET /api/self-service/decision-log?owner=&limit=`(읽기 전용, 기본 20건, owner 스코프 강제)
   신규 API가 최근 판단 근거 목록을 최신순으로 반환한다.
5. 당장(비동기) 캡처가 동기적으로 연결되지 않았음(즉 사용자 체감 응답 지연이 거의 0)을
   실측으로 확인한다(NFR6 충족, Story 1.20 스파이크 동기 호출 실측치(약 0.7~0.9초
   추가)와 비교해 이번 구현은 그 지연이 사용자 응답 경로에 전혀 포함되지 않음을 증명).
6. 기존 self_service 회귀 테스트 전체가 그대로 통과하고, 신규 로직에 대한 단위 테스트
   (`test_self_service_decision_rationale.py`)가 추가된다(캡처 성공/실패 양쪽 경로, API
   페이지네이션/owner 격리 포함).

## Dev Notes

- **왜 새 테이블인가(vs 기존 `self_service_config_change_db` 재사용)**: 판단 근거는 "값 변경"이
  아니라 "판단 결과"이므로 의미상 다른 엔티티다. 다만 CRUD 패턴(owner 스코프, 페이지네이션,
  API 인증)은 `self_service_config_change_db.py`/Story 1.9 API를 그대로 복제한다(신규 패턴
  발명 지양).
- **판단 근거 캡처는 절대 판단 로직에 영향을 주면 안 된다**: Story 1.18의 2-hop 지식그래프,
  Story 7.1의 Smart Turn 관측 로깅과 동일하게 "관측 전용 추가"만 한다 — 기존 `_SELF_SERVICE_
  SYSTEM_PROMPT_TEMPLATE`/`_TOOL_USAGE_INSTRUCTION`의 판단 기준 문구는 이 Story에서 건드리지
  않는다(회귀 위험 최소화, CR 원칙).
- Story 1.20에서 선택된 캡처 방식이 (b) 센티널 태그 방식이었다면 `update_history=False`
  또는 사용자 노출 전 정제 단계가 필요했겠지만, 실제로는 (b)가 0% 성공률로 기각되고 (c)의
  비동기 변형이 채택되어 이 리스크 자체가 해당 없음(응답 생성 호출과 분류 호출이 완전히
  분리된 별도 API 요청이라 conversation_history 오염 경로가 없다).
- API 라우터 위치는 기존 `settings_ai_assistant.py`(Story 1.18의 `/intellidecision-policy`
  엔드포인트가 이미 있는 파일) 재사용을 우선 검토 — 신규 라우터 파일 생성은 최후 수단.
