## Story

**As a** 개발자,
**I want** `LLMClient`가 `google-genai` SDK를 사용하도록 전환하여 `thinking_budget=0`이
실제로 적용되게 하고,
**so that** chitchat 등 내부 추론이 필요 없는 응답의 TTFT가 실제로 단축되고, 기존 호출부
(booking_agent.py, self_service_agent.py, classify_intent_node 등)는 코드 변경 없이 그대로
동작한다.

## Acceptance Criteria

1. `LLMClient.__init__`이 `google.genai.Client(api_key=...)`로 클라이언트를 생성하고,
   모델명은 문자열로 보관한다(`genai.GenerativeModel` 인스턴스 생성 제거). [Source: architecture §3]
2. `_thinking_off()`/`_effective_generation_config()`가 `types.GenerateContentConfig` +
   `types.ThinkingConfig(thinking_budget=0)`를 사용하며, 예외로 조용히 무시되지 않는다 —
   실패 시 반드시 `logger.error`(또는 상위 레벨)로 드러나야 한다(PRD FR1, "조용한 실패 금지").
3. `LLMClient`의 8개 공개 메서드(`generate_simple`, `generate_help_items_json`,
   `generate_response`, `generate_response_streaming`, `format_for_customer`,
   `format_hitl_reply_for_customer`, `judge_barge_in`, `judge_usefulness`)의 시그니처와 반환
   타입이 변경되지 않는다(PRD FR2, CR1).
4. `finish_reason` 판별 로직(`generate_response`, `generate_help_items_json`)이 신규 SDK의
   실제 응답 값 타입을 코드로 직접 확인한 뒤, 정수/enum 어느 쪽이든
   `"STOP"|"MAX_TOKENS"|"SAFETY"|"RECITATION"` 문자열로 정규화하는 private 헬퍼를 통해
   처리된다(architecture §3.1). 추측 금지 — 실제 응답 객체를 스크립트로 출력해 확인한 근거를
   Dev Agent Record에 남긴다.
5. 기존 `LLMClient` 관련 단위 테스트가 신규 SDK 응답 형태를 반영해 갱신되고 전부 통과한다.
6. 스파이크 스크립트(`scripts/spike_google_genai_thinking_off.py`)와 동등한 방식으로 실제
   API 호출 시 TTFT가 개선됨을 재확인한다(모델 변경 없이, 이번엔 `LLMClient`를 통해).

## Dev Agent Record

### 구현 요약(2026-07-24)

- **임포트/클라이언트**: `import google.generativeai as genai` → `from google import genai`
  (`genai.Client(api_key=...)`). `self.model`은 신규 `_GenAIModelAdapter`(모듈 레벨 헬퍼 클래스)로
  대체 — `generate_content(contents, generation_config=, stream=)` 동일 시그니처를 유지해
  8개 공개 메서드 본문의 `self.model.generate_content(...)` 호출부는 **단 한 줄도 수정하지
  않았다**(CR1 실증).
- **GenerationConfig → GenerateContentConfig**: 저장소 내 6개 호출부 전부 치환(필드명
  동일이라 kwargs 변경 없음).
- **finish_reason 정규화**: 실제 API 호출로 직접 확인(추측 금지 원칙 준수) —
  `response.candidates[0].finish_reason`은 정수가 아니라 `google.genai.types.FinishReason`
  enum이며 `int(finish_reason)`은 `TypeError`를 낸다(`isinstance(fr, int)` → `False`).
  `.name` 속성으로 `"STOP"`/`"MAX_TOKENS"` 등 문자열을 바로 얻을 수 있어, 신설한
  `_finish_reason_name(response)` 헬퍼로 기존 `fr_map`+`int()` 매핑 3곳을 모두 대체했다.
  `usage_metadata`의 `candidates_token_count`/`prompt_token_count` 필드명은 신규 SDK에서도
  동일해 변경 불필요함을 실제 응답 객체로 확인.
- **실 API 검증(로컬, `C:\work\gemini-api-key.json`의 키 사용)**:
  - `generate_response()`: "안녕하세요! 오늘 날씨가 참 좋네요." → 1.31초(스파이크의 `thinking_budget=0`
    실측 0.77초와 동일 자릿수, 기존 경로가 실제로 6~9초대였던 것과 대비해 확연한 개선).
  - `generate_response_streaming()`: 문장 단위 yield 정상 동작 확인.
  - `judge_usefulness()`: `finish_reason=STOP`으로 정상 로깅됨(과거 `int()` 매핑이었다면
    `TypeError`로 죽었을 지점) — 실제 JSON 추출 결과도 정상.
  - `judge_barge_in()`: "맞장구"/"interruption" 판별 정상 동작.
