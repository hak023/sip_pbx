## 구현 완료 요약 (2026-07-23)

사용자가 "응 진행해줘"로 결정 지원 리포트의 **축소된 권장 설계**(신규 레지스트리 모듈/API/5번째 탭 대신,
기존 `settings_catalog`·`/catalog`·`/screen-graph` 재사용)을 승인해 즉시 구현했다. 상세는 아래 "최종 구현
내용"을 참고하고, 원래 계획단계에서 논의된 옵션들은 이력 보존 목적으로 그대로 아래에 남겨둔다.

## Story

**As a** 테넌트 관리자,
**I want** AI가 안내하는 "할 수 있는 일" 목록과 프론트엔드 도움말 화면에 표시되는 능력 목록이
항상 실제 시스템 상태(카탈로그·화면·Tool 구성)와 정확히 일치하기를,
**so that** Epic 2에서 설정 카탈로그가 동적으로 바뀌어도 안내 문구가 낡은 채로 남지 않는다.

## 배경

[2026-07-23 리서치 리포트](../reports/2026-07/2026-07-23_intellidecision_enhancement_research.md)
§5에서 발견한 구조적 문제: `settings_catalog.py`(7개 도메인)·`screen_graph.py`(화면 정보)·
`tools.py`(`SELF_SERVICE_TOOLS`)는 이미 각각 실행 시점에 조회 가능한 실제 데이터이지만, 유형
C(도움 요청, Story 1.15)의 능력 안내 문구와 매뉴얼 `self-service-manual-content.md` §9는
**사람이 수작업으로 유지하는 정적 텍스트**다. Story 1.15에서 실제로 §9가 이미 구현된 기능을
"향후 지원되면"이라는 미래형으로 방치해 stale해진 사례가 있었다. Epic 2(Story 2.1~2.8)가
"카탈로그·Screen Graph 메타데이터를 코드 상수 → DB 동적 로딩"으로 전환한 것과 동일한 철학을
**능력 소개 자체**에도 적용해, 코드가 유일한 진실 소스가 되도록 재구성하는 것이 이 Story의 목표다.

사용자가 "제안 2는 frontend 반영까지 필요해 보인다"고 판단했으므로, 백엔드 프롬프트 반영에
그치지 않고 **프론트엔드 열람 화면까지 포함한 계획**으로 수립한다(단, 이번 Story는 계획만 —
구현은 후속 세션에서 사용자 승인 후 진행).

## 범위(계획 단계 — 확정 아님, 검토용)

### 1. 백엔드: 능력 레지스트리 함수 신설

- **위치(안)**: `src/ai_voicebot/self_service/capabilities.py`(신규 모듈).
- **핵심 함수(안)**: `describe_dynamic_capabilities(owner: str) -> dict`
  - `settings_catalog.list_domains()` + `get_domain_schema(domain)` + `domain_writable_fields(domain)`
    → 도메인별 "조회 가능"/"쓰기 가능(writable_fields 존재)" 여부를 실시간 판별.
  - `screen_graph.list_all_screens()` → 화면 안내 가능 도메인 목록.
  - `tools.SELF_SERVICE_TOOLS`에서 정적 메타(이름/설명 docstring 첫 줄) 추출 → 통계·통화 이력
    NLQ·온보딩·(Story 1.16 신규) 실행 취소 등 Tool 기반 능력 목록.
  - 반환 형태(안): `{"queryable_domains": [...], "writable_domains": [...],
    "screen_guided_domains": [...], "tool_capabilities": [{"name", "summary", "example"}, ...]}`
    — 예시 발화(`example`)는 초기에는 소규모 정적 매핑(Tool 이름 → 예시 1개)으로 시작하고,
    이후 필요 시 매뉴얼 Q&A와 연결(과욕 금지 원칙, MVP는 정적 예시 매핑으로 충분).
- **캐싱**: Epic 2의 `catalog_config_loader.get_cached_config()`와 동일 원칙 — 카탈로그
  버전이 바뀌지 않으면 재계산하지 않고, `invalidate_cache()`가 호출되면(Story 2.5 업로드/롤백
  API) 능력 레지스트리 캐시도 함께 무효화한다. (동일 모듈에 캐시를 두거나, `catalog_config_loader`에
  훅을 추가하는 두 방식을 후속 설계 단계에서 비교.)

### 2. 백엔드: 시스템 프롬프트 연동 (유형 C 대체)

- `self_service_agent.py`의 유형 C 규칙(Story 1.15, 항목 7)에서 **정적 하드코딩 카테고리
  목록**을 제거하고, `_SELF_SERVICE_SYSTEM_PROMPT_TEMPLATE`에 신규 변수 `{capability_section}`을
  추가해 `describe_dynamic_capabilities()` 결과를 텍스트로 조립해 주입.
- **회귀 리스크 관리(계획 단계에서 반드시 확인할 사항)**: 유형 C의 AC(Story 1.15) — "최소 3개
  카테고리를 구체적 예시 발화와 함께 안내" — 를 동적 텍스트도 동일하게 만족해야 한다. 실서버
  검증 시 하드코딩 버전과 동적 버전의 실제 응답 품질을 A/B 비교할 것을 후속 Story의 필수
  검증 항목으로 포함한다.

### 3. 백엔드: 신규 API 엔드포인트 (프론트엔드 노출용)

- **위치(안)**: `src/api/routers/settings_ai_assistant.py`에 기존 4개 엔드포인트
  (`/docs`, `/catalog`, `/screen-graph`, `/catalog-config/*`)와 동일 패턴으로
  `GET /api/settings/ai-assistant/capabilities` 신규 추가.
- 응답은 §1의 `describe_dynamic_capabilities()` 결과를 그대로 JSON으로 노출(백엔드 프롬프트와
  프론트엔드가 **동일 함수를 단일 진실 소스로 공유** — Epic 2의 "export_static_snapshot()을
  마이그레이션 스크립트와 API가 공유"한 설계 원칙과 동일).

### 4. 프론트엔드: 신규 탭 "AI가 할 수 있는 일"

- **위치**: `frontend/app/settings/ai-assistant/docs/page.tsx`의 기존 4탭
  (`qa`/`catalog`/`screen`/`manage`)에 5번째 탭 `capabilities` 추가(탭 배열
  `(["qa", "catalog", "screen", "manage"] as Tab[])`에 `"capabilities"` 추가하는 패턴 재사용).
- 신규 탭은 §3 API를 호출해 도메인별 조회/쓰기 가능 여부, Tool 기반 능력(통계·통화 이력 NLQ·
  실행 취소 등)을 표 또는 카드 UI로 렌더링 — **하드코딩 문구 없이 API 응답을 그대로 렌더링**
  (기존 `catalog`/`screen` 탭이 이미 이 패턴).
- 관리자가 "AI에게 뭘 물어볼 수 있는지" 대시보드에서도 확인 가능해져, 유형 C(전화로 물어보기)와
  프론트엔드 열람이 동일한 데이터 소스로 일관성을 갖는다(FR14가 Screen Graph에 대해 이미 확립한
  패턴을 능력 목록에도 적용).

### 5. 매뉴얼 콘텐츠 §9 역할 재정의

- §9는 "능력 목록 나열"이 아니라 **동적으로 대체되지 않는 정적 설명**(셀프서비스 모드 진입
  방법, 모드 자체의 개념 설명)만 남긴다. 능력 열거는 §1(레지스트리)이 단일 진실 소스가 된다.
- RAG가 §9를 검색 결과로 반환하는 경우에도 "구체적 능력은 다양하니 직접 '뭘 할 수 있어?'라고
  물어보세요"처럼 레지스트리 기반 응답(유형 C)으로 유도하는 짧은 안내만 남긴다.

## 2026-07-23 추가 분석 — 권장안 갱신(범위 축소)

[결정 지원 리포트](../reports/2026-07/2026-07-23_capability_registry_decision_options.md)에서
`GET /catalog`·`GET /screen-graph` API가 **이미 도메인별 조회/쓰기/화면 안내 정보를 실시간으로
프론트엔드에 노출하고 있음**을 확인했다. 즉, 원래 계획한 "완전 신규 레지스트리+API+5번째 탭"은
기존 정보와 중복이 크다. 실제 공백은 **Tool 기반 능력 5종**(통계 조회/통화 이력 검색/최다 발신
집계/미응답 조회/실행 취소)뿐이다. 권장 축소 설계:

1. 캐시 계층 신설 없이 매 요청 재계산(기존 Epic 2 캐시 위에 얹는 캐시라 무효화 버그 리스크만 늘림).
2. Tool 5종 예시 발화는 정적 매핑(코드 상수)으로 관리 — 매뉴얼 자동 연결은 기각.
3. 프론트엔드는 신규 5번째 탭 대신 기존 `qa` 탭에 "Tool 기반 능력" 소단면만 추가.
4. 유형 C 프롬프트는 원시 dict를 그대로 넣지 않고, 기존 `_format_*` 함수들과 동일한 패턴의
   포맷터로 자연스러운 텍스트를 조립해 주입(품질 저하 방지, 실서버 A/B 필수).
5. 매뉴얼 §9는 완전 삭제 대신 "직접 물어보라"는 유도 문구로 축소.

상세 근거·대안 비교는 결정 지원 리포트를 참고. **이 갱신도 계획 단계이며 코드 변경 없음.**

## 최종 구현 내용 (2026-07-23, 사용자 승인 후 착수·완료)

### Acceptance Criteria (실제 구현 기준)

1. 유형 C(도움 요청) 응답의 설정 조회/변경 가능 도메인 목록이 `settings_catalog`에서 실시간
   조회되어, 카탈로그가 바뀌면(Epic 2 핫 리로드) 서버 재시작 없이 다음 프롬프트 조립부터
   자동 반영된다.
2. Tool 기반 능력(통계·통화 이력·온보딩·실행 취소)은 정적 매핑으로 안내되며, 존재하지 않는
   기능을 지어내지 않는다.
3. 능력 목록 생성이 예외를 던지거나 도메인이 0개면 Story 1.15의 정적 문구로 즉시 폴백한다
   (회귀 방지 안전망).
4. 프론트엔드 도움말 페이지의 "이용 매뉴얼 Q&A" 탭에 Tool 기반 능력 5종이 정적으로 안내된다
   (신규 API·신규 탭 없이 기존 페이지에 소단면만 추가).
5. 매뉴얼 §9는 능력 목록을 나열하지 않고 "직접 물어보라"는 유도 문구로 축소되어, 이번처럼
   다시 stale해질 여지를 구조적으로 제거한다.
