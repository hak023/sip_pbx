## Story

**As a** 지식베이스를 운영하는 테넌트 관리자,
**I want** 마크다운/일반 텍스트/PDF/OpenAPI 문서를 웹 화면에서 업로드하고 조회·수정·삭제할 수 있고,
**so that** 코드 배포나 개발자 개입 없이 지식베이스를 직접 구성할 수 있다.

## Acceptance Criteria

1. `SourceAdapter` 프로토콜(Story 1.25)에 `PdfDocumentAdapter`(PDF 텍스트 추출 후 문단 단위 청킹)와 `OpenApiSpecAdapter`(OpenAPI JSON/YAML의 각 endpoint를 Q&A 유사 페어로 변환)가 신규 구현체로 추가된다. 기존 `MarkdownManualAdapter`는 변경되지 않는다.
2. 신규 API `POST /api/knowledge-base/documents`(업로드), `GET /api/knowledge-base/documents`(목록, owner/domain_tag/source_type 필터), `GET /api/knowledge-base/documents/{document_id}`(단건+청크 목록), `PUT /api/knowledge-base/documents/{document_id}`(메타데이터/본문 수정 → 재색인), `DELETE /api/knowledge-base/documents/{document_id}`(삭제, 색인에서도 제거)가 추가된다.
3. 업로드 문서는 공통 메타데이터(`document_id`, `owner`, `domain_tags: List[str]`, `source_type`, `version`, `uploaded_at`, `uploaded_by`)를 가지며, `owner` 필터 기반 테넌트 격리를 통과해야 한다(NFR2).
4. `domain_tags`는 자유 텍스트 배열이며, 기존 self_service 도메인(persona 등)과의 하위 호환은 `domain_tags=["persona"]`처럼 매핑되어야 한다 — 기존 매뉴얼 Q&A 52건의 조회/응대 동작에 회귀가 없어야 한다.
5. 프론트엔드 `settings/ai-assistant/docs` 페이지에 "지식 업로드" 탭(6번째)이 추가된다: 파일 업로드(드래그 앤 드롭)+메타데이터 폼+업로드된 문서 목록(수정/삭제 버튼). 기존 탭의 카드/표 UI 패턴을 재사용하고 신규 npm 의존성을 추가하지 않는다.
6. 기존 `knowledge_service.add_knowledge()`/`list_knowledge()`/`get_all_knowledge()`를 재사용하며, 벡터 스토어(ChromaDB) 자체를 교체하지 않는다.
7. PDF/OpenAPI 파싱 실패 시 명확한 오류 메시지를 반환하고 부분 색인 상태를 남기지 않는다(NFR8).

## Dev Notes

- **왜 PDF/OpenAPI를 1단계부터 포함하는가**: 사용자가 명시적으로 "처음부터 PDF/OpenAPI까지 포함"을 선택함(2026-08-04 계획 확인) — 마크다운/텍스트로 축소한 축소판 로드맵은 폐기되었다.
- **회귀 위험 관리**: Story 1.25가 이미 `SourceAdapter` 프로토콜과 `MarkdownManualAdapter`를 도입해뒀으므로, 이번 Story는 신규 어댑터 2종을 "추가"하는 것이지 기존 어댑터를 변경하지 않는다 — 기존 색인 파이프라인 무변경 원칙(NFR7과 동일 원칙 적용).
- **CRUD API 설계 원칙**: 신규 벡터 스토어/신규 DB 스키마를 최소화하고 기존 `knowledge_service` 함수를 최대한 재사용한다. 필요한 신규 부분은 "문서 단위 lifecycle 관리"(생성/수정/삭제 시점 관리)뿐이다.
