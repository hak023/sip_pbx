# Story 1.11: Screen Graph 구축 및 화면 안내형 응대

## Status

Done

## Story

**As a** 테넌트 관리자,
**I want** 설정 기능이나 방법을 물을 때 AI가 실제 프론트엔드 화면을 설명하면서 안내해주기를,
**so that** 설정화면을 직접 열어보지 않아도 어디를 어떻게 클릭해야 하는지 대화만으로 파악할 수 있다.

## Acceptance Criteria

1. 설정 카탈로그 도메인(persona/ai-escalation/call-control/chat-relay/contacts/general/integrations)을 프론트엔드 라우트·화면 내 UI 요소와 연결하는 **경량 지식 그래프(Screen Graph)**가 신규 구축된다(별도 그래프 DB 없이 `settings_catalog.py`와 동일한 정적 레지스트리 패턴).
2. 프론트엔드 전용 화면이 없는 도메인(예: persona)은 화면 정보 없이 등록된다(존재하지 않는 화면을 안내하지 않음).
3. `self_service_agent_node`가 RAG 검색 결과의 `related_domain`으로 Screen Graph를 조회해 화면 안내 정보를 시스템 프롬프트에 주입한다(GraphRAG의 Local Search 패턴 재현 — 매뉴얼 RAG → 도메인 → 화면 1-hop 확장).
4. 화면 정보가 있는 경우 탐색성(IntelliDecision 유형 A) 응답에 화면 안내가 포함되고, 없는 경우 기존처럼 매뉴얼 텍스트 설명만 제공된다.

### Integration Verification

- **IV1**: Screen Graph 조회 실패/예외가 전체 응답 흐름을 중단시키지 않는다(best-effort, IntelliDecision 힌트와 동일한 안전 원칙).
- **IV2**: 실행성(Story 1.8/1.10 유형 B) 응답 흐름은 화면 안내 주입과 무관하게 회귀 없이 동작한다.

## Dev Notes

### 리서치 근거

본 Story는 [SELF_SERVICE_SCREEN_GUIDED_GRAPHRAG_RESEARCH.md](../design/SELF_SERVICE_SCREEN_GUIDED_GRAPHRAG_RESEARCH.md)의
리서치 결론을 그대로 구현한다. Full GraphRAG(microsoft/graphrag — LLM 엔터티 추출 + Leiden
클러스터링 + 커뮤니티 요약)는 채택하지 **않는다** — 코퍼스 규모(매뉴얼 52건, 도메인 7개, 화면
8개)가 작고 관계가 이미 알려져 있어(수작업 매뉴얼 저작 시점부터 도메인이 분류됨) LLM 자동 추출이
불필요한 환각 리스크만 추가하기 때문이다. 대신 GraphRAG의 "Local Search"(엔터티에서 이웃으로
팬아웃) 아이디어만 차용해 `settings_catalog.py`와 동일한 정적 레지스트리로 구현한다.

### Previous Story Insights

- `manual_indexer.py`(어제 구현)가 이미 매뉴얼 Q&A마다 `related_domain` 메타데이터를 ChromaDB에
  저장하고 있다 — 이 Story는 이 기존 태그를 **그대로 재사용**하며 매뉴얼 재색인이 필요 없다.
- `intent_tier.py`(Story 1.10)의 "예외를 삼키고 항상 안전한 기본값 반환" 설계 원칙을 그대로
  따른다 — Screen Graph 조회도 반드시 best-effort여야 한다(IV1).

### Technical Constraints

- **NFR1**: Screen Graph 조회는 순수 딕셔너리 lookup(LLM 호출 없음) — 첫 응답 지연에 영향 없어야 한다.

  수작업으로 등록해야 한다(매뉴얼 작성 원칙과 동일).
