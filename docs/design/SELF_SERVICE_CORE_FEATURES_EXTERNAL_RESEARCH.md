## 1. IntelliDecision (발화 유형 판단·응대 전략, Story 1.2 FR12 + 1.15~1.19)

### 1.1 개념·학술 매핑

우리 구현은 사용자 발화를 **탐색성(exploratory/informational) vs 실행성(transactional)**, 그리고 이후 확장된 도움요청·정정·Undo·모호성해소 등 총 9개 유형으로 분류해 응대 전략을 분기한다. 이는 학술적으로 두 개의 독립된 연구 계보와 맞닿아 있다.

1. **Dialog Act(대화행위) 이론**: 발화를 "atomic unit of conversation"으로 보고 STATEMENT/QUESTION/REQUEST 등으로 태깅하는 화용론(pragmatics) 연구 분야(Wikipedia "Dialog act"; Stolcke et al. 2000, *Dialogue Act Modeling for Automatic Tagging and Recognition of Conversational Speech*, Computational Linguistics 26(3) — 42종 태그 분류 체계). 우리의 유형 A(탐색성)/B(실행성) 구분은 이 태그 체계 중 "정보 요청(Info-request)"과 "행동 요청(Action-directive)"의 이분법과 사실상 동일한 개념이다.
2. **정보성(informational) vs 거래성(transactional) 검색의도**: 웹검색/대화형 AI 분야에서 널리 쓰이는 이분법으로, "궁금해서 묻는다"와 "실행을 원한다"를 구분해 서로 다른 파이프라인으로 라우팅하는 것이 표준적인 접근이다.
3. **대화 수리(Conversation Repair)**: 유형 D(정정)/F(모호성 해소)/H(반복요청)는 대화 분석(Conversation Analysis)의 "repair" 개념(자기수정, 명확화 요청)에 해당한다.

### 1.3 산업 적용 사례

- **Rasa (오픈소스 대화형 AI 프레임워크)**: `Rules`/`Forms`로 명시적 정책을 YAML로 선언하고, `Stories`로 학습 기반 정책을 병행하는 하이브리드 구조. "정책이 프롬프트 산문이 아니라 선언적 데이터"라는 점에서 우리가 Story 1.18/1.19로 도달한 방향(정책 레지스트리+자동 렌더링)과 유사한 철학.
- **Amazon Lex / Alexa Conversations**: 슬롯필링 후 "confirmation prompt"로 실행 전 확인하는 패턴이 표준(우리 유형 B의 "확인 발화 후 실행"과 동일). Alexa Conversations는 대화 시뮬레이션(dialog simulator)으로 다양한 발화 변형에 대해 정책이 일관되게 동작하는지 사전 검증하는 도구를 제공 — 우리는 이 역할을 회귀 테스트(`master-qa.md`)로 수행 중.
- **Google Dialogflow CX**: "Intent"와 "State Handler"를 명시적으로 분리한 상태 기계(state machine) 구조 — 우리의 유형별 분기가 결국 암묵적 상태 기계를 자연어 프롬프트로 흉내 내고 있는 셈이라는 비교가 가능.

## 2. 매뉴얼 RAG 연동 (Story 1.3)

### 2.1 개념·학술 매핑

**Retrieval-Augmented Generation(RAG)**은 Lewis et al. (2020), *Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks* (NeurIPS 2020, arXiv:2005.11401)에서 정의된 개념으로, 파라메트릭 메모리(LLM 가중치)와 비파라메트릭 메모리(외부 문서 인덱스)를 결합해 사실 기반 응답을 생성하는 구조다. 우리 구현(`doc_type=self_service_manual` + owner 필터 + ChromaDB 벡터 검색)은 이 원형 정의 그대로다.

### 2.2 연구자료

- Lewis et al. (2020) — RAG 원 논문. 검색된 passage 조건화가 파라메트릭 전용 seq2seq보다 사실성(factuality)이 높음을 실증.
- Microsoft **GraphRAG**(공식 문서, 이미 저장소 리서치에서 2회 검토·기각) — 엔터티 자동추출+Leiden 클러스터링, 대규모 비정형 데이터에 적합. 우리 규모(매뉴얼 Q&A 52건)에는 과설계로 재확인됨(§3.1 참고, 아래 5번 항목과 교차).
- Anthropic *Building Effective Agents* — "augmented LLM"(retrieval+tools+memory)을 에이전트의 기본 빌딩블록으로 제시, RAG를 별도 아키텍처가 아니라 LLM 호출의 한 "증강" 요소로 취급.

### 2.3 산업 적용 사례

- 고객지원 챗봇(Intercom Fin, Zendesk AI 등)이 표준적으로 "지식베이스 문서 임베딩 + 검색 + LLM 요약 응답" 구조를 채택 — 우리의 "매뉴얼 RAG + owner 필터"와 동일 패턴.
- 멀티테넌트 SaaS(Notion AI, Slack AI 등)는 테넌트별 문서 격리를 위해 임베딩 인덱스에 tenant_id 메타데이터 필터를 반드시 포함 — 우리 IV1(테넌트 고객용 RAG와 완전 분리)과 동일한 보안 요구사항.

## 3. 자동설정 Tool-calling (Story 1.6, FR6)

### 3.1 개념·학술 매핑

**LLM Function/Tool Calling**은 모델이 자연어 대신 구조화된 함수 호출(이름+인자)을 생성하도록 하는 메커니즘으로, OpenAI(2023-06 Function Calling GA), Google Gemini, Anthropic Claude가 모두 유사한 JSON Schema 기반 선언 방식을 채택했다. 우리 구현(`booking_gemini_fc.py`)은 Gemini 네이티브 FC를 사용한다.

### 3.2 연구자료·공식 문서

- Google, *Gemini API 함수 호출* 공식 문서(ai.google.dev/gemini-api/docs/function-calling) — 함수 선언(JSON Schema 하위집합)→모델 호출→함수 실행(애플리케이션 책임)→결과 재전송의 4단계 표준 흐름. 이는 우리 `_run_self_service_tool_loop()`의 구조와 정확히 일치.
- 동 문서의 "권장사항": 활성 Tool 집합을 10~20개 이내로 유지 — 우리 `SELF_SERVICE_TOOLS`(현재 9개)는 이 권고 범위 내.
- Anthropic *Building Effective Agents* Appendix 2, "Prompt Engineering your Tools" — 도구 설명·파라미터명을 "주니어 개발자를 위한 좋은 docstring"처럼 작성하라는 권고. 우리의 `_build_writable_fields_hint()`(도메인별 실제 writable 필드명을 동적 docstring 삽입, 2026-07-15 수정)가 정확히 이 원칙을 실천한 사례.

### 3.3 산업 적용 사례

- **LangChain/LangGraph**: `bind_tools()` 추상화로 여러 LLM 벤더의 Tool-calling API를 통일된 인터페이스로 제공 — 우리 저장소는 이 경로가 `LLMClient`의 구조적 한계로 항상 실패해(`_chat_model` 속성 부재) Gemini 네이티브 FC로 직접 폴백하는 특이 사례(2026-07-15 발견).
- **Model Context Protocol(MCP, Anthropic)**: 도구를 표준 프로토콜로 외부화해 여러 클라이언트가 재사용 가능하게 하는 최신 트렌드 — 우리의 사내 전용 Tool 레지스트리(`SELF_SERVICE_TOOLS`)와 대비되는 "범용 프로토콜화" 방향.

### 3.4 상용 레퍼런스 비교

## 4. 설정 카탈로그 (Story 1.4, FR5/FR6/FR11)

### 4.1 개념·학술 매핑

"설정 항목을 코드가 아니라 데이터(레지스트리)로 등록해 신규 도메인 추가 시 코드 배포 없이 확장 가능하게 한다"는 아이디어는 소프트웨어 공학의 **플러그인 아키텍처(Plugin Architecture)**, 또는 **메타데이터 기반 동적 폼(Metadata-driven / Schema-driven UI)** 패턴에 해당한다.

### 4.2 연구자료·산업 사례

- **Kubernetes CRD(Custom Resource Definition)**: 스키마를 데이터(YAML)로 등록하면 API가 자동으로 검증·CRUD를 지원하는 패턴 — 우리의 `settings_catalog.py`(도메인·필드·writable 여부를 데이터로 등록)와 철학적으로 동일.
- **Salesforce Metadata-Driven Architecture**: 커스텀 필드·객체를 코드 배포 없이 메타데이터로 정의해 런타임에 UI·API가 자동 반영 — "설정 카탈로그 등록만으로 자동설정 Tool이 인식"(FR11)이라는 우리 요구사항과 사실상 동일한 목표.
- **JSON Schema 기반 동적 폼 생성기**(react-jsonschema-form 등 오픈소스) — 스키마로부터 폼 UI를 자동 생성하는 표준적 접근, 우리 카탈로그의 "필수/옵션 스키마 동적 조회"(FR6)와 대응.

### 4.3 상용 레퍼런스 비교

| 시스템                            | 화이트리스트/보안 모델                                                                                          | 우리와의 차이                                                             |
| --------------------------------- | --------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| **우리 시스템**                   | `_GET_FN_REGISTRY`/`_UPDATE_FN_REGISTRY` 코드 화이트리스트 + DB는 메타데이터만(RCE 방지, Epic 2 핵심 설계 결정) | 실행 로직은 코드에, 메타데이터만 동적 — 가장 보수적인 설계                |
| **Kubernetes CRD**                | Admission Webhook으로 스키마 검증, 실행 로직은 컨트롤러(코드)에 위치                                            | 동일한 "데이터는 동적, 실행은 정적 코드" 원칙                             |
| **Salesforce 완전 노코드 플랫폼** | 로우코드 실행 로직(Flow, Apex 트리거)까지 메타데이터화                                                          | RCE 리스크가 더 크고 우리는 이를 명시적 Non-Goal로 배제(설계 결정과 일치) |

## 6. 통계 자연어 질의 (Story 1.7, FR7 — PRD상 Story 번호는 1.7 목표 범위, 실제 구현은 이후 Story 1.13/1.15 등으로 확장)

### 6.1 개념·학술 매핑

자연어 질문을 구조화 데이터 질의로 변환하는 문제는 학술적으로 **NL2SQL(Natural Language to SQL)** 분야에 해당한다(예: Spider, WikiSQL 벤치마크). 다만 우리 구현(FR7/FR15, NFR5)은 "LLM이 직접 SQL을 생성"하는 방식이 아니라, **사전 정의된 Tool 함수(집계/검색/카운트) 중 하나를 LLM이 선택·인자화**하는 방식 — 이는 NL2SQL보다는 **Semantic Parsing to API calls**(자연어→고정 API 호출)에 더 가깝다.

### 6.2 연구자료·비교

- Spider/WikiSQL 계열 NL2SQL 연구는 "임의의 SQL을 생성"하는 유연성이 강점이지만 SQL 인젝션·성능 예측 불가 리스크가 있음.
- 우리의 "구조화 검색·집계 Tool 화이트리스트" 방식(NFR5)은 LangChain의 "SQL Agent"보다 안전하지만 유연성이 낮음 — 이는 저장소가 이미 NFR5에서 의도적으로 선택한 트레이드오프(신규 벡터 임베딩·임의 SQL 생성 모두 배제)로, 보안 우선 설계 원칙과 일치.

### 6.3 상용 레퍼런스

| 제품                                                               | 방식                                                                            | 우리와의 차이                                                            |
| ------------------------------------------------------------------ | ------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| **우리 시스템**                                                    | 고정 Tool(검색/집계/미응답 조회) 화이트리스트, LLM은 인자 채움+결과 요약만 담당 | SQL 인젝션 원천 차단, 신규 질의 유형 추가 시 Tool 추가 필요(유연성 낮음) |
| **LangChain SQL Agent / Text2SQL 상용 제품(예: ThoughtSpot Sage)** | LLM이 직접 SQL(또는 유사 질의) 생성                                             | 유연성 높으나 프롬프트 인젝션발 임의 쿼리 위험 관리 필요                 |

### 6.4 대안 비교·장단점

| 접근                        | 장점                        | 단점                                                                                           |
| --------------------------- | --------------------------- | ---------------------------------------------------------------------------------------------- |
| **Tool 화이트리스트(현재)** | 보안 안전, 예측 가능한 성능 | 신규 질의 패턴마다 Tool 추가 개발 필요                                                         |
| **LLM 직접 SQL 생성**       | 임의 질의 대응 가능         | SQL 인젝션/성능 폭주 리스크, 멀티테넌트 환경에서 owner 필터 누락 위험(보안상 우리 원칙과 배치) |

## 7. 셀프콜/셀프문자 감지 및 전용 대화 레인 (Story 1.1/1.2 기반부)

### 7.1 개념·학술 매핑

이 기능은 PBX/SIP 도메인에 특화된 "발신자-착신자 동일 테넌트 매핑에 따른 세션 분기"로, 범용 학술 문헌은 상대적으로 적다. 가장 가까운 일반 개념은 **컨텍스트 기반 라우팅(Context-aware Routing)** — Anthropic의 Routing 워크플로 패턴을 세션 메타데이터(발신/수신 owner) 기준으로 적용한 사례로 볼 수 있다.

### 7.2 산업 사례

- 콜센터 IVR 시스템의 "내선 간 통화 특수 처리"(예: 관리자 내선↔대표번호 통화 시 관리 모드 진입)가 유사한 선례. 다만 이는 대부분 클로즈드 벤더 제품(Genesys, Avaya 등)의 내부 구현이라 공개 연구자료는 희소.

### 7.3 비교·장단점

이 기능은 도메인 특화도가 높아 "타 대안과 비교"보다는 **우리 자체의 안전장치 설계**(IV1: 플래그 미설정 시 항상 기존 경로로 폴백)가 핵심 장점이다. 일반적 대안으로는 "별도 채널(전용 앱/웹 콘솔)"이 있으나, 이는 PRD의 핵심 목표("전화/문자만으로 접근")와 정면으로 배치되어 비교 대상에서 제외한다.

## 8. 종합 결론 및 후속 검토 제안

1. **IntelliDecision**은 학술적으로 최신 트렌드(LLM 기반 의도 분류, Routing 워크플로)와 정합하나, **판단 근거 로깅(설명가능성) 강화**가 Dialogflow CX 등 상용 제품 대비 유일한 개선 여지로 확인됨 — 후속 Story 후보로 제안.
2. **RAG/설정 카탈로그**는 이미 업계 표준 패턴(경량 벡터검색, 메타데이터 기반 플러그인 아키텍처)을 정확히 따르고 있으며, Full GraphRAG/완전 노코드 등 과설계 대안은 재차 기각이 타당함이 확인됨.
3. **Tool-calling**은 벤더 SDK 마이그레이션 이력(google-generativeai→google-genai)에서 보듯 벤더 종속 리스크가 실존하나, MCP 표준화는 현재 규모에서 이득 대비 비용이 낮아 보류가 합리적.
4. **통계 질의**는 보안(SQL 인젝션 방지) 우선 설계가 업계의 "LLM 직접 SQL 생성" 트렌드보다 이 멀티테넌트 시스템에는 더 적합한 선택으로 재확인됨.

**다음 단계**: 사용자가 위 4개 개선 제안(특히 IntelliDecision 판단 근거 로깅) 중 착수를 원하는 항목이 있으면 BMAD 절차(PRD 갱신→architecture→story)로 진행 가능.
