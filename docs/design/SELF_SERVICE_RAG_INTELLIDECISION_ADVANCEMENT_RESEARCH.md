## 0. 문제 재정의 — 왜 "과설계" 판단이 지금은 바뀌어야 하는가

2026-07-16/27 리서치는 반복적으로 "Full GraphRAG는 노드 100개 미만·매뉴얼 Q&A 52건 규모엔 과설계"라고
결론지었다(§2.4, `SELF_SERVICE_SCREEN_GUIDED_GRAPHRAG_RESEARCH.md`). 이 결론 자체는 **"현재 데이터
규모" 전제 하에서는 여전히 유효**하다. 그러나 이번 요구사항은 규모가 아니라 **미래에 유입될 데이터
종류의 다양성**(도움말 Q&A뿐 아니라 API/Tool 문서, 운영 매뉴얼, FAQ, 정책 문서 등 이종 소스)과
**그 파이프라인이 특정 벤더(ChromaDB+Gemini 임베딩)에 하드코딩되지 않아야 한다는 것**을 문제 삼고
있다. 즉 "그래프 알고리즘의 복잡도"가 아니라 **"수집(ingestion) 파이프라인의 확장성과 관측성"**이
핵심 공백이다 — 이 둘은 서로 다른 축이므로, 과거 결론(그래프 알고리즘 기각)과 상충하지 않는다.

## 1. 시장 동향 — 벤더 비종속 RAG 수집 계층

### 1.1 핵심 개념: "Modular RAG" (Naive → Advanced → Modular)

Gao et al. (2023/2024 개정, arXiv:2312.10997) *Retrieval-Augmented Generation for Large Language
Models: A Survey*는 RAG 아키텍처의 진화를 3단계로 정리한다.

| 단계             | 특징                                                                                                                                                         | 우리 저장소 현황                                                                      |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------- |
| **Naive RAG**    | 청크 분할→임베딩→유사도 검색→프롬프트 삽입, 단일 파이프라인 하드코딩                                                                                         | 현재 `manual_indexer.py`(§9 태그 파싱)+ChromaDB — 사실상 이 단계                      |
| **Advanced RAG** | 검색 전 쿼리 재작성/라우팅, 검색 후 재순위화(rerank)·압축을 **전용 모듈**로 분리                                                                             | `rewrite_query_node`는 있으나 doc_type/owner 필터링에 그침, 재순위화 모듈 없음        |
| **Modular RAG**  | 색인(Indexing)·전검색(Pre-retrieval)·검색(Retrieval)·후검색(Post-retrieval)·생성(Generation)을 **독립 교체 가능한 모듈**로 분리, 모듈 간 인터페이스만 표준화 | 목표 상태 — 사용자가 요구하는 "데이터를 넣으면 RAG가 구성된다"는 이 모듈화가 전제조건 |

**핵심 시사점**: 벤더 비종속성은 "임베딩 모델을 바꿀 수 있다"는 것뿐 아니라, **소스 문서의 형식(마크다운
Q&A, OpenAPI 스펙, PDF 매뉴얼, Tool JSON Schema 등)마다 다른 파서(loader)를 붙였다 뗐다 할 수 있는
"Indexing 모듈의 플러그인화"**를 의미한다. 이는 LangChain의 `DocumentLoader`/LlamaIndex의
`Reader`가 채택한 표준 패턴과 동일하다 — 소스별 로더가 공통 `Document(page_content, metadata)`
객체로 정규화되어 이후 파이프라인(청킹·임베딩·색인)은 소스 종류를 몰라도 되게 만든다.

### 1.2 Contextual Retrieval — 청크가 원본 맥락을 잃는 문제 해결 (Anthropic, 2024-09)

Anthropic *Introducing Contextual Retrieval*(2024-09)은 우리 문제의식과 정확히 맞닿는 실증 연구다.

- **문제**: 문서를 청크로 쪼개면(현재 우리 `manual_indexer.py`의 섹션 단위 분할도 동일 리스크) 개별
  청크가 "이게 어느 문서, 어느 도메인 얘기인지"를 잃어버려 검색 실패율이 올라간다.
  예: "매출이 전분기 대비 3% 늘었다"만 남으면 어느 회사·어느 분기인지 알 수 없음.
- **해결(Contextual Retrieval)**: 청크를 임베딩/BM25 색인하기 **전에** LLM으로 "이 청크가 전체
  문서에서 어떤 맥락인지"를 50~100 토큰으로 요약해 청크 앞에 자동으로 붙인다(수작업 아님, 전량 자동화).
- **실증 효과**: Contextual Embeddings만으로 top-20 검색 실패율 35%↓(5.7%→3.7%), Contextual BM25까지
  결합 시 49%↓(→2.9%), 재순위화(rerank)까지 추가 시 **67%↓(→1.9%)**.
- **우리와의 연결**: `manual_indexer.py`의 `{domain: xxx}` 태그(Story 2.8)는 "수작업 메타데이터
  부여"에 해당하며 이미 좋은 실천이다. Contextual Retrieval은 이를 한 단계 더 자동화해, **신규
  소스(API 문서, Tool 설명 등)를 넣을 때 사람이 태그를 안 달아도 LLM이 청크-문서 관계를 자동
  주석**하게 만드는 방향이다 — "데이터만 넣으면 RAG가 구성된다"는 사용자 요구사항의 구체적 구현
  기법으로 직접 채택 가능.
- **BM25 하이브리드 검색**: 벡터 임베딩은 의미 유사도엔 강하지만 정확한 식별자(에러코드, API
  엔드포인트명, 필드명 등 — 앞으로 넣을 API/Tool 문서에 많을 유형)에는 약하다. BM25(키워드 정확
  매칭)를 병행하는 것이 표준 권고이며, 우리가 다룰 "API/Tool 문서"류 데이터는 특히 BM25 이득이 큰
  카테고리다(예: "get_top_caller_tool 파라미터가 뭐야" 같은 질의).

### 1.3 상용/오픈소스 벤더 비종속 아키텍처 사례

| 사례                                                  | 벤더 비종속 설계 방식                                                                                                                                                                 | 투명성 기능                                                                                           |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| **LangChain `DocumentLoader` + `VectorStore` 추상화** | 소스별 로더(≈150종: PDF/Notion/Confluence/OpenAPI/GitHub 등) → 공통 `Document` → 교체 가능한 벡터스토어(Chroma/Pinecone/PGVector 등)                                                  | LangSmith로 각 단계 trace(검색된 문서·점수) 시각화                                                    |
| **LlamaIndex `IngestionPipeline`**                    | `Transformation`(청킹/메타추출/임베딩)을 리스트로 선언, 소스 무관하게 동일 파이프라인 재사용. `docstore`+`vector_store`+`index_store` 3중 저장소 분리로 벤더 교체 시 영향 범위 최소화 | `Reader`별 자동 메타데이터(`file_name`, `page_label` 등) 부여로 "어느 소스에서 왔는지" 항상 추적 가능 |
| **Haystack (deepset) `Pipeline`**                     | YAML로 컴포넌트 그래프를 선언(색인/검색/생성 컴포넌트를 노드로 연결) — 코드 변경 없이 컴포넌트 교체                                                                                   | 파이프라인 YAML 자체가 "이 RAG가 어떤 순서로 동작하는지"의 투명한 문서 역할                           |
| **Microsoft Kernel Memory**                           | "Memory Pipeline" 개념 — 문서 수집(import)→분할→임베딩→저장을 단계별 핸들러 체인으로 커스터마이징 가능, 각 단계 상태를 조회 API로 노출                                                | `/upload-status` API로 색인 진행 상황을 실시간 조회 가능(투명성 사례로 참고할 만함)                   |

**공통 패턴**: 세 프레임워크 모두 "소스 어댑터(로더) → 정규화된 중간 표현 → 파이프라인(청킹/임베딩) →
교체 가능한 저장소"의 4단 계층을 채택한다. 우리 저장소가 벤더 종속을 피하려면 이 계층 구조를
`manual_indexer.py`(현재는 마크다운 전용) 위에 얹어야 한다.

| 데이터 유형                                                                   | 특성                                                                                | 권장 처리 방식                                                                                                                                                                                                       |
| ----------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **도움말 Q&A**(현재 매뉴얼)                                                   | 짧고 구조화됨(질문-답변 쌍)                                                         | 현재 방식(섹션 파싱+태그) 유지, Contextual Retrieval로 보강                                                                                                                                                          |
| **API/Tool 문서**(OpenAPI 스펙, LangChain Tool docstring 등)                  | 파라미터명·타입·필수여부 등 **정확한 식별자** 중심, 자연어보다 구조 데이터에 가까움 | 자유 텍스트 임베딩보다 **BM25/정확매칭 우선 + 구조화 메타데이터 필터**(우리의 `_build_writable_fields_hint()`가 이미 "docstring에 정확한 필드명을 동적 삽입"하는 방식으로 유사 문제를 해결한 선례 — RAG로 확장 가능) |
| **정책/운영 매뉴얼**(장문, 문맥 의존)                                         | 청크 분리 시 맥락 손실 위험 큼                                                      | Contextual Retrieval(청크별 요약 프리픽스) 필수 후보                                                                                                                                                                 |
| **관계형 지식**(화면→설정→적용 가능 유형처럼 여러 홉을 거쳐야 답이 나오는 것) | 단일 벡터 검색으로 못 찾음, 그래프 순회 필요                                        | 이미 구현된 `knowledge_graph.py::traverse()`(2-hop) 방식 유지·확장 — Full GraphRAG 대신 **명시적 스키마 기반 소규모 그래프**가 여전히 적절(§2.2에서 근거 재확인)                                                     |

## 2. 지식베이스 구성 투명성 — "무엇이 들어있는지"를 보여주는 방법

### 2.1 시장 동향: RAG Observability/Evaluation 도구

- **RAGAS**(오픈소스 RAG 평가 프레임워크): `context_precision`/`context_recall`/`faithfulness`/
  `answer_relevancy` 4대 지표로 "검색된 컨텍스트가 실제로 관련 있었는지"를 정량화. 우리가 "지식베이스
  구성상황을 투명하게"라고 할 때, 정성적 나열(문서 목록)뿐 아니라 **이 지표 기반 정량 대시보드**가
  업계 표준 접근이다.
- **LangSmith / Langfuse (오픈소스 LLM observability)**: 각 RAG 호출마다 "어떤 쿼리 → 어떤 청크
  top-K가 검색됐는지 → 점수는 얼마였는지 → 최종 프롬프트에 뭐가 들어갔는지"를 trace로 남겨 UI에서
  drill-down 가능하게 함. 우리 저장소가 이미 갖춘 `logs/app.log` 구조화 로그(structlog)에 이 수준의
  RAG trace 필드(검색 쿼리, top-K 문서 ID·점수, 최종 사용 청크)를 추가하면 **자체 구현으로 상당 부분
  달성 가능**(별도 SaaS 도입 없이).
- **문서 계보(lineage) 메타데이터**: 업계 표준은 각 청크에 `source_uri`/`ingested_at`/`source_version`/
  `chunk_index`/`domain_tags`를 필수 메타데이터로 부여해, "이 답변이 어느 원본 문서 몇 번째 청크에서
  왔는지"를 사용자(운영자)가 역추적 가능하게 하는 것이다.

### 2.2 저장소 현황과의 격차

- **있음**: Story 2.4의 `GET /catalog-config/export`(카탈로그/화면 설정 export), Story 1.18의
  `GET /intellidecision-policy`(유형 9종 표/그래프 뷰) — **구조화 데이터(카탈로그·정책)**의 투명성은
  이미 상당 부분 확보됨.
- **없음**: **매뉴얼 RAG(ChromaDB 색인) 자체의 인벤토리 조회 API**가 없다. 어떤 문서가 몇 개 청크로
  색인됐는지, 마지막 색인 시각, owner별 격리 상태 등을 확인하려면 코드/스크립트로 직접 ChromaDB를
  조회해야 한다(`_check_emb_meta.py` 같은 1회성 스크립트가 이미 존재한다는 사실 자체가 이 공백의
  증거). 이는 사용자가 지적한 "구성상황이 투명하게 안 보인다"의 핵심 원인으로 판단된다.
- **제안 방향(상세 설계는 후속 BMAD Story)**: `GET /api/self-service/knowledge-base/inventory` 같은
  읽기 전용 엔드포인트를 신설해, ChromaDB 컬렉션별 문서 수·도메인 분포·최근 색인 시각·소스 유형(마크다운/
  API 문서/기타)을 집계해 반환하고, Story 1.18의 "AI 의사결결정 로직" 탭과 나란히 "지식베이스 현황"
  탭을 추가하는 것이 기존 UI 패턴(축 C-1)의 자연스러운 확장이다.

## 3. IntelliDecision 분기별 RAG 매칭 예측 — "어떻게 매칭될지 투명하게 보여야 한다"

### 3.1 학술적 배경: Query Routing과 RAG-Fusion

- **Query Routing**(Advanced RAG의 핵심 모듈, Gao et al. 서베이 §Pre-retrieval): 질의를 여러 검색
  전략/인덱스 중 하나로 라우팅하는 기법 — 우리의 IntelliDecision(유형 A~I 분기)이 사실상 "RAG를
  포함한 전체 응대 전략의 라우터" 역할을 하고 있다. 즉 IntelliDecision과 RAG 매칭은 이미 개념적으로
  연결된 하나의 라우팅 문제다.
- **RAG-Fusion / Multi-Query Retrieval**: 하나의 사용자 질의를 LLM으로 여러 변형 질의로 확장해 각각
  검색한 뒤 결과를 합치는 기법 — "이 발화가 어떤 검색으로 이어질지"를 사전에 시뮬레이션하는 것과
  본질적으로 같은 방향성(우리가 원하는 "예측 가능성"의 근접 사례).
- **Anthropic, Building Effective Agents(2024-12) "Routing" 패턴**: "분류 후 전용 경로로 처리"의
  이점 중 하나로 **"각 경로에 대해 별도의 프롬프트/도구/가드레일을 최적화할 수 있다"**를 명시한다.
  이는 IntelliDecision 유형별로 "이 유형은 RAG를 어떤 필터·어떤 top-K로 쓰는지"를 **유형별 정책
  레지스트리 항목으로 명시**해야 한다는 근거가 된다.

### 3.2 저장소 현황과의 격차 — "예측"이 안 되는 이유

현재 `intellidecision_policy.py`(Story 1.18/1.19)는 유형 A~I의 **응대 전략**(Tool 필요 여부, 확인
발화 필요 여부 등)은 데이터화되어 있으나, **"이 유형일 때 RAG 검색이 어떤 조건(doc_type, owner
필터, top-K, 재순위화 여부)으로 실행되는지"는 레지스트리에 없고 코드(`self_service_agent_node`)에
암묵적으로 흩어져 있다**. 즉 유형별 프롬프트 전략은 투명해졌지만, "유형별 RAG 매칭 전략"은 아직
2026-07-27 리서치가 지적했던 "정적 프롬프트 산문" 문제와 동일한 종류의 암묵성이 RAG 쪽에 남아있다.

### 3.3 제안 방향 — RAG 정책도 IntelliDecision 레지스트리 패턴으로 데이터화

`intellidecision_policy.py`의 유형별 항목에 다음과 같은 **RAG 매칭 메타데이터 필드**를 추가하는
방향을 제안한다(설계 상세·API 스키마는 후속 BMAD PRD/architecture 단계에서 확정):

- `rag_enabled`: 이 유형이 RAG 검색을 트리거하는지 여부(예: 유형 A/C는 O, 유형 B 순수 실행형은 X 가능)
- `rag_source_scope`: 어떤 doc_type/domain 범위에서 검색할지(현재 owner 필터는 이미 있으나 "유형별
  범위"는 암묵적)
- `rag_strategy_hint`: 벡터 단독 vs 하이브리드(BM25+벡터) vs 그래프 순회(`knowledge_graph.traverse`)
  중 어느 전략이 이 유형에 적합한지 — Screen Graph 2-hop이 이미 유형 B/E(실행성) 쪽에 연결된 것처럼,
  향후 API/Tool 문서 검색은 유형 C(포괄적 도움 요청)에 하이브리드 검색을 붙이는 식으로 매핑 가능
- 이 메타데이터를 Story 1.18의 `GET /intellidecision-policy` 응답에 함께 노출하면, **"이 유형의
  발화가 들어오면 어떤 지식 소스가 어떤 전략으로 매칭될 예정인지"를 운영자가 대화 실행 전에도 표에서
  미리 확인**할 수 있다 — 사용자가 요구한 "분기마다 매칭이 어떻게 될지 투명하게 예상 가능"의 직접적
  구현.
- 실행 시점 검증(사후 투명성)은 §2.1의 RAG trace 로깅(검색 쿼리·top-K 문서·점수)과 짝을 이뤄야
  완전해진다 — **사전 예측(정책 레지스트리 표시)과 사후 실측(trace 로그)을 모두 갖춰야** "예상"과
  "실제"를 비교 검증할 수 있다(설명가능성의 핵심 요건).

### 3.4 Hop 관리 — 규모에 맞는 절충안 재확인

Full GraphRAG(엔터티 자동추출+커뮤니티 클러스터링)는 이번에도 데이터 규모·관계 복잡도 기준으로는
과설계 판정을 유지한다(§0에서 이미 구분했듯 이는 "그래프 알고리즘" 축의 문제). 그러나 사용자가
언급한 "hop 관리"는 이미 Story 1.18의 `knowledge_graph.py::traverse()`(화면→writable 여부→적용
가능 유형, 2-hop)로 프레임워크가 마련되어 있다 — **신규 데이터 소스(API/Tool 문서)가 늘어나면 이
그래프에 새 노드 타입(예: "API 엔드포인트" 노드, "Tool" 노드)을 추가하고 hop 수를 3~4단계로
점진적으로 확장하는 것**이 Full GraphRAG 전면 도입보다 우리 규모에 맞는 절충안이다(Rasa/Dialogflow
비교 리서치, §1.5의 "하이브리드" 결론과 일관됨).

| ③IntelliDecision 분기별 RAG 매칭 사전 예측 | Query Routing(Advanced RAG), Anthropic Routing 패턴("경로별 최적화")        | `intellidecision_policy.py`에 `rag_enabled`/`rag_source_scope`/`rag_strategy_hint` 필드 추가 + 기존 API 응답에 노출(사전 예측) + RAG 실행 시 trace 로깅 추가(사후 검증), 둘을 대조 가능하게 구성                                         |

**공통 원칙(과거 리서치와의 일관성 유지)**: Full GraphRAG·독립 벡터DB 네임스페이스 물리 격리 등
"인프라 복잡도가 큰" 옵션은 여전히 이 규모엔 Non-Goal로 유지한다. 이번 요구사항의 본질은 "더 큰
그래프 알고리즘"이 아니라 **"소스 어댑터의 플러그인화(벤더 비종속) + 기존 관측성 부재 해소(투명성)
+ 이미 있는 정책 레지스트리 패턴을 RAG 매칭 메타데이터까지 확장(예측 가능성)"**이며, 세 방향 모두
기존 저장소 패턴(레지스트리+화이트리스트, Story 2.x의 카탈로그 동적화, Story 1.18의 정책 레지스트리)을
그대로 재사용할 수 있어 구조적 위험이 낮다.

**다음 단계 제안**: 사용자 승인 시 BMAD 절차(PRD 증분 반영 → architecture 갱신 → Story 분할)로 진행.
우선순위는 ②(투명성, 저위험·즉시 가치)→③(레지스트리 확장, 기존 패턴 재사용)→①(소스 어댑터 리팩터링,
범위가 가장 큼) 순서를 권장하되, 최종 우선순위는 사용자 확인 후 확정한다.
